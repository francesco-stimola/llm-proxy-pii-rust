## Round 1 (2026-07-20)

**What I verified independently.** All via PowerShell (Git Bash's `link.exe` shadows the MSVC linker).

- `cargo build` green. `cargo clippy-onnx -- -D warnings` **clean**. `cargo clippy-directml -- -D warnings`
  **clean**. `cargo test-onnx`: **143 lib** + adversarial 10 + anthropic\_messages\_e2e 10 + binary\_smoke 1
  + complexity 4 + dependency\_footprint 1 + log\_safety 1 + ner\_corpus 2 + ner\_eval 1 + perf 2 +
  pii\_corpus 5 + pii\_pipeline 16 + pii\_properties 4 + proxy\_e2e 15 — **green, zero warnings**. The three
  new EP unit tests (EP-01..03) run and pass.
- **Drove the real binaries end-to-end**, not just the test harness: the default build, the `onnx` build,
  and a freshly rebuilt `target/directml` build, against the real XLM-R int8 model.
- **Reproduced the DEVLOG's DirectML numbers with the shipped tool.** `--bench-providers` on the DirectML
  build: CPU-int8 **27.1 / 46.5 / 108.4 ms**, DML-int8 **101.1 / 346.1 / 599.3 ms** at seq 128/256/512
  (DEVLOG recorded 26.5/47.1/121.3 and 104.8/344.3/607.6). The verdict, the ranking, and the int8 `!!`
  warning all reproduce. **The M9 measurement is honest and the NO-GO conclusion stands.**
- Verified the non-`onnx` build's `--bench-providers` explains rather than errors — as claimed.
- Verified the typo path end-to-end: `NER_EXECUTION_PROVIDER=directl` →
  `Error: unknown NER_EXECUTION_PROVIDER "directl" (expected one of: …)`, **exit 1**, before any listener
  binds. The error reaches the operator verbatim. **No finding** — builder's doubt #3 resolved.

**The safety questions the handoff raised, and what I found by trying to break them:**

- **The untested-EP argument is sound for leaks — I could not break it.** I traced all three paths the
  builder named. (1) *Structured layer:* `StructuredRecognizers` is pure CPU regex with no ONNX
  involvement — no EP can reach it. (2) *Fixpoint:* **both** ML detectors return `Ok(Vec::new())` from
  `redetect` (`onnx.rs:674`, `gliner.rs:470`), so the NER contributes on pass 0 only and an EP cannot
  add, remove, or lengthen a masking pass — the fixpoint's termination is independent of the backend.
  (3) *`NER_REQUIRED` posture:* an EP-induced `session.run` error propagates through `try_detect` exactly
  like any other inference error — unwrapped → 400 (fail-closed), wrapped → structured-only. An EP can
  change *availability* and *NER recall*; it cannot forward an unmasked structured value. **The blast
  radius as documented is correct.** (One documentation gap in its *timing* — see [M9-R11](#m9-r11).)
- **Fallback under `NER_REQUIRED` is the right call — I agree with the builder, for a sharper reason
  than the docs give.** `NER_REQUIRED` is a *detection-posture* knob ("the ML layer must be present and
  must not silently degrade"), not a performance knob. CPU is the reference implementation, so falling
  back to it degrades nothing the posture is about — it costs latency only. Making it fatal would let a
  driver update take down a privacy proxy that is still masking perfectly. **No finding on the posture.**
  The docs' *justification* for it is self-contradictory, though ([M9-R6](#m9-r6)), and what the operator
  is told afterwards is wrong ([M9-R1](#m9-r1)).
- **Where it did break: the honesty guarantees, not the masking.** M9's stated goal is that an operator
  never believes a GPU is engaged when it isn't. The mechanism built for that (`build_session_reporting`)
  was wired to the **benchmark** and not to the **server** — so the production startup line reports the
  requested provider as if it were effective ([M9-R1](#m9-r1)), the pool can silently end up
  half-GPU/half-CPU ([M9-R2](#m9-r2)), and the report's `ok` overstates what ORT actually did
  ([M9-R5](#m9-r5)). This is the M4-retrospective shape: *the fix exists and a sibling path didn't get
  it.*

**Net: no leak, no fail-open regression, no over-masking, and the DirectML verdict is reproducible and
correctly reasoned.** Nothing in M9 can forward raw PII, and I could not construct an input where it
does. The eleven findings below are observability, correctness-of-diagnostics, one fail-open CLI surface,
and docs. **None is a leak.**

<a id="m9-r1"></a>
### M9-R1 — the server logs the **requested** provider as if it were the **effective** one (observability)

**Confirmed live, not reasoned.** Booting the plain `onnx` build (no `ep-*` feature) with
`NER_EXECUTION_PROVIDER=directml` and `NER_REQUIRED=1`:

```
WARN …pii::onnx: accelerated execution provider failed to initialize; falling back to CPU
     provider="directml" error=register execution provider: The execution provider could not be
     registered because its corresponding Cargo feature is not enabled.
…303 lines of ORT INFO chatter…
INFO …server: ONNX NER detector loaded model="…model_quantized.onnx" pool_size=1
     intra_threads=12 provider="directml"
```

The session is running **on CPU**. The line that is this codebase's *record of effective config* says
`provider="directml"`.

**Mechanism.** `server.rs:337-343` logs the `provider` variable it passed *in* — the requested one —
because `OnnxNerDetector::load` (`onnx.rs:420-453`) builds through `build_session`, which
**discards** the effective provider (`onnx.rs:327`: `.map(|(session, _)| session)`). `load_gliner`
(`server.rs:438-445`) has the identical defect. `build_session_reporting` (`onnx.rs:338`) exists
precisely to prevent this and is called only from `bench.rs:153`.

**The comment directly above that log line already states the invariant it now breaks**
(`server.rs:334-336`):

> `// Both values are the **effective** ones — resolved once, above, and handed to `load` unchanged —`
> `// so this line can never name a pool the process doesn't have (M7-R5).`

`provider` was added as a **third** field to a statement whose contract is *"every field here is the
effective value"* — and it is the one field that isn't. The comment now vouches for it.

**Why this is the M4 pattern, not a nit.** M9's own commit message states the goal as *"rather than
silently running CPU behind an operator who believes a GPU is engaged"*, and M7-R5 already established
this codebase's rule for exactly this line: *"a derived value an operator cannot reproduce from the
logged inputs defeats the reason it is logged."* The honesty mechanism was built, then wired to the
diagnostic tool and not to the thing that runs in production. The `warn!` is real but is not a
substitute: it is emitted 300+ lines earlier, is invisible at `RUST_LOG=error`, and an operator
grepping `provider=` — the field the codebase deliberately added for this — reads `directml`.

**Fix.** Thread the effective provider out of the loaders: have `OnnxNerDetector::load` /
`GLiNerDetector::load` build through `build_session_reporting` and return (or expose) the effective
provider, then log `provider = effective.as_str()` — and, when it differs, `requested` alongside, so
the fallback is legible on the one line that claims to describe the running config.

**Test.** A unit test over the reporting seam: build a session requesting an EP whose feature is not
compiled and assert the returned effective provider is `Cpu`. That already holds for
`build_session_reporting`; the missing coverage is that the **server's logged value** is derived from
it rather than from the request — assert the loader surfaces `Cpu`, not `DirectMl`, in that scenario.

**CLOSED (builder, 2026-07-20).** The effective provider now reaches the log. `build_session_pool`
returns `(sessions, effective)`; both detectors store it and expose `provider()`; `server.rs` derives the
`provider=` field from `detector.provider()` through a shared `log_ml_detector_loaded`, which **escalates to
`warn!` and adds `requested=`** when the two differ — so a fallback is legible on the one line that claims to
describe the running config, not only in a warning 300 lines earlier. The dead `build_session` wrapper (the
one that discarded the effective value) was **removed**, so the discarding path no longer exists to be reused.
Test: `NER-EP-01` (`tests/ner_perf.rs`, model-gated) asserts a detector requesting an unavailable EP reports
`Cpu`, for pool sizes 1 and 2.

### M9-R2 — a session pool can end up **heterogeneous**: some sessions on the GPU, some on CPU (correctness)

**Mechanism.** `OnnxNerDetector::load` (`onnx.rs:437-444`) loops `pool_size` times calling
`build_session`, and **each call decides independently** whether the accelerator initializes.
`GLiNerDetector::load` (`gliner.rs:123-131`) is the same. Nothing requires the pool to be homogeneous
and nothing detects that it isn't. Requests are then dispatched round-robin
(`onnx.rs:591`: `self.next.fetch_add(1, …) % self.sessions.len()`).

**Failure scenario — and it is not exotic on the very hardware M9 targets.** ORT's own device probe in
my run reports `DxgiVideoMemory=512 MB` for this box's iGPU, while the DEVLOG records the XLM-R fp16
export at **555 MB** and each session at ~270 MB. With `NER_POOL_SIZE=2` and
`NER_EXECUTION_PROVIDER=directml`, session 0 acquiring the device and session 1 failing on VRAM
exhaustion is the *expected* outcome, not a corner case. The proxy then holds one DirectML session and
one CPU session and alternates between them. The same input text yields whichever backend's logits the
round-robin index lands on — so a name masked on one request can be missed on the next, **within a
single process, with no configuration change**. The content-keyed cache (`pii::cache`) then pins
whichever answer happened to be computed first, keyed on bytes, and serves it to both.

**Why it matters here specifically.** ARCHITECTURE's *NER threading* section rests on a measured
property — `m7_r3_intra_threads_changes_speed_not_detection` — that detection does not vary with
execution shape, and states that *"an execution-provider swap must re-run that guard."* A heterogeneous
pool doesn't just swap the backend, it makes the backend **a per-request variable**, which is a
strictly stronger assumption than the guard was ever run against. Bounded to NER recall (never the
structured layer), so not a leak — but it is nondeterminism the design does not know it has.

**Fix.** Make the pool homogeneous by construction: resolve the effective provider **once** (build the
first session via `build_session_reporting`, then build the remainder on the provider it actually
got), so the pool is uniformly GPU or uniformly CPU. Log that single effective provider — this is the
same edit as [M9-R1](#m9-r1). If a later session fails on an EP the first one got, fall the *whole
pool* back to CPU rather than mixing.

**Test.** Construct a two-session pool requesting an uncompiled EP and assert every session reports the
same effective provider. The stronger property — *all sessions in a pool share one backend* — is worth
pinning as an invariant test, since the failure is silent by nature.

**CLOSED (builder, 2026-07-20).** Pools are homogeneous by construction. `onnx::build_session_pool` builds
the **first** session, keeps the provider it actually got, and builds the rest on *that*; if a later session
cannot match it (the VRAM case this finding names), the **whole pool is rebuilt on CPU** with a `warn!` rather
than served mixed. Both detectors route through it, so the backend can no longer be a per-request variable.
Test: `NER-EP-01` runs the `pool_size = 2` case and asserts the single reported effective provider.

### M9-R3 — `--bench-providers` ignores `NER_INTRA_THREADS` / `NER_POOL_SIZE`, so its CPU baseline is not the CPU the server runs (correctness)

**Reproduced live.** With `NER_POOL_SIZE=2` and `NER_INTRA_THREADS=3` set — i.e. the server would give
each session **3** intra-op threads — the report prints:

```
  cores : 12 (CPU intra-op threads)
  …
  => FASTEST: cpu on model_quantized (112.1ms).
```

It measured with **12**, and labelled 12 as the intra-op thread count.

**Mechanism.** `bench.rs:191`: `let intra_threads = available_cores();`. The server resolves the same
quantity through `onnx::resolve_pool_and_intra(NER_POOL_SIZE, NER_INTRA_THREADS, cores)`
(`server.rs:313-317`). The two agree only at the shipped default (`pool=1` → `intra=cores`) and diverge
the moment an operator touches either knob.

**Consequence.** The CPU row is measured with up to `pool ×` more threads than production gives it, so
the CPU baseline is **optimistic** and the recommendation is biased **against** the accelerator — on
exactly the tuned, centralized deployment where an accelerator is most likely to be worth having. The
header line compounds it by presenting the wrong number as the configured one.

**Why this one stings.** It is [M7-R1](M7.md#m7-r1)'s failure class verbatim — *the harness and the
server resolving the same knob differently, so the benchmark measures a configuration nobody runs* —
and `resolve_pool_and_intra` exists solely to make that impossible. The same commit invokes M7-R1 by
name when unifying **model** resolution (`server.rs:201-204`: *"a second copy of this resolution would
let the two drift"*) and then hardcodes the **thread** resolution one file over. The lesson was applied
to one knob and not to its neighbour.

**Fix.** Resolve `(pool, intra)` in `run_provider_benchmark` via `resolve_pool_and_intra` and pass
`intra` into `benchmark_matrix`; print both in the report header instead of raw `cores`.

**Test.** Assert `benchmark_matrix`'s thread count is the one `resolve_pool_and_intra` returns for the
same env — the M7-R1 guard (`the_harness_and_the_server_cannot_disagree_about_the_default`) shaped for
the benchmark.

**CLOSED (builder, 2026-07-20).** `run_provider_benchmark` now resolves the thread shape through
`onnx::resolve_pool_and_intra` — the same call the server makes — and passes `intra_threads` into
`benchmark_matrix`. The report header prints the **effective** shape
(`threads: N intra-op per session, pool M (of C cores)`) instead of the raw core count, so the number shown is
the one measured and the one production uses. M7-R1's lesson now applies to both knobs it was written for.

### M9-R4 — an unrecognized CLI argument silently **starts a live proxy** instead of failing (hardening, fail-open)

**Reproduced live on the freshly built `onnx` binary.** Each of these starts the proxy and binds the
listener:

```
llm-proxy-pii-rust.exe --bench-provider      # typo (singular)  -> LISTENING on 127.0.0.1:18099
llm-proxy-pii-rust.exe --bench-providers=1   # `=` form         -> LISTENING
llm-proxy-pii-rust.exe --help                #                  -> LISTENING
```

**Mechanism.** `main.rs`: `if std::env::args().skip(1).any(|a| a == BENCH_PROVIDERS_FLAG)`. Anything
that isn't that exact string is discarded, and control falls through to `Config::from_env()` + `run`.

**Failure scenario.** An operator types the flag slightly wrong — or, as I hit myself, runs a binary
that predates the flag — and instead of a measurement gets a **listening proxy pointed at the default
`https://api.openai.com`**, with no output saying so at `RUST_LOG=warn`. They walk away believing they
ran a diagnostic. (This is how I first hit it: `target/directml/` held a binary built before the flag
landed; it ignored `--bench-providers` and served on :8080 for ten minutes. The staleness hazard is
already documented in `.cargo/config.toml`; the *silent-serve* response to it is not.)

**Why it belongs to M9.** M9 created this surface — before it, the binary had no arguments and
ignoring them was harmless. And the project's stance on precisely this shape is already written down,
one layer down, in this same milestone: a typo'd `NER_EXECUTION_PROVIDER` **fails startup** rather than
doing something else silently ([M9-R1](#m9-r1)'s neighbour, EP-02, M8-R5's rule). The argument parser
violates the rule the flag it introduced was built to honour — and fails **open**: unexpected input →
serve, where every other unexpected-input path in this codebase blocks or refuses.

**Fix.** Reject unknown arguments: anything in `args().skip(1)` that is not `--bench-providers` is an
error naming the bad argument and listing what is accepted, exiting non-zero before any listener binds
— the same shape `ExecutionProvider::parse` already uses. A `--help` that prints usage and exits 0 is
the natural companion.

**Test.** Extend the `tests/binary_smoke.rs` pattern: spawn the real `.exe` with `--bench-provider` and
assert it exits non-zero *and* never becomes healthy on its port. The "never binds" half is the point —
asserting only the exit code would miss a proxy that serves and then exits.

**CLOSED (builder, 2026-07-20).** `main.rs` parses arguments explicitly: `--bench-providers` runs the
benchmark, `--help`/`-h` prints usage and exits 0, and **anything else is refused** with a message naming the
bad argument, before `Config::from_env` and before any listener binds. Tests: `CLI-01`
(`unknown_cli_argument_is_refused_and_never_binds`) asserts both halves — non-zero exit **and** that the port
never becomes reachable — and `CLI-02` covers `--help`. Both run in the ordinary `cargo test-onnx` suite.

### M9-R5 — `engaged()` / `ok` reports **registration**, not execution: ORT's per-node CPU fallback is counted as an accelerator measurement (docs / diagnostics)

**The builder's doubt #4, confirmed with ORT's own logs.** From my DirectML `--bench-providers` run
(`RUST_LOG=info`), in one session build:

```
INFO ort::ep: Successfully registered `DmlExecutionProvider` source=session options
…
INFO ort::logging: ORT optimization- Force fallback to CPU execution for node: /roberta/Gather …
INFO ort::logging: … for node: /roberta/Unsqueeze_2 …  (8+ nodes)
WARN ort::logging: Some nodes were not assigned to the preferred execution providers which may or
     may not have an negative impact on performance.
```

and the report for that same row printed:

```
  directml     |     101.1ms |     346.1ms |     599.3ms | ok
```

ORT emitted a **WARN** that nodes were not assigned to the preferred EP; the report says `ok`.

**Mechanism.** `ProviderResult::engaged()` (`bench.rs:55`) is `requested == effective`, and `effective`
comes from `build_session_reporting`, which only distinguishes *registration succeeded* from
*registration failed* (`onnx.rs:344-363`). ORT's graph partitioning — which assigns nodes per-EP and
force-falls-back whatever the EP handles poorly — happens *after* registration and is invisible to it.

**What is and isn't wrong.** The **numbers are honest** and the **decision is correct**: 599.3 ms is
genuinely what an operator gets by setting `NER_EXECUTION_PROVIDER=directml`, partitioning included, so
the recommendation is sound. What overclaims is the *guarantee* the docs attach to it:

- `ARCHITECTURE.md:767` — *"**A fallback is reported, never counted.** `build_session_reporting`
  returns the *effective* provider, so a row whose accelerator did not engage prints
  `unavailable — fell back to cpu` instead of quietly presenting CPU timings under a GPU's name."*
- DEVLOG 2026-07-19 — *"a session that falls back is reported as `unavailable — fell back to cpu`
  rather than silently logged as a GPU measurement."*

Both are true **only at session granularity**. Per-node fallback — the exact mechanism the report's own
quantization NOTE describes ("its ops partition badly onto GPU providers") — is presented as `ok`. The
report explains the phenomenon in prose while its status column denies it, which is the reading an
operator will trust.

**Fix (docs, in my lane once the wording is agreed).** Qualify the claim: the effective-provider
contract covers **registration**, and ORT may still place individual nodes on CPU inside a registered
EP, so `ok` means *"the EP was registered and these are the timings you will actually get"*, not *"the
whole graph ran on the accelerator."* Worth promoting to ARCHITECTURE next to the bullet, since it is
the property that makes the *quantization* lesson mechanical rather than folklore. Optionally surface
it in the tool: ORT's "not assigned to the preferred execution providers" warning is available and a
`partial` status would be truer than `ok`.

**Test.** Not CI-testable (needs real hardware + a real EP). The guard is the documented wording.

**CLOSED (builder, 2026-07-20), as documentation — the wording was the deliverable.** ARCHITECTURE's
bullet now states the contract at **session granularity** and says plainly that ORT may still place individual
nodes on the CPU inside a registered EP, so `ok` means *"the EP was registered, and these are the timings you
will actually get"* — not "the whole graph ran on it". Per-node partitioning is also listed as one of the three
things the fallback does **not** catch, and tied to the quantization lesson (int8-on-GPU is slow *because* its
ops partition back). The README carries the same caveat. A `partial` status in the tool is left undone
deliberately: the numbers are already honest, and the claim was the only thing overreaching.

### M9-R6 — ARCHITECTURE contradicts itself on the fallback's safety, in adjacent paragraphs (docs)

`ARCHITECTURE.md:700-701` justifies the CPU fallback with:

> …drops to CPU with a `warn!`, because *a privacy proxy must start*, and masking is
> **bit-identical on any backend** (only slower).

Eight lines later, `ARCHITECTURE.md:709-712`:

> **The fallback covers *initialization*, not *numerical correctness*…** An accelerator that registers
> but **computes subtly different logits than the CPU** is *not* caught by the fallback.

These cannot both hold. The second is correct (and is the load-bearing claim for the untested-EP trade);
the first is the one an operator reads when deciding whether the fallback is acceptable under
`NER_REQUIRED` — the exact question the builder flagged.

**What was meant** is the *converse*, and it is true and worth stating precisely: **CPU is the reference
implementation**, so falling *back to* it can only cost latency, never masking quality. The error is the
generalization to "any backend."

**Fix.** Reword to the directional claim: *"…because a privacy proxy must start, and CPU is the
reference implementation — falling back to it costs latency, never masking quality (the reverse
direction is not symmetric; see the note below)."*

**Test.** None — prose. But this is the sentence that answers "is fallback right under `NER_REQUIRED`?",
so it should say what it means.

**CLOSED (builder, 2026-07-20).** The contradiction is gone. The justification now makes the
**directional** claim the finding identified as what was meant: *CPU is the reference implementation, so
falling back to it costs latency, never masking quality* — with an explicit note that the symmetric reading
("every backend computes identically") is false and points at the note below. The paragraph also now carries
the `NER_REQUIRED` reasoning the reviewer supplied: it is a detection-posture knob, and dropping to the
reference implementation degrades nothing that posture is about.

<a id="m9-r7"></a>
### M9-R7 — the provider table marks DirectML "✅ tested" with the same symbol as CPU, while the prose says no EP is trusted until the determinism guard is re-run (docs)

**This is my answer to the builder's open question**, and it is narrower than the question assumed.
Not re-running the cross-thread determinism guard for DirectML is **defensible**: DirectML is not the
default, requires both a build flag and an env var, and was measured a NO-GO on this hardware anyway.
Documenting the requirement is the right call. **The defect is that the table contradicts the
documentation.**

`ARCHITECTURE.md:717-718`:

> …the tested one still owes the cross-thread-determinism guard above: **an execution-provider swap
> must re-run it** before the backend is trusted…

and the table immediately below:

| `cpu` (default) | … | ✅ **tested** — the always-on baseline |
| `directml` | … | ✅ **tested** — this box's AMD DX12 iGPU |

`cpu` has passed `m7_r3_intra_threads_changes_speed_not_detection`; `directml` has not been run against
it at all. The same ✅ for both says the opposite of the sentence above it, and a future builder
scanning the table — which is what tables are for — will read DirectML as trusted. Compounded by
[M9-R2](#m9-r2): the guard was never run against a *heterogeneous* pool either, which is a stronger
condition than the guard ever contemplated.

**Fix.** Split "measured" from "trusted" in the Status column, e.g. `directml` → *"⚠️ **benchmarked**,
determinism guard NOT re-run — see the note above"*, and state explicitly that **`cpu` is the only
provider that has passed the cross-thread determinism guard.** Then the table and the prose say the
same thing.

**Test.** The guard itself (`ner_perf.rs::m7_r3_…`) already exists; nothing new to write until someone
runs it under an EP. Recording *that it has not been run* is the deliverable.

**CLOSED (builder, 2026-07-20).** *Measured* and *trusted* are now separate. A lead-in states that **only
`cpu` has passed the cross-thread determinism guard and no accelerator has been run against it at all**;
`cpu` is marked ✅ **trusted**, DirectML is 📊 **benchmarked, not trusted — determinism guard not re-run**, and
a closing sentence says nothing above `cpu` should be read as safe to trust blindly (safe to *try*, which is
what the fallback and the bounded blast radius buy). The table and the prose now agree.

<a id="m9-r8"></a>
### M9-R8 — `--bench-providers` cannot benchmark a BERT-family model: it never sends `token_type_ids` (correctness)

**Mechanism.** `bench.rs::run_once` (`bench.rs:122-136`) always builds exactly two inputs,
`input_ids` and `attention_mask`. `run_provider_benchmark` (`server.rs:254`) never reads
`NER_TOKEN_TYPE_IDS`, and `resolve_ner_model` doesn't return it. But the detector path does
(`server.rs:318`: `let needs_token_type_ids = env_flag("NER_TOKEN_TYPE_IDS");` →
`onnx.rs:596-606`, which sends a third tensor), and the model contract in `onnx.rs:13-17` plus
`SETUP.md:107-109` document `NER_TOKEN_TYPE_IDS=1` as the supported BERT-family path (Piiranha).

**Failure scenario.** An operator running a BERT-family model — the configuration the rest of the
codebase supports — runs `--bench-providers` and **every row fails**, because ORT rejects a `run()`
missing a required graph input. The report then prints `FAILED: ONNX run: …` for each and concludes
`=> No (model, provider) pair completed the benchmark.` with no hint that the cause is a missing input
the tool chose not to send. The benchmark is unusable for that operator, and the failure doesn't name
its own reason.

**Why it slipped.** `run_provider_benchmark`'s doc comment states the design rule — *"the benchmark
deliberately measures the model the proxy would actually run"* — and `resolve_ner_model` was extracted
to one home so the **model path** cannot drift. The *input contract* for that model was not carried
across with it. (I could not reproduce this end-to-end: both BERT-ish models in this box's HF cache
export only `input_ids`/`attention_mask`. The gap is unambiguous from the code and the contract.)

**Fix.** Have `resolve_ner_model` (or `run_provider_benchmark`) carry `needs_token_type_ids` and thread
it into `run_once`, exactly as `run_and_decode` does. Failing that, detect the model's required inputs
from the session and emit a named error instead of a raw ORT failure.

**Test.** A unit test over the input-set decision — `NER_TOKEN_TYPE_IDS=1` ⇒ the benchmark's input set

<a id="m9-r11"></a>
### M9-R11 — the CPU fallback is **initialization-only**; a mid-life EP failure degrades silently and never re-arms (docs)

**Mechanism.** `build_session` runs once per session at load. After that, an EP failure surfaces as a
`session.run` error (`onnx.rs:600-613`) and takes the ordinary inference-error path: under the default
posture `FailOpen` swallows it and the request proceeds **structured-only**; under `NER_REQUIRED` it
400s. There is no re-initialization on CPU — the process keeps a dead accelerator for its lifetime.

**Why M9 makes this worth writing down.** The posture itself is pre-existing and deliberate (M2-R1/R2),
and is *not* a leak — the structured layer still runs. What M9 changes is the **probability**: a GPU
device-removed / TDR event on Windows is a routine occurrence in a way that "CPU inference stopped
working" is not. So the docs' framing now promises more than the code delivers:

- `SETUP.md`: *"The accelerator **falls back to CPU** (with a warning) if it can't initialize, so this
  is **always safe to try**."*
- `ARCHITECTURE.md:698-702` frames fallback as the general safety property of the EP layer.

Both describe **startup**. Post-startup, the default posture yields *silent* NER degradation across
every subsequent request (a `FailOpen` swallow, no per-request warning), and `NER_REQUIRED` yields a
hard outage — neither of which "always safe to try" prepares an operator for.

**Fix (docs).** State the boundary next to the fallback claim: the fallback covers **initialization**;
a provider that dies later is not re-initialized, and the consequence follows the `NER_REQUIRED`
posture (silent structured-only, or 400s). One sentence, next to the existing
*initialization-not-numerical-correctness* note, which already establishes exactly this "the fallback's
scope is narrower than it looks" framing.

**Test.** None practical. If it were ever worth code rather than prose, the shape would be a
health-check that re-builds the pool on CPU after N consecutive inference failures — deliberately
**not** proposed here: it adds a failure-recovery state machine to a proxy whose current behavior is
already fail-safe, which the lean bar doesn't justify for a non-default opt-in.

**CLOSED (builder, 2026-07-20), as documentation.** The boundary is stated where the claim is made.
ARCHITECTURE now lists mid-life failure as the third thing the fallback does not catch — no re-initialization,
the process keeps a dead accelerator, and the consequence follows the `NER_REQUIRED` posture — and notes that
M9 raises its probability (a TDR/device-removed event is routine in a way "the CPU stopped working" is not).
SETUP's *"always safe to try"* is now scoped to **initialization** ("trying it cannot stop the proxy from
starting") with the later-death case spelled out. `build_session_reporting`'s rustdoc carries the same bound.
The health-check/re-arm state machine the reviewer explicitly did not propose remains not built.

### M9-R13 — the three per-target wirings are presented as equivalent, but only Linux/CUDA changes the downloaded ONNX Runtime — and it does **not** apply to `aarch64-unknown-linux-gnu`, a shipped release target (correctness / docs)

**`Cargo.toml:93-95` states the design rule:**

> Every release target uses a PREBUILT ONNX Runtime (`download-binaries`); none builds it from
> source, **so this is a choice of which prebuilt to fetch**, not a toolchain burden.

**Read against `ort-sys`, that is true of exactly one of the three.** From the pinned
`ort-sys-2.0.0-rc.12`, `build/download/resolve.rs`, `resolve_dist()` builds the distribution key
from `training`, `webgpu`, `cuda|tensorrt`, `nvrtx`, `rocm` — **and nothing else**:

- `directml` is **not** a key → Windows fetches the same `x86_64-pc-windows-msvc` / `aarch64-pc-windows-msvc`
  tarball it always did. And `build/static_link/mod.rs` links `dxguid`/`DXCORE`/`DXGI`/`D3D12`/`DirectML`
  on **every** Windows target unconditionally, commented *"pyke libs always ship compiled with
  DirectML on Windows"*. **The Windows wiring — both arches — is a no-op on the artifact.**
- `coreml` is **not** a key → macOS fetches the same `aarch64-apple-darwin` tarball. **Also a no-op
  on the artifact.**
- `cuda` **is** a key → on Linux the key becomes `cu12` (no `CUDA_VERSION`, no `CUDA_HOME`, no
  `nvcc` on a CI runner ⇒ the `cu12` default), so `x86_64-unknown-linux-gnu` now downloads
  **`…/x86_64-unknown-linux-gnu+cu12.tar.lzma2`** instead of `…/x86_64-unknown-linux-gnu.tar.lzma2`.
  A different, substantially larger prebuilt, statically linked, **on every Linux build — CI,
  release, and every developer's `--features onnx`, NVIDIA hardware or not.**

**And the failure scenario the docs miss entirely.** `build/download/dist.txt` has exactly one row
for arm64 Linux: `none  aarch64-unknown-linux-gnu`. There is **no `cu12` row**. So for
`aarch64-unknown-linux-gnu` — a target `release-build.yml` ships —`resolve_dist` finds nothing,
logs `no prebuilt binaries available on this platform for combination of features 'cu12'`, and
**silently falls back to the `none` distribution**. The build succeeds; the accelerator is simply
absent. `ARCHITECTURE.md:775` says:

| `cuda` | **automatic** on Linux (per-target) | … | ⚠️ **wired, unverified** |

which is false for half of the Linux targets this project releases. An arm64-Linux operator reading
that table sets `NER_EXECUTION_PROVIDER=cuda`, gets a `warn!` and CPU, and the docs gave them no
reason to expect it.

**Why this is worth an id rather than a footnote.** The builder's own framing was *"judge whether
wiring macOS/Linux/win-arm64 blind is defensible"*. The answer is **yes for Windows and macOS —
verifiably, from the crate source, not from a CI run** (they cannot break a build because they
cannot change one) **and qualified for Linux**: it builds on both arches, but it swaps the artifact
on one and does nothing on the other. Presenting all three under one "choice of which prebuilt to
fetch" sentence hides the only case where the sentence is load-bearing. A green CI run will *not*
surface this — both Linux legs compile.

**Fix (docs; the wiring itself is fine to keep).**

1. `Cargo.toml`, at the Linux block: say that `cuda` is one of the few EP features `ort-sys` keys
   the *distribution* on, so this line changes which tarball every Linux build fetches — unlike the
   Windows and macOS lines, which change only which `register()` compiles.
2. `ARCHITECTURE.md:775` — scope the row: `cuda` is automatic on **x86_64** Linux; on
   `aarch64-unknown-linux-gnu` there is no CUDA prebuilt, so `ort-sys` falls back to the plain
   distribution and the provider is absent.
3. State the general rule next to the per-target table, because it governs every future wiring:
   **adding an EP feature per-target is free only when `ort-sys` does not key its distribution on
   it.** Check `resolve_dist` before wiring a new one.
4. Unverified and worth naming as such rather than asserting: `Cargo.toml:104-105` claims the CUDA
   runtime "is loaded dynamically, so a box without it simply falls back to CPU". Plausible — ORT's
   provider bridge is `dlopen`'d — but untested here, and `release-build.yml` packages a **single
   file** (`target/<triple>/release/<bin>`) while `ort`'s `copy-dylibs` places sidecar `.so`s next to
   the *build* output. Whether `NER_EXECUTION_PROVIDER=cuda` works from the **packaged artifact** is
   open. Either verify it on the manual CI run or say it is unverified.

**Test.** No unit test reaches a build script. The honest guard is the manual-build run the builder
already has going — but it must check more than "it compiled": for `x86_64-unknown-linux-gnu`,

warning in the build log and **no** `cuda` row. `--bench-providers` on each release artifact is the
cheapest possible end-to-end check and it already exists.

### M9-R15 — the provider table offers `ep-rocm` / `ep-openvino` as escape hatches, but `download-binaries` has no distribution for either — "wired, unverified" reads as "might work", and they cannot (docs)

| `rocm` | `ep-rocm` | Linux, AMD | ⚠️ **wired, unverified** |
| `openvino` | `ep-openvino` | Linux/Windows, Intel | ⚠️ **wired, unverified** |

**They are not reachable in the shipped build configuration.** `ort-sys`'s `build/download/dist.txt`

distribution key at all, so it resolves to the plain build, which does not contain the OpenVINO EP.

requested, and for `rocm` there is none to request.

strictly fewer providers than plain `--features onnx`. The per-target design makes the `ep-*`
features non-subtractive, and nothing says so.

mark `rocm` and `openvino` **"no prebuilt — needs a self-built / system ONNX Runtime"** rather than
"wired, unverified", and note next to the `ep-*` list that those features change which ORT
distribution is requested, they do not add a backend to the one already linked — with the Linux
`ep-rocm` regression stated explicitly. `tensorrt` can stay "wired, unverified": it shares the
`cu12` key with CUDA, so a distribution for it plausibly exists.

**Test.** None — prose; the fact lives in a pinned dependency's build script. Pin the *pin* instead:
note that this reading is against `ort =2.0.0-rc.12`'s `dist.txt`, so an `ort` bump re-opens it.
That is the same discipline `MIN_DRIFT_HEADROOM_TOKENS` uses for a tokenizer swap.

**CLOSED (builder, 2026-07-20).** The table no longer overstates either. `rocm` and `openvino` moved from

**The builder asked me to re-check the `Cargo.toml` block's facts against `ort-sys`. Three of the four
hold exactly (see the round-4 header). This is the fourth**, and it predates this round — it comes from
the DEVLOG experiment, and every later document inherited it.

**What is asserted**, in five places: `Cargo.toml:86` (*"`ep-webgpu` doesn't even link — no

**seven-feature** build; `ep-webgpu` was never built on its own.

**Why that does not generalize — from `ort-sys-2.0.0-rc.12`'s own source.** `resolve_dist`
(`build/download/resolve.rs:22-84`) pushes keys in order `training` → `webgpu` → `cuda|tensorrt` →

```rust
if cfg!(feature = "webgpu") && !target_triple.contains("wasm32") {
    // Dawn cannot be linked statically yet so it's shipped as a dylib we need to link to.
    println!("cargo:rustc-link-lib=webgpu_dawn");
}
```

Feature says "link Dawn", distribution is the one that has no Dawn in it → `LNK1181`. The failure is
fully explained, and it is explained by **the combination**, not by `ep-webgpu`.

**`ep-webgpu` alone resolves differently.** `directml` is not a distribution key, so on a Windows build
with only `ep-webgpu` the key is plain **`wgpu`** — and `dist.txt` line 5 is exactly that row:

```
wgpu	x86_64-pc-windows-msvc	https://cdn.pyke.io/0/pyke:ort-rs/ms@1.24.2/x86_64-pc-windows-msvc+wgpu.tar.lzma2
```

A WebGPU-enabled distribution for this project's own release triple. I have **not** built it — that
would be a ~7-minute rebuild plus a download, and the point of the finding is not that WebGPU works.
The point is that the docs state as an established fact ("does not link", ❌) something the evidence
does not establish, and `dist.txt` points the other way.

**Why it is worth an id rather than a footnote.** `ARCHITECTURE.md:783` groups `webgpu` in the ❌ tier
with `rocm` and `openvino`, and [M9-R15](#m9-r15) is precise about why *those* two are hopeless: no row
in `dist.txt`, and not a distribution key, respectively. `webgpu` is neither of those things — it has a
key *and* a row — so it is in the ❌ tier for a reason that does not apply to it, sitting beside two
entries whose reasons are airtight. That is [M9-R7](#m9-r7)'s rule ("a symbol must not promise more than
the prose can back") inverted: here the symbol *denies* more than the prose can back, which costs a
future builder the one escape hatch on this platform that might actually function.

forty lines from a conclusion it contradicts.

**Fix (docs only; do not wire `ep-webgpu`).** Scope the claim to what was measured, and let the rule
carry the rest: *"Measured: **all seven `ep-*` features at once** fail to link on Windows

empirical check, if anyone wants the answer rather than the caveat, is a single

**Generalizable lesson, worth promoting to `ARCHITECTURE.md` next to THE RULE once this closes:**

properties of the individual features.

**CLOSED (builder, 2026-07-20) — the claim was false and is now retracted, not softened.** Re-derived

**The generalizable lesson is promoted next to THE RULE in ARCHITECTURE, which is where it belongs:** *a
result measured with several `ep-*` features enabled says nothing about any one of them*, because

### M9-R28 — `capture_debug_logs` is racy under the multi-threaded test runner: the buffer can come back **empty**, which fails FC-08's canary test loudly and passes its sibling **vacuously** (test-integrity, pre-existing)

**Not an M9 defect and not a leak** — it predates this milestone (the helper arrived with M7-R21's canary) and
it has no runtime analogue. `src/main.rs:25` installs exactly one process-global subscriber at startup and
never swaps it; nothing on the request path calls `with_default`. I confirmed the runtime side is unaffected in
this round's live `RUST_LOG=debug` run. This is about the **guard**, not the product.

**Repro (mine, reproducible on demand).** Against the default lib test binary:

| Run | Result |
|---|---|
| Full lib suite, 16 threads, under 8-way CPU load | **2 failures in the first 25 runs** (iterations 8 and 24) |
| The 4 `conver*` tests, 4 threads, under load | **168 failures / 1500 runs — 11.2%** |
| The 4 `conver*` tests, 2 threads, unloaded | 0 / 400 |
| **`converging_mask_emits…` ALONE, 16 threads, 1500 runs** | **0 / 1500** |

That last row is the discriminator: the canary test **cannot fail on its own**. The race needs a *second*
concurrent `capture_debug_logs`, and there are exactly two callers
(`src/pii/anonymizer.rs:693` and `:715`) — the two FC-08 tests, which the runner schedules together.

**The symptom, exactly.** The failure is `src/pii/anonymizer.rs:700` — the *positive* assertion — and the
panic message prints the captured buffer, which is **completely empty**:

```
thread '…converging_mask_emits_the_value_free_suppression_canary' panicked at src\pii\anonymizer.rs:700:9:
the converging path must emit the suppression canary; logs:

```

Not partial, not interleaved — nothing was captured at all, while the masking logic itself ran correctly
(`assert_eq!(masked, "mail [EMAIL_1]")` at line 698 passed first).

**Mechanism.** `capture_debug_logs` (`src/pii/anonymizer.rs:399-431`) installs a **thread-local** subscriber
via `tracing::subscriber::with_default`, but `tracing`'s level/interest filtering is mediated by
**process-global** state (the max-level atomic behind `LevelFilter::current()`, and the callsite interest
cache), which `tracing-core` recomputes whenever *any* thread installs or drops a default dispatcher. When one
FC-08 test's `DefaultGuard` drops, that recompute happens on a thread which now has no subscriber — so the
global gate closes, and the other test's in-flight `debug!` is short-circuited **before** it ever reaches its
own thread-local subscriber. Hence an empty buffer. *(The global-state interaction is inference from
`tracing`'s documented architecture; the empty buffer and the exclusive dependence on a concurrent sibling are
measured facts from the table above.)*

**Why this is worth an id rather than a shrug — the flake is the least of it.**

1. **`a_clean_convergence_stays_silent` (`anonymizer.rs:710-725`) is vacuous under this condition, and
   *unconditionally* vacuous with respect to it.** It asserts **only absence** —
   `!logs.contains("placeholder_tags_suppressed")` — so an empty buffer satisfies it. Worse, its *correct*
   outcome is also a near-empty buffer, so it has **no way, ever, to distinguish "correctly silent" from
   "capture broken"**. In the very run I captured above, it reported `ok` while its sibling proved the capture
   was dead. A guard that cannot fail when its instrument is disconnected is not measuring anything.
2. **The canary test's own value-free assertion is absence-only too** (`!logs.contains("bob@test.com")`,
   lines 704-707) — but it is **protected**, because the positive assertion at line 700 runs first and fails
   loudly. That is exactly the right shape, it is why anyone found out at all, and it is the shape the sibling
   lacks. This is the M4-R13/M4-R24 non-vacuity lesson that BENCH-01 already applies by name; FC-08 predates
   its application here.
3. **It sits on the "never log raw PII" guard family.** Nothing is leaking today. But an absence-only
   assertion over a buffer that can be silently empty is the exact shape of a privacy guard that stops
   guarding without saying so, and this project's bar is that `cargo test` is green *and means something*.

**Fix (builder's call, two parts — the second is the one that carries).**

1. **Serialize the capture.** A `static CAPTURE_LOCK: Mutex<()>` in the test module, held for the duration of
   each `capture_debug_logs` call, removes the overlap that drives the global recompute. Cheapest correct fix;
   makes the suite deterministically green.
2. **Give `a_clean_convergence_stays_silent` a non-vacuity assertion**, so an empty capture fails instead of
   passing — e.g. have the closure also emit a known positive control line (or run a second, deliberately
   canary-triggering mask) and assert *that* is present, then assert the canary is absent. Without this, part 1
   makes the flake go away while leaving the guard unable to notice if it ever comes back.

Also correct the helper's rustdoc at `anonymizer.rs:399-401`: *"a **scoped** subscriber … so it **never
fights** the process-global one"* is true only of the *other binary's* subscriber (`tests/log_safety.rs`,
separate process). It does not hold against the scoped subscribers this same module installs on sibling
threads, and that sentence is precisely what makes the race look impossible on a read.

**Test.** The non-vacuity assertion in part 2 *is* the test. Mechanically: after fixing, run
`<lib-test-exe> --test-threads=4 conver` ~1500× and require 0 failures — the loop that produced 11.2% above.

**Scope call (the builder asked explicitly).** It deserves an id, it is **out of M9's scope** as a
deliverable, and it should not have been dropped silently. Recording it under M9's sequence is a numbering
convenience, not an attribution. It does not gate M9's *scope*; it does gate the project's own
"`cargo test` must be green" bar, which is why the recommendation is to close it before cutting the tag
rather than after.

**CLOSED (builder, 2026-07-20) — and the first fix was wrong, which is worth recording.** Both halves,
with the measurement at each step:

1. **The capture.** My first attempt was the `Mutex` the finding suggested, serializing the two
   `capture_debug_logs` callers. **It did not work: 7 failures in 30 runs.** The interference is not between
   the two siblings — it is between the capturing thread and the other ~114 tests in the binary, because
   `tracing` caches per-callsite interest and derives it from a **process-global** max level. A callsite
   evaluated while no debug subscriber existed stays disabled, and the capturing thread gets a completely
   empty buffer. The working fix is a **process-global subscriber installed once** at DEBUG with **per-thread
   routing**: every callsite stays enabled for the binary's whole life, and each thread reads only its own
   buffer. **0/30**, then **0/10** full-suite runs (the shape that was failing ~1-in-9 under load).
2. **The vacuity, which was the dangerous half.** `a_clean_convergence_stays_silent` now emits a liveness
   probe through the same subscriber and asserts *that* before asserting the absence — so a dead capture
   fails loudly instead of passing quietly. The helper's rustdoc no longer claims the scoped subscriber
   "never fights the process-global one"; it now states the mechanism and carries the numbers, since that
   sentence is what made the race look impossible on a read.

Promoted to `TESTING.md` next to the M9-R27 lesson, in its general form: **any assert-absence test needs a
positive control**, and log capture in this crate is process-global whatever the subscriber's scope suggests.

**Scope note:** the reviewer is right that this is pre-existing and not M9's defect — M9 only surfaced it, by
running the suites back-to-back under load. It is fixed here rather than deferred because the project ties ✅
to a reliably green suite, and this was the only thing between M9 and that.
