### M6-R1 — a `document` block with a non-text source that carries text is forwarded **unmasked** · leak · **closed**

**Finding.** `mask_anthropic_block`'s `document` arm masks `source.data` **only when `source.type ==
"text"`** and silently skips every other source type. But the Anthropic Messages schema has a
**`content`** document source — `{"type":"document","source":{"type":"content","content":[{"type":"text",
"text":"…"}]}}` — whose blocks carry **plaintext PII**. That source is skipped, so its PII is forwarded to
the provider **in clear**. This is the exact Option-B failure M6's premise warns about ("a missed schema
field is a leak"), and it is reachable: the ROADMAP lists the **Anthropic SDK** as a supported native
client, and content-source documents are a normal SDK/RAG shape.

**Mechanism** (`src/pipeline/privacy.rs:448`):

```rust
Some("document") => {
    if let Some(source) = block.get_mut("source") {
        if source.get("type").and_then(Value::as_str) == Some("text") {
            if let Some(data) = source.get_mut("data") { transform_string_value(data, f); }
        }
    }
    Ok(())          // ← every non-"text" source falls through here, unmasked
}
```

The block-level dispatch is strict (unknown *block type* → `Err`, fail closed), but the **source-type**
dispatch inside the known `document` block is *fail-open*: it masks the one source it knows and skips the
rest. A text-bearing source (`content`) is thereby stranded exactly the way the design intended `document`
to *not* be stranded (the builder deliberately handled the text source "because never-leak beats the plan's
'skip document'"; the same reasoning applies to the content source).

**Repro (through the real router + a mock native upstream — reviewer's throwaway harness, verified with my
own eyes):** a request whose `content` holds two documents, one `text`-source and one `content`-source:

```
text-src leaked   (textsrc@x.com):        false   ← masked to [EMAIL_1] ✓
content-src leaked (contentsrc@y.com):    true    ← FORWARDED IN CLEAR
content-src IBAN leaked (IT60…123456):    true    ← FORWARDED IN CLEAR
```

The upstream received `…"source":{"content":[{"text":"content-src leak contentsrc@y.com and IBAN
IT60X0542811101000000123456","type":"text"}],"type":"content"}…` verbatim.

**Fix.** Dispatch the document `source.type` the way blocks dispatch on `type`:
- `text` → mask `source.data` (unchanged);
- `content` → recurse its block array (it is text/image blocks — reuse `mask_tool_result_content`, which
  already walks a text/image/bare-string array and fails closed on the rest);
- `base64` / `url` → skip (opaque binary / a fetch target that must not be rewritten — the accepted
  non-text tradeoff, same as `image`);
- **any other source type → `Err` (fail closed)**, so a new Anthropic document source is a conscious
  addition, never a silent leak — matching the block-level rule.

Also update [`ARCHITECTURE.md`](../ARCHITECTURE.md) → *Native Anthropic Messages* and the M6 ROADMAP scope,
which currently describe the document handling as "text-source → masked; image / base64 / redacted → skipped"
without the `content` case.

**Test.** A unit case in `mask_anthropic_request` (a `content`-source document with an email + IBAN in a
nested text block → both masked, upstream sees placeholders) **and** a fail-closed case (a document with an
unrecognized `source.type` → `Err`). An e2e companion in `tests/anthropic_messages_e2e.rs` asserting the
raw values are absent from the echoed upstream body. The existing
`anthropic_masks_text_source_document_but_skips_file_source` (ANT-02) covers only `text` vs `base64` — extend
it to pin `content`.

**Closed (2026-07-16, `0cdd251`+fix).** The `document` arm now calls `mask_anthropic_document`
(`src/pipeline/privacy.rs`), which masks `title` / `context` and dispatches `source.type`: `text` →
`source.data`; `content` → the nested block array via `mask_tool_result_content` (the same text/image/bare
walk); `base64` / `url` → skipped; **any other → `Err` (fail closed)**. ANT-02 renamed to
`anthropic_masks_document_text_and_content_sources_title_and_context` (covers all three text-bearing parts +
opaque base64/image), `anthropic_unknown_document_source_type_fails_closed` (ANT-09) pins the fail-closed
source, and `messages_content_source_document_is_masked_upstream` (ANT-E2E-10) reproduces the exact leak shape
through the real router and asserts the document's own text block is masked. ARCHITECTURE *Native Anthropic
Messages* and the ROADMAP M6 scope now describe the full `source.type` dispatch. *(While here, `title` /
`context` — text-bearing document metadata the first cut also skipped — are masked too.)*

### M6-R2 — `mask_anthropic_system`'s array branch fails **open** on an object it doesn't recognize · hardening · **closed**

**Finding.** The top-level `system` array walk masks a block's `text` if present, else fails closed **only
for a non-object element**; an *object* element with no `text` key is silently skipped
(`src/pipeline/privacy.rs:354`):

```rust
Value::Array(blocks) => {
    for block in blocks {
        if let Some(text) = block.get_mut("text") {
            transform_string_value(text, f);
        } else if !block.is_object() {
            return Err("`system` array has an unrecognized element".to_string());
        }
        // ← an object with no `text` falls through, unmasked and un-blocked
    }
    Ok(())
}
```

This is the **same fail-open-on-an-unknown-sub-shape class as [M6-R1](#m6-r1)**, one level up. Risk today is
low — Anthropic `system` blocks are text-only (`{type:text, text, cache_control?}`), all of which carry
`text` — so no real leak is known. But it diverges from the invariant the rest of M6 upholds ("an
unrecognized shape fails closed"), so a future non-text system block would leak silently rather than 400.

**Fix.** Fail closed on a `system` array *object* that carries no `text` (i.e. treat "object without a
recognizable text field" the same as a non-object element), or — if a deliberate skip is wanted — restrict
the skip to a known-safe marker and document it. The block-level dispatch is the model to mirror.

**Test.** Extend `anthropic_block_without_type_and_missing_messages_fail_closed` (ANT-05) with a `system`
array holding an object that has no `text` → `Err`.

**Closed (2026-07-16).** The `system` array branch now fails closed on **any** element without a `text` field
(the `else if !block.is_object()` became a plain `else { return Err(…) }`), so an unknown-shape object blocks
instead of skipping — matching the block-level rule. ANT-05 extended with a `{"type":"mystery"}` system block
→ `Err`.

### M6-R4 — e2e placeholder-presence asserts are satisfiable by the augmentation prompt text · test-quality · **closed**

**Finding.** The injected augmentation prompt **literally contains** `[EMAIL_1]`, `[PHONE_2]`, `[PERSON_1]`,
`[IBAN_1]` (as examples). Several e2e asserts read as "masking happened" but are actually satisfied by that
prompt whenever *anything* was masked (the prompt is injected iff the vault is non-empty):
- `messages_buffered_roundtrip…`: `seen.contains("[EMAIL_1]") && … && seen.contains("[IBAN_1]")` — `[EMAIL_1]`
  and `[IBAN_1]` are in the prompt; only `[PHONE_1]` is not.
- `messages_masks_system_content_blocks…`: `seen.contains("[EMAIL_1]")` with the message *"nothing masked"* —
  the prompt guarantees it once the vault is non-empty.
- `messages_streaming…`: `upstream_saw.contains("[EMAIL_1]")` *"expected placeholder upstream"* — same.

**These tests are not vacuous** — each pairs the placeholder-presence check with `!contains(raw)` absence
checks over the real PII (the roundtrip also uses `[PHONE_1]`, which is *not* in the prompt), and those
absence checks are what actually catch an unmasked field. But the placeholder-**presence** asserts are weaker
than they read: they'd pass even if the specific field they name were never masked, as long as some other
field was. (The unit test `anthropic_masks_every_text_bearing_field` is clean — it calls the walk directly,
without augmentation, so its `[EMAIL_1]` assert genuinely proves masking.)

**Fix.** For a "masking happened" signal, assert a placeholder that is **absent from the augmentation prompt**
(e.g. `[PHONE_1]`), or assert the specific field's value rather than a substring of the whole body. Leave the
`!contains(raw)` absence checks — they are the real guard.

**Test.** N/A (this *is* about the tests).

**Closed (2026-07-16).** The three presence asserts now read the **specific masked field**, not the whole
body: `messages_buffered_roundtrip…` and `messages_streaming…` extract the masked **user message** (which
excludes the `system`-borne prompt) and assert the placeholders there; `messages_masks_system_content_blocks…`
asserts `[EMAIL_6]` (six distinct emails masked — a token absent from the prompt). The `!contains(raw)`
absence checks are untouched (they were always the real guard). The new
`messages_content_source_document_is_masked_upstream` asserts on the document's own text block for the same
reason.

### M6-R5 — `inject_augmentation_anthropic` doc comment says "Prepend" but the code appends · docs · **closed**

**Finding.** `src/pipeline/privacy.rs:514` — the function doc reads *"Prepend the augmentation to the
top-level `system` field"*, but every branch **appends**: a string becomes `format!("{s}\n\n{AUG}")` (existing
text first) and an array `push`es the prompt block at the end. The "prepend" wording is a carry-over from the
OpenAI analogue, where a brand-new `system` *message* is inserted at index 0. ARCHITECTURE already describes
it correctly ("created / string-appended / block-array-pushed"); only the code comment is off.

**Fix.** Reword the comment to "Append the augmentation to … (or create it)".

**Test.** N/A (comment).

**Closed (2026-07-16).** The doc comment now reads *"Append the augmentation to the top-level `system` field
(string or text-block array), or create it"*.
