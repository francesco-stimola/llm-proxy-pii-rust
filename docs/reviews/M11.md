### The class-or-instance verdict on the priority fix

Asked whether `VAT-14` pins the class or two instances. The **ordering** is genuinely class-closing:
the only recognizers that can claim a bare `\b\d{11}\b` token are the always-on `\d{11}` national ID
and the domestic-phone `Trunk` family's third arm `\b0\d{6,11}\b` (the other three phone shape
families all require separators, so they cannot match a bare digit run), and `TaxId` = 2 sits
strictly below both `NationalId` = 4 and `Phone` = 3, so `outranks` can never let `TaxId` name that
union. Two instances are enough to pin an ordering between two kinds.

**What is not closed is the other direction, and it is the larger of the two — see
[M11-R2](#m11-r2).**

### M11-R1 — `VAT-04` asserts the absence of an ES VAT number in a form no ES recognizer could match — *guard, medium*

**The ES arm cannot fail.** `src/pii/recognizers.rs:3086`:

```rust
for text in ["ES B12345678", "FR40404833048", "LV40003032949"] {
```

The tier documents, and enforces, that there is **no space between the country prefix and the
body** (`vat_recognizers`'s own doc, *"No space between prefix and digits"*), and the VIES canonical
rendering is `ESB12345678`. So the ES negative is written in the one shape the tier's grammar can
never match — it is absent for a reason that has nothing to do with ES not shipping.

**Repro.** Added a canonical, checksum-less ES recognizer — precisely the "half-shipped" outcome
VAT-04 exists to forbid — to `vat_recognizers()`:

```rust
Recognizer {
    kind: PiiKind::TaxId,
    regex: Regex::new(r"(?-u:\b)ES[A-Z0-9]\d{7}[A-Z0-9](?-u:\b)").unwrap(),
    validate: None,
    scan: Scan::Overlapping,
    shrink_on_reject: false,
},
```

`cargo test --lib unmeasured_vat_countries_are_absent_rather_than_guessed` → **ok**. The stub was
confirmed live at the same moment: `VAT-16` reported *"the tier now ships 7 of them"*. Adding one
matching control to `ONE_PER_SHIPPED_SCHEME` — the natural way anyone would make that red go green —
left the **entire default suite at 239 passed / 0 failed**, with an unmeasured, checksum-less
Spanish VAT recognizer shipping.

**Scoped by the same mutation:** FR and LV are *not* vacuous. Stubs for both turn VAT-04 red at
`recognizers.rs:3112`. ES is the only broken arm.

**Why it matters more than a test nit.** VAT-04 is what ARCHITECTURE cites for *"the gap stays a
decision rather than a discovery"*, and ES is the one of the three whose failure mode the code
comment describes in detail (*"Shipping the person half alone would be a VAT recognizer that misses
the case it exists for"*). The guard that is supposed to catch exactly that is the one that cannot.

**Fix.** Write the ES negatives the way the tier would match them — at minimum `ESB12345678` (the
legal-entity CIF form the comment names), and ideally the two person forms `ES12345678Z` and
`ESX1234567X` alongside it. FR and LV stay as they are.

**Test that would have caught it.** The mutation itself, but the durable guard is a **reachability
assertion on the negatives**: each VAT-04 input must be a token the tier's grammar could in
principle match (no whitespace inside; a 2-letter uppercase prefix followed by 7–12 alphanumerics),
so a negative written in an unmatchable shape is red on the spot rather than quietly true. That is
the same "prove the corpus can express the thing" move PROP-04 made for M4-R17.

**Closed 2026-09-03 (builder).** Negatives rewritten to the three canonical no-space forms the tier
could actually match — `ESB12345678` (the legal-entity CIF form the recognizer's own doc names),
`ES12345678Z` (DNI + control letter) and `ESX1234567L` (NIE). FR and LV left alone, since the round
proved both arms non-vacuous.

**And the durable half, which is the point:** each input is now checked for **reachability first**,
inside the loop, against the tier's grammar — two uppercase ASCII letters then an unbroken
alphanumeric run of at least 7. A negative the grammar could never match is red on the spot, so the
next person who writes `"ES B12345678"` is told rather than silently reassured.

**Mutations, both RED (expected RED):**
- the round's own repro — a live checksum-less ES recognizer added to `vat_recognizers()` →
  **RED** at `recognizers.rs:3149`, the absence assertion. It was GREEN before this fix.
- one negative reverted to the old unmatchable `"ES B12345678"` → **RED** at `recognizers.rs:3131`,
  the reachability assertion. That is the guard on the guard, and it watches.

### M11-R2 — the priority fix closed the small collision and created the large one; `VAT-10` measures the wrong one, and the "costs no coverage" claim is false under the shipped default — *fidelity / measurement, medium*

**Not a leak.** Every byte is masked either way — this is about which token the model is handed, and
about a published number that does not measure what it is quoted for.

**The claim.** `src/pii/recognizers.rs:440-445`, on the bare P.IVA recognizer:

> `\d{11}` … **THE one shape that collides with an existing recognizer** … also the DE Steuer-ID / LV
> personal code pattern … **The collision costs no coverage;** what this recognizer *adds* is every
> P.IVA that is not also a valid Steuer-ID or LV code.

The comment names one collision. The milestone found a second one — the compact domestic phone —
and *fixed the direction of it* (`TaxId` below `Phone`, VAT-14), but the comment, `VAT-10` and
[`ARCHITECTURE.md:78-83`](../ARCHITECTURE.md) all still describe the collision as the national-ID
one.

**Measured.** A probe over 300 000 sweep points, restricted to **issuable** P.IVAs (leading `0` —
the only bare shape the phone `Trunk` arm `\b0\d{6,11}\b` can claim — and a province code in
001…110, so unissuable synthetics are excluded), asking which kind names the span:

| Detector | named `Phone` / valid 0-leading P.IVAs | `00xx` | `0[1-9]xx` |
|---|---|---|---|
| **`StructuredRecognizers::new()` — the shipped default (all 9 vetted regions on)** | **2372 / 3241 = 73.2 %** | 12/541 = 2.2 % | **2360/2700 = 87.4 %** |
| `PII_LOCALES=de` | 2104 / 3241 = 64.9 % | 11/541 | 2093/2700 = 77.5 % |
| `PII_LOCALES=it` — the feature's primary locale | 1856 / 3241 = 57.3 % | 12/541 | 1844/2700 = 68.3 % |
| `PII_LOCALES=cn` | 1057 / 3241 = 32.6 % | 11/541 | 1046/2700 = 38.7 % |
| `PII_LOCALES=gb` | 909 / 3241 = 28.0 % | 11/541 | 898/2700 = 33.3 % |
| `PII_LOCALES=nl` | 27 / 3241 = 0.8 % | | |
| `PII_LOCALES=fr` | 11 / 3241 = 0.3 % | | |

So under the configuration the product ships with, **roughly three out of four issuable 0-leading
Partita IVAs are announced to the model as `[PHONE_n]`, not `[TAXID_n]`.** Example (issuable-shaped,
not a real company): `01032501239` → `Phone` under `new()`.

**Why every existing guard is green, and this is the part worth keeping.** The split by leading pair
is decisive: `00xx` is **2.2 %**, `0[1-9]xx` is **87.4 %** — a leading `00` reads to libphonenumber
as the international access code, so those are rejected as numbers. **All five real published
P.IVAs in this repo's corpus — `00905811006`, `00159560366`, `00488410010`, `00891030272`,
`00811720580` — are `00…`-leading**, i.e. entirely inside the immune sub-shape. VAT-01, VAT-03,
VAT-05, VAT-06, VAT-14 and VAT-16's controls are all drawn from it. *A corpus has a shape, and that
shape is a blind spot* — [M4's lesson 2](M4.md#retrospective), landing again, on a corpus assembled
in the milestone that quotes it.

**And `VAT-10` cannot see it by construction.** `recognizers.rs:3219` sweeps
`format!("{:011}", 10_000_000_000 + i)` — **every value starts with `1`**, and the only phone family
that can claim a bare digit run requires a leading `0`. The guard that ROADMAP presents as *"the
number a reader needs in order to know whether the naming rule matters in practice"* measures the
0.0998 national-ID collision and is structurally incapable of measuring the ~0.73 phone one. The
published statistic understates the labelling collision by about **7×**.

**What is and is not wrong.** The *ordering* is right and its justification (an assigned-number plan
lookup is better evidence than a mod-10 check) stands. Three things are wrong:
1. the magnitude was never measured, so nobody chose it;
2. *"The collision costs no coverage"* is false under the shipped default — what the recognizer adds
   is every P.IVA that is not also a Steuer-ID, an LV code, **or an assigned domestic number in any
   of the nine vetted regions**, and that last clause removes ~73 % of the issuable 0-leading space;
3. decision 1's entire purpose — a token that distinguishes a *business* identifier from a person's
   — is not delivered for the majority of the bare form's issuable space, which is the form the
   ROADMAP calls "the primary case".

**Fix.** Extend `VAT-10` to sweep the shape the phone collision actually lives in (leading `0`,
province code 001…110) and report the rate **against `StructuredRecognizers::new()`**, not only
against the validators; correct the `recognizers.rs:440-445` comment and
[`ARCHITECTURE.md`](../ARCHITECTURE.md)'s priority bullet to state both collisions and the measured
share. Then — and this is **the maintainer's call, not the builder's**, because it changes
product-visible labelling — decide whether `TaxId` should outrank `Phone` when the phone candidate
is reachable *only* through the separator-free `\b0\d{6,11}\b` arm (the weakest evidence in the
phone tier: no grouping, no context) while keeping `Phone` ahead on every separated rendering.

**Test that would have caught it.** VAT-14 with its instances drawn from `0[1-9]…` instead of `00…`
— or, better, a rate assertion beside VAT-10 quantifying over the *default* detector, so the number
that decides the naming rule is measured against the configuration that ships.

**Closed 2026-09-03 (builder) — the measurement and the two false claims. The ordering question is
NOT closed here, because it is not the builder's to close.**

### M11-R6 — `KIND-01`'s chain forces an *arm*, not a place in the walk: a twelfth `PiiKind` still ships with the suite green — *guard, medium-low*

**M11-R3 was closed with a chokepoint claim, and the claim is false.** Three places state it:

- `src/pii/mod.rs:76-82` — *"a new variant is a compile error there, its author has to say where in the
  chain it goes, and once it is in the chain it appears here automatically"*;
- [`TESTING.md`](../TESTING.md) → KIND-01 — *"A new variant is a compile error there, **its author has to
  place it in the chain**"*;
- [M11-R3](#m11-r3)'s closure note — *"Adding a variant is a compile error there; its author must place
  it in the chain."*

The compiler demands an **arm**. It does not demand that anything **point to** the new variant, and the
walk only ever visits what the chain reaches from its hard-coded start (`src/pii/mod.rs:525`,
`let mut walked = vec![PiiKind::Email];`).

**Repro — two of the three minimal ways to satisfy `error[E0004]` leave the suite green.** A twelfth
`PiiKind::Vin` was added to the enum with **only** what the compiler refuses to build without: `label`
(`src/pii/mod.rs:114`), `priority` (`:182`), `KIND-01`'s `next` (`:526`), and `AUG-01`'s `exemplified`
(`src/pipeline/privacy.rs:990`). It was **not** added to `PiiKind::ALL` and **not** to `from_label`.

| chain arm written for `Vin` | outcome |
|---|---|
| `PiiKind::Vin => return None,` (P1) | **149 passed / 0 failed** |
| `PiiKind::Vin => PiiKind::Email,` (P1b) | **149 passed / 0 failed** |
| slotted between two existing variants | RED — this is the one M11-R3's closure tested |

`all_lists_every_variant_in_order`, `every_kind_round_trips_through_its_label` and
`the_augmentation_prompt_names_every_placeholder_kind_it_should` are **all three green** in the first two
rows. `ALL` stays at 11, so `AUG-01`'s `PiiKind::ALL.len() == 11` non-vacuity check passes too — the
guard designed to notice `ALL` shrinking cannot notice `ALL` failing to grow.

**Why it is not cosmetic, and it is the same consequence M11-R3 named.** `KIND-02` iterates
`PiiKind::ALL`, so a variant missing from `ALL` is a variant `KIND-02` never asks about — and in both
rows above `Vin` is in `label` but **not** in `from_label`. `from_label` gates
`anonymizer::is_placeholder_token` (`src/pii/anonymizer.rs:335`), which is what makes `[VIN_1]` **inert**
to the next detection pass — the mechanism `Vault::mask_all`'s fixpoint rests on (M5-R4) — and it gates
the M1.5 warning that an unresolved known-kind placeholder is logged rather than silently shipped. The
failure is fail-*closed* (a non-converging `mask_all` blocks, M4-R20) rather than a leak, so this is
availability and observability, not privacy. But it is precisely the harm the closure claimed to have
made impossible.

**Fix — and it must be *one* level, not a fourth.** Do not add a guard that watches `KIND-01`. Delete the
hand-written list instead: declare the variants **once**, in a `macro_rules!` that emits both the `enum`
and `ALL` from the same token list. Then a variant absent from `ALL` is not a test failure, it is a
variant that does not exist — and `KIND-01` and its successor chain can both be deleted, which is the
mark of a real chokepoint rather than another layer. If the macro is judged too much, the honest
alternative is to keep the chain and **correct the three claims above** to what it actually does: *the
chain proves `ALL` agrees with the chain; it does not prove either agrees with the enum.*

**Test that would have caught it.** The mutation in row 1 — the laziest edit that compiles. M11-R3's own
mutation wired `Vin` into the chain, which is the *diligent* author's edit; the guard exists for the
other one.

**Closed 2026-09-03 (builder) — by deleting the guard, which is what the finding asked for.**

The round is right that no test can close this: Rust cannot enumerate an enum's variants, so any
guard is reduced to checking a *list against a list*, and the compiler can only be made to demand
an **arm**. `Vin => return None` is a legal arm. So the chain is gone and the question is removed
instead of watched.

**`pii_kinds!` generates the enum, `PiiKind::ALL`, `label` and `from_label` from one list.** Adding
a kind is one line and all four move together; declaring a variant outside that list is a *parse
error*. Deliberately **not** generated: `priority` and `is_structured` — those are judgements about
a new kind rather than restatements of it, and the compiler already stops you at their exhaustive
`match`, which is the right place to be stopped. One level, as the finding prescribed: the chain
was deleted rather than joined by a second guard.

**Four mutations, every remaining route, all RED:**

| # | Route | Result |
|---|---|---|
| R6a | 12th kind added to the macro list | **RED** — `error[E0004]` at `priority`/`is_structured`. The list can grow; the judgement cannot be skipped. |
| R6b | variant declared **without** a label — *this round's P1 route* | **RED** — `error: no rules expected` \`,\`. The route that beat the chain is now a parse error. |
| R6c | two kinds share a label | **RED** — `KIND-02`, plus two callers |
| R6d | a label that is not uppercase (unreachable after `to_ascii_uppercase`) | **RED** — `KIND-02`, plus three callers |

guard is driven from, and the priority judgement was actually made rather than defaulted.

### M11-R10 — a lower- or mixed-case IBAN or VAT number is forwarded **in clear**: the structured tier's case axis was never decided — *leak, high*

**Reproduced through the real binary, not read off the regexes.** With the proxy pointed at a
recording mock upstream, these reach the provider **unmasked**, byte for byte:

| rendering | value | what the provider receives |
|---|---|---|
| lowercase VIES prefix | `it00905811006`, `de136695976`, `gb220430231`, `pt524287244`, `nl111222333b01` | raw |
| mixed-case prefix | `It00905811006`, `Gb220430231` | raw |
| uppercase prefix, lowercase internal `B` | `NL111222333b01` | raw |
| lowercase IBAN | `it60x0542811101000000123456`, `de89370400440532013000` | raw |
| **one** lowercase letter in an otherwise uppercase IBAN | `IT60x0542811101000000123456` | raw |
| space-grouped lowercase IBAN | `it60 x054 2811 1010 0000 0123 456` | raw |

Every value above is one this repo already treats as a positive in its own corpus; only the letter
case changes. The uppercase renderings of all of them mask correctly.

**Mechanism.** `src/pii/recognizers.rs:465-521` (the six VAT patterns) and `:238` (IBAN) spell
their letters as uppercase-only character classes — `IT`, `DE`, `GB`, `PT`, `NL…B`, and
`[A-Z]{2}\d{2}[A-Z0-9]{11,30}`. Lowercasing any of them does not merely lose the *prefix*: the
letters are ASCII word characters, so there is no `(?-u:\b)` between them and the digits for the
bare `\d{11}` recognizer (or the always-on 9-digit national-ID recognizer) to fall back on. The
span is not shortened, it **disappears**.

**This is an axis, not an instance, and the tier is inconsistent along it.** Driven in the same
run: the Codice Fiscale (`[A-Za-z]{6}…`), ES DNI/NIE (`[XYZxyz]…[A-Za-z]`) and Chinese resident-id
(`\d{17}[0-9Xx]`) recognizers all fold case and mask either way. Two families do not, and one of
them is from **M1**: this half of the finding predates M11 by ten milestones and has survived
every review this repo has run. `iban_mod97`'s own doc comment says *"letters are folded to
uppercase"* — the **validator** was written for input the **regex** can never deliver, which is
the clearest evidence available that nobody chose this.

**The published reason for the VAT half does not survive the tier's own grammar.**
`recognizers.rs:411-417` and `TESTING.md` → `VAT-05` both argue:

> Lowercase would make `it` a matchable prefix — and `it` is one of the commonest words in English
> prose. `"call it 12345678901"` with a mod-10-valid tail would then produce a **14-character**
> span swallowing an ordinary English word.

The very next section of that same doc comment says there is **no space between prefix and
digits**. `it 12345678901` therefore cannot match under *any* case rule, and the mutation confirms
it: making the `IT` pattern case-insensitive turns exactly **one** assertion red in 149 lib tests —
`kinds("it00905811006").is_empty()`, the one that pins the miss. `kinds("call it 00905811006
back")`, the assertion the rationale is attached to, stays **green**. And the `NL…B…` separator's
case is covered by no argument at all and pinned by no test: changing `B` to `[Bb]` leaves the
suite at **246 / 0 / 5**.

**Measured, because the two halves do not resolve the same way** — 341.1 MB / 16 380 files of
uncurated third-party source, the same stand-in Round 1 used:

- **VAT: folding case costs 0.** All five prefixed schemes fire **0** times uppercase and **0**
  times case-insensitively. Each is checksum-gated besides (NL is fourteen fixed positions with
  three literal anchors), so the marginal false-positive cost is zero on this corpus and bounded
  by a checksum everywhere else.
- **IBAN: folding case costs a lot, and the rule is load-bearing.** The continuous arm goes from
  **2** hits to **933** — hex digests, base64 blobs, `Ed25519PublicKey` — and IBAN has **no hard
  checksum gate** (mod-97 is a confidence signal, M4), so all 931 extra would be masked. Masking a
  hex digest inside a `tool_use.input` is exactly the harm M10 spent nine rounds bounding.
- **But the cheap gate closes it anyway: 0 of the 931 survive mod-97 + the ISO 13616 length.**
  (Only 26 of them even carry a country code the length table knows.)

**Fix — one decision at the recognizer table, not five patches.** The axis is *"for each
letter-bearing pattern, does letter case matter, and what does the answer cost?"*, and it should be
answered once, per pattern, with the number beside it:
1. **VAT (five schemes + the NL `B`): fold case.** Measured cost 0; closes seven of the thirteen
   renderings above. Replace the refuted rationale in `recognizers.rs` and `VAT-05` with the
   measurement, and keep `VAT-05` — but as a guard on the *span boundary* (`"call it <digits>"`
   must still yield the digits alone), which is the real property it protects and the only one its
   first assertion actually tests.
2. **IBAN: fold case, and require a non-canonical-case rendering to be `Verified`** (mod-97 **and**
   `iban_country_length`) rather than `Structural`. Measured residue **0/931**, and the uppercase
   path keeps M4's deliberate "a structurally valid IBAN is masked even when mod-97 fails" rule
   untouched.
3. **`Secret`'s `AKIA…` stays uppercase-only** — that one is a format, not a convention.

Both are **product-visible coverage changes**, so per `CLAUDE.md` the decision is the maintainer's,
not the builder's; the numbers to decide on are above. Doing nothing is a legitimate third option —
but then it has to be *written down as a decided limit with these numbers*, because today the docs
assert a reason that the code refutes.

**Test that would have caught it, and it is one test, not seven.** A **case matrix over the
recognizer table**: for every recognizer whose pattern contains a letter, assert that a known
positive in `to_lowercase()`, in `to_uppercase()` and with one letter case-flipped either **all
mask** or **all miss**, and that the answer for each pattern is the one recorded in a table beside
it. A new letter-bearing recognizer then cannot ship without an answer, which is what
`shipped_tax_recognizer_count` does for the count and what the `pii_kinds!` macro does for the
enum. The instance-shaped version — adding `it00905811006` to a corpus — would close IT and leave
DE, GB, PT, NL and IBAN open, which is the move [M4's retrospective](M4.md#retrospective) is six
rounds of warning against.

**Closed 2026-09-03 — maintainer's decision: option 1, both halves.** Put to the maintainer with
both costs re-measured independently of this round (same 341.1 MB / 16 380 files; distinct values
rather than occurrences, hence 149 where the round counted 933 hits). **The leak was reproduced
first**: `it00905811006`, `IT60x0542811101000000123456` and the rest yield *no detection at all*,
while `RSSMRA85T10A562S`/`rssmra85t10a562s` and `12345678Z`/`12345678z` both mask — the
inconsistency is exactly as reported.

- **VAT: folded.** All five prefixed schemes plus the NL literal `B` now spell their letters as
  explicit ASCII classes (`[Ii][Tt]`, `[Nn][Ll]…[Bb]`) rather than `(?i)`, so no Unicode case
  folding can widen them. Re-measured cost: **0 added matches** for every scheme.
- **IBAN: folded, with `iban_case_gate`.** Canonical uppercase keeps M4's rule untouched
  (structurally valid is masked even when mod-97 fails); a rendering carrying **any** lowercase
  letter must be fully verifiable. **One correction to the round's arithmetic, in the safe
  direction:** `iban_length_ok` returns `true` for an unknown country code, so for 145 of the 149
  the gate is mod-97 *alone* — weaker than the round modelled. Re-measured under that weaker
  reading: still **0 survivors**.
- `confidence_of`'s NL arm folded too, or a lowercase btw-id would have been mis-tagged.

**`VAT-05` was rewritten rather than deleted.** Its rationale was refuted, but the property under
its first assertion is real and independent of the case rule — a VAT number after an English word
must still yield the digits alone. It now guards that, in both cases, plus the leak itself.

**`CASE-01` and `CASE-02` are the chokepoint**, per the finding's own prescription: one matrix over
the recognizer table asking each letter-bearing pattern the same question, including the
single-letter-flipped rendering that a lowercase corpus would miss. `CASE-02` pins both halves of
the IBAN split, since getting either wrong is silent.

**Verified:** 248/0/5, fmt and both clippy legs clean. `CAT-01` caught the two new ids as
uncatalogued before they were written up — the guard working on its own author.

### M11-R11 — `CASE-01` is a hand-written list wearing a chokepoint's doc comment: four letter-bearing recognizers have no answer, and NINO can be made uppercase-only with the suite green — *guard, high*

**The guard's own doc comment states the property it does not have.** `src/pii/recognizers.rs:3284`
promises, in two places:

> every letter-bearing recognizer has a recorded answer on the case axis
>
> A new letter-bearing recognizer cannot ship without an entry here, and an entry cannot be added

> `pii_kinds!` for the enum.

Neither move is made. `shipped_tax_recognizer_count` **counts `vat_recognizers()`**, the live set;
`pii_kinds!` **generates** the enum. `MATRIX` is a nine-line `const` that derives nothing from the
recognizer registry, so the set it quantifies over is "the values someone typed", not "the
recognizers this build ships". It is exactly the instance-shaped fix
[M4's retrospective](M4.md#retrospective) warns about, wearing the vocabulary of the chokepoint
that finding asked for — which is how it passed review inside its own closure.

**Derived from the registry rather than counted by eye, this build ships 12 letter-bearing

**Second half — the guard cannot express the answer M11-R10's own decision 3 gave.** The doc
comment closes with:

> **`MUST_MATCH` is not decoration: `Some(kind)` means the lowercase form must be detected *as that
> kind*.**

There is no `MUST_MATCH` and no `Option` in this file: the const is `MATRIX: &[(&str, PiiKind)]`,
and every row asserts *folds*. The paragraph describes a shape that would have carried a
"deliberately does not fold" answer — and that answer is precisely M11-R10's **decision 3**,
*"`Secret`'s `AKIA…` stays uppercase-only — that one is a format, not a convention"*. The decision
is recorded in the review record and is unrepresentable in the matrix that exists to record it,
which is why `Secret` is one of the four missing rows rather than a row saying *no*.

**Fix — the chokepoint, and adding four rows is not it.** Nine hand-written rows becoming thirteen
is the same defect with a different number. `StructuredRecognizers` already holds an enumerable
`Vec<Recognizer>` and every `Recognizer` carries its compiled `Regex`, so the pattern is
interrogable: **derive** the letter-bearing set from the shipped registry, and require every member
to carry a declared answer — one that can also say *does not fold, on purpose*, or `Secret` does not
fit. A new letter-bearing recognizer must then turn the guard red until someone writes its answer
down.

**And it needs two proofs, not one.** The matrix proves the answers are **right**; a synthetic
recognizer injected into the registry proves the guard is **reached**. The second is the one that
gets skipped — and skipping it is how a nine-row const came to be described as a chokepoint.

**Closed 2026-09-04 — the set is derived, and the answer table only says what the answer is.**

`StructuredRecognizers::shipped_patterns()` exposes every recognizer the scan is actually built
from as `(kind, pattern)`; `pattern_can_match_a_letter` decides which of them carry letters by
parsing the pattern to the same HIR `regex` compiles and asking each literal and character class
whether it covers `A-Za-z`. **A textual scan cannot answer this** — a word boundary and a digit
class are both spelled with letters that match none, so every pattern in the file "contains a
letter" and none of that is the question. The parse costs a test-only `regex-syntax`
dev-dependency, which is the crate `regex` itself already pulls: no new crate, no build script, no
native code, and `tests/dependency_footprint.rs` asserts the **default** tree, which
dev-dependencies do not enter.

`audit_case_axis(shipped, answers)` is the pure decision, and it reports **three** disagreements,
not two:

- `unanswered` — a letter-bearing recognizer this build ships that no answer covers;
- `stale` — an answer naming a `(kind, pattern)` no longer shipped, so a deleted recognizer cannot
  leave its answer behind asserting a closed question;
- `not_letter_bearing` — **the field that stops the guard passing vacuously.** An empty
  `unanswered` list is exactly what a derivation answering *no* to everything would also produce.
  Requiring every recorded answer to be about a pattern the derivation *does* call letter-bearing
  turns the two into an equality — the letter-bearing recognizers this build ships are precisely
  the ones the answers name — **with no count for anyone to keep current**. That is deliberately
  not the shape `CAT-01`'s floor had (M11-R4 / M11-R7): a number somebody has to re-measure is a
  number that goes stale, and this one derives itself.

**`CaseRule` is an enum because decision 3 is an answer.** `Folds` asserts the lowercase, uppercase
and one-letter-flipped renderings are all detected as the same kind. `Fixed { variant, why }`
asserts the canonical rendering *is* detected and a **named** case rendering of the same characters
is **not** — with `variant.eq_ignore_ascii_case(positive)` checked, so the row cannot cheat by
naming an unrelated undetectable string. That is what makes M11-R10's decision 3 — `Secret`'s
`sk-` and `AKIA` are formats, not conventions — expressible in the matrix that exists to record it.
`Secret`'s positive is `sk-AbCdEf123456`, mixed-case **on purpose**: the prefix is case-fixed but
the key body is opaque, and an all-lowercase positive would have left the body unpinned — which was
one of the four green mutations below.

**The answer table holds each pattern verbatim rather than sharing a constant with the recognizer.**
That is the forcing function: editing a letter-bearing pattern invalidates its recorded answer and
the guard demands the answer be re-decided, printing the new pattern in the failure. A shared
constant would let the key follow the edit silently and leave only the behavioural assertion.

**Answers now recorded: 14 rows over 12 letter-bearing recognizers** (IBAN and `Secret` carry two
each — two countries, two formats). The four M11-R11 named — `Secret`, `Email`, the GB NINO, the CN
resident id — are among them, and the count is not asserted anywhere: the equality above is.

### M11-R13 — the case gate turned a benign over-match into a dropped span: a real IBAN reaches the provider **in clear** — *leak, high*

**Reproduced through the real `.exe` against a recording mock upstream, in a sentence nobody had to
construct:**

```text
client sends : Please wire the deposit to ES91 2100 0418 4502 0005 1332 for the invoice we discussed.
provider gets: Please wire the deposit to ES91 2100 [PHONE_1] 1332 for the invoice we discussed.
```

Twelve of the IBAN's twenty-four characters — the country code, both **check digits** and the final
group — are forwarded verbatim, and the middle is announced to the model under the wrong kind. The
Italian equivalent behaves identically (`Il mio IBAN e' ES91 2100 [PHONE_1] 1332 e il conto…`).

**Mechanism — three lines of `src/pii/recognizers.rs` that were never all true at once before M11.**

1. `:238` — the grouped arm is `(?: [A-Za-z0-9]{4}){2,7}(?: [A-Za-z0-9]{1,4})?`, greedy. When an
   IBAN's grouped rendering **ends on a full four-character group** the optional `{1,4}` tail is
   still free, so the match runs on into the next token: `ES91 2100 0418 4502 0005 1332 for`.
2. `:242` — `validate: Some(free(iban_case_gate))`, **added by M11-R10**. The over-long span contains
   a lowercase byte (here from the swallowed word `for`; in a lowercase rendering, from the IBAN
   itself), so the gate demands mod-97 **and** the ISO 13616 length. The over-long string fails both.
   **Rejected.**
3. `:244` — `shrink_on_reject: false`, so `shrink_to_a_valid_prefix` returns `None` on the spot. And
   `Scan::Overlapping` resumes one `char` past the match's *start*, where there is no ASCII word
   boundary at which `[A-Za-z]{2}\d{2}` can begin again — the next viable start is past the IBAN.

So **no IBAN candidate is produced at all.** What reaches the resolver is whatever another recognizer
happened to grab of the digits — the ES `Groups` phone family here, Luhn elsewhere — and everything
outside it goes upstream raw. This is M10-R1's shape exactly, on the recognizer that never received
M10-R1's fix: *the fixpoint recovers a value it did not touch; it can never recover one the mask ate.*

**It is a regression, and the proof is a build rather than an argument.** With `iban_case_gate`
replaced by `true` — precisely the pre-M11-R10 posture, `validate: None` — the same binary, the same
matrix:

| build | leaking rows / 40 |
|---|---|
| HEAD | **6** |
| `iban_case_gate` neutralised (pre-M11-R10 behaviour) | **0** |

Before the fix the over-long match was *accepted*, so the union covered the IBAN and merely swallowed
the next word: an over-mask, which is the direction this project errs in on purpose. **The fix turned
the same over-match into a leak.**

**The matrix, five countries × two cases × four trailing contexts, through the binary.**

| IBAN | length | + lowercase word | + `2026` | + a 6-letter word | alone |
|---|---|---|---|---|---|
| `ES91 2100 0418 4502 0005 1332` **uppercase** | 24 | **LEAK** | ok (span all-uppercase → gate passes → over-mask) | ok | ok |
| same, lowercase | 24 | **LEAK** | **LEAK** | ok | ok |
| `BE68 5390 0754 7034` uppercase | 16 | **LEAK** | ok | ok | ok |
| same, lowercase | 16 | **LEAK** | **LEAK** | ok | ok |
| `PL61 1090 1014 0000 0712 1981 2874` | 28 | partial — `PL61` in clear, the rest taken by `[CARD_1]` | ok | ok | ok |
| `AT61 1904 3002 3457 3201` | 20 | partial — `AT61` in clear (`Konto AT61 [CARD_1] bei der Bank`) | — | — | ok |
| `DE89 3704 0044 0532 0130 00` | 22 | ok | ok | ok | ok |
| `IT60 X054 2811 1010 0000 0123 456` | 27 | ok | ok | ok | ok |

**The predicate, stated so the exposure is a number and not an anecdote.** The span is lost when all
three hold:

- the IBAN's **compact length is a multiple of 4**, so its canonical grouping leaves the optional
  `{1,4}` tail unused — **14 of the 36 countries `iban_country_length` knows** (AD · AT · BE · CY ·
  CZ · EE · ES · HU · LT · LU · PL · RO · SE · SK), plus any country outside the table whose length
  is a multiple of 4, where `iban_length_ok` returns `true` and the gate is mod-97 alone;
- the **next token is 1–4 alphanumeric characters** — an English or Italian short word, a 4-digit
  year, a currency code, the next column of a CSV;
- the resulting span holds **at least one lowercase ASCII letter** — supplied by the swallowed word
  even when the IBAN itself is canonical uppercase, which is why this is not confined to the
  rendering M11-R10 added.

DE, IT, FR, GB, NL, PT and the rest of the ≢ 0 (mod 4) countries are immune, because their canonical
grouping already spends the optional tail on a 2- or 3-character last group.

**Why every guard missed it — and it is M4's lesson 2 landing on the guard itself.** `IBAN-04`
(`iban_does_not_absorb_a_following_word`) is the guard named for this exact behaviour, and its two
fixtures are **`IT60X…` (27) and `DE89 3704 … 00` (22)** — the two countries that *cannot*
over-reach. `CASE-02` exercises the IBAN alone, never followed by anything. `PROP-03` quantifies over
**accepted** candidates and these bytes belong to a **rejected** one; `masking_leaves_nothing_detectable`
(PROP-04) passes because the orphan `ES91 2100 … 1332` is not detectable — word for word the note
M10-R1 left behind about the orphaned `912`, in the one place its prescription was never applied. The
repo's whole IBAN corpus is DE / IT / FR / LV / NL / ZZ: **not one vulnerable length is in it.**

**Fix — the chokepoint is the rejection, not the arm.** Two things are true and both need saying:

1. **`shrink_on_reject: true` for the IBAN recognizer.** This is M10-R1's fix, and it applies here
   for M10-R1's reason: IBAN is now an un-anchored family with a rejecting validator. Cutting at the
   last separator inside the span turns `ES91 … 1332 for` into `ES91 … 1332`, which verifies. It
   closes the grouped arm, where every reachable instance above lives.
2. **It does not close the continuous arm**, and that residue must be measured rather than assumed:
   `es9121000418450200051332abcd` has no separator to cut at, and it leaks today (verified through
   the binary). That is an evasion-shaped input rather than a natural one, so it may well be an
   accepted limit — but it is a *decision*, and the general rule underneath it is the one to write
   down: **a validator added to a recognizer that previously accepted everything must not be able to
   reduce coverage.** Whatever `iban_case_gate` refuses, the bytes it refuses must still reach the
   resolver in some form, or the gate is a coverage switch wearing a precision argument.

**Test that would have caught it, and it is not another example.** The predicate M10-R1 arrived at —
***no byte of a real value survives masking***, not *nothing detectable survives* — has a guard for
the phone tier (`PHONE-NAT-09`) and none for IBAN. A property test over the IBAN corpus × a trailing
token of 1–5 characters × {lowercase, uppercase, one-letter-flipped}, asserting that no 4+-character
run of the original IBAN appears in the masked output, fails on the first case here and on the
continuous arm too. The instance-shaped version — adding an ES IBAN to
`iban_does_not_absorb_a_following_word` — closes ES and leaves thirteen countries and the whole
continuous arm open.

**Closed 2026-09-04 — `shrink_on_reject: true` on the IBAN recognizer, and the guard is the
predicate rather than another example.**

**Reproduced first, then the regression proved by build rather than argued.** Three runs of the same
probe, each a real detection through `StructuredRecognizers::new()`:

| build | `…to ES91 2100 0418 4502 0005 1332 for the invoice.` |
|---|---|
| HEAD | `[(Phone, "0418 4502 0005")]` — country code, both check digits and the last group **in clear** |
| `iban_case_gate` neutralised (its `if` forced true) | `[(Iban, "ES91 … 1332 for")]` — the benign over-match, an over-mask |
| the **exact** pre-M11-R10 recognizer (uppercase-only pattern, `validate: None`) | `[(Iban, "ES91 … 1332")]` |

The third row is the one that settles what kind of defect this is. Pre-M11-R10 the pattern could not
match a lowercase byte **at all**, so the greedy `{1,4}` tail could never swallow an English word:
the span was exactly the IBAN. Folding case made the over-reach possible and the gate then deleted
the result. **A regression, introduced by M11-R10, in the direction this project never errs in.**

**The fix.** `shrink_to_a_valid_prefix` already existed for precisely this shape (M10-R1) and IBAN
was excluded from it by a doc comment about *checksum* recognizers. IBAN is not one: `iban_case_gate`
**accepts unconditionally** unless the span carries a lowercase byte, so a rejection only ever
happens on a rendering the pattern could not match before M11-R10 — and every shortened prefix it
then tries either carries no lowercase (accepted structurally, exactly what shipped for ten
milestones) or must pass mod-97 **and** the ISO 13616 length. **The shrink therefore cannot admit
anything the pre-M11-R10 build did not already admit.** That argument is now written on the
`shrink_on_reject` field itself, replacing the sentence that excluded IBAN.

Result, same probe: `[(Iban, "ES91 2100 0418 4502 0005 1332")]` — and note it is **better than
pre-M11-R10**, which masked the IBAN but also swallowed nothing extra only because it could not; the
shrink cuts the span to the value itself in both letter cases.

**The guard — `IBAN-05`, `no_window_of_an_iban_survives_masking`.** M10-R1's predicate (*no byte of
the value survives*, not *nothing detectable survives*), which the phone tier has had as
`PHONE-NAT-09` and IBAN never got. The corpus is **derived, not collected**: all 676 two-letter codes
are probed against `iban_country_length`, every country it knows is synthesised into a structurally
valid IBAN with **real** check digits (solved for, then re-checked with `iban_mod97`), and each is
driven in both renderings × three letter cases × six trailing contexts × two carrier sentences. It
asserts a non-vacuity floor in the dimension the defect lives in — at least ten countries whose
length is divisible by 4, of which there are **14** — because a corpus of immune countries is exactly
how `IBAN-04` stayed green through this.

**Mutations.**

| mutation | outcome |
|---|---|
| `shrink_on_reject: true` -> `false` (the fix removed) | **red**, and on a *worse* case than the one reported: with the carrier `" and confirm."` the AD IBAN is masked **not at all** — `AD49 1852 9630 7418 5296 3074` reaches the provider whole |
| `iban_case_gate`'s `if` forced true | red (`CASE-02`) |
| IBAN pattern back to uppercase-only | red (`CASE-01`, `CASE-02`, `CASE-03`) |

**Decided limit, measured not assumed, and it is not a regression.** A lowercase IBAN **glued** to
1-4 alphanumerics (`es9121000418450200051332abcd`) still yields no candidate: the continuous arm
carries no separator for the shrink to cut at. Verified against the pre-M11-R10 build in the table
above — it produced **no candidate for that string either**, its uppercase-only pattern being unable
to match it at all. So this is a residue of the M11-R10 fix's reach, not damage it did. Closing it
would need a **length-derived** cut rather than a separator-derived one, whose false-positive cost is
unmeasured and whose shape is IBAN-specific logic inside a generic mechanism. Recorded in
`docs/TESTING.md` -> `IBAN-05` and raised to the maintainer rather than decided here, per `CLAUDE.md`
— it is product-visible coverage.

**Promoted out of this archive.** `ARCHITECTURE.md` now carries the rule as an invariant beside the
ASCII-word-boundary one: ***a validator that rejects must not be able to delete a value*** —
whatever a newly added validator refuses, those bytes must still reach the resolver in some form, or
the gate is a coverage switch wearing a precision argument.

**Verified:** **250 / 0 / 5** over 24 binaries (round 4 measured 249; the +1 is `IBAN-05`), re-run

## Round 5 — the cost of the fix, and a published zero that is a one (2026-09-04)

Round 4 found that the M11-R10 fix had *relocated* a leak, and closed it with
`shrink_on_reject: true`. Round 5 asked the two questions that closure invites and that the M4
retrospective says are the ones that get skipped: **does the fix hold on the axis its own guard
holds constant**, and **what does it now cost on the worst input an attacker can send** (M4
retrospective, lesson 5 — *a safety fix has a cost, and the cost is part of the fix*).

**The fix holds, and holds well.** On a 5 280-case matrix that varies the axis `IBAN-05` does not —
the token *before* the value — every separated rendering is masked: **0 leaks in 3 360 separated
cases**, and HEAD is strictly better than either build behind it (1 600 leaking at HEAD against
2 599 without the M11-R13 fix and 3 840 pre-M11-R10, and all 1 600 of HEAD's are the glued residue
already recorded). The M11-R13 repro masks correctly through a rebuilt library, and HEAD's leaking
set is a strict subset of the pre-M11 one.

**What it cost was never measured, and it is large.** The IBAN validator is declared `free` — a
wrapper whose doc comment states its premise as *"a checksum over at most 18 bytes"* — and
`shrink_on_reject: true` now runs it **up to eight times per rejected match**, on spans up to 44
characters, each call allocating inside `iban_mod97`. Driven through the **real release `.exe`**
against a mock upstream, one legal 14 640 KiB request costs **8.2–10.3 s** where the byte-identical
body uppercased costs **2.1–3.1 s** in the same session. `ARCHITECTURE.md` publishes *"across every
shape measured, a request costs at most about 3 s"*. [M11-R18](#m11-r18).

**And the number that justified the gate does not reproduce.** `iban_case_gate`'s residue is
published as **0** in five places. Measured on 304.9 MB of uncurated third-party Rust source it is
**1 of 936** — a matrix-multiply kernel's register list, `ab22 ab23 ab44 ab45 ab66 ab67`, masked as
`[IBAN_1]`. [M11-R19](#m11-r19). Separately, the residue M11-R13 escalated to the maintainer is
written as affecting a *lowercase* IBAN; measured, a **canonical uppercase** one glued to a
lowercase token has the identical fate. [M11-R20](#m11-r20).

### M11-R18 — the M11-R13 fix multiplies an **unbudgeted** scan cost: a legal 14.6 MiB request now costs 8–10 s against a published ceiling of ~3 s — *hardening / availability, medium*

**Availability is a privacy property here**, in this repo's own words: *a proxy too slow to keep
switched on protects nothing.* This is not a leak and not a super-linear blow-up — the path stays
linear — but it is a constant factor of **3–4x** on an unauthenticated path, landing above the
number `ARCHITECTURE.md` publishes as the ceiling.

**Reproduced through the real release `.exe`** against a recording mock upstream: two sessions,
three reps each, every treatment paired with an in-run control on the byte-identical payload.

| body (15 360 059 bytes of JSON, one `messages[0].content`) | session 1 | session 2 |
|---|---|---|
| four-character groups, **UPPERCASE** — the gate short-circuits, no shrink runs | 2.41 / 2.07 / 2.08 s | 3.13 / 2.59 / 2.59 s |
| the same body **lowercased** — fold, gate, shrink | **9.39 / 8.19 / 10.34 s** | **8.55 / 9.23 / 9.11 s** |

Both answer `200`. The ratio is **3.2x–4.2x**; the absolute moved between sessions and the ratio did
not, so the ratio is the claim (M7-R9's rule).

**Attribution, at the library level — three builds x three reps on a 4 MiB field**, with an
uppercase control that is flat across all three, which is what proves the difference is the
case-fold path rather than the measurement:

| build | lowercase groups | UPPERCASE groups (control) |
|---|---|---|
| the exact pre-M11-R10 recognizer | **145 / 147 / 159 ms** (0 spans) | 414 / 424 / 447 ms |
| M11-R10 as it landed (`shrink_on_reject: false`) | **422 / 475 / 432 ms** | 474 / 425 / 411 ms |
| **HEAD** (with the M11-R13 fix) | **1 421 / 2 306 / 2 643 ms** | 662 / 641 / 489 ms |

So M11 took this shape from ~150 ms to ~440 ms (the fold plus the gate) and then to 1.4–2.6 s (the
shrink): **~10-17x pre-M11**, of which the M11-R13 fix is ~3-6x. At 16 MiB a single `try_detect`
measures **5 663 / 5 380 / 6 010 ms** at HEAD against **2 139 / 2 502 / 2 510 ms** without the
shrink.

**Mechanism — three lines of `src/pii/recognizers.rs` that only became true together in `5844a09`.**

1. `:253` — `shrink_on_reject: true`, the M11-R13 fix. A rejected IBAN match is now retried once per
   interior separator: up to **seven** extra validator calls for the grouped arm's widest form, on
   top of the one that rejected it.
2. `:1087-1108` — `shrink_to_a_valid_prefix` calls `check(prefix, budget)` for each attempt. The
   per-scan memo keys on the matched bytes, so on a body of **distinct** groups every one is a miss —
   the exact axis DOS-06 exists for, on a recognizer DOS-06 does not exercise.
3. `:67` — `free()` wraps `iban_case_gate`, so **none of it is charged to the request budget**. Its
   doc comment states the premise the exemption rests on: *"A validator whose cost is negligible — a
   checksum over at most **18 bytes**"*. An IBAN span is up to **44** characters and `iban_mod97`
   allocates a `String` per call, so after the fix one rejected match can cost eight allocations and
   ~350 character-operations where the premise assumed one and ~44.

`MAX_PHONE_VALIDATIONS_PER_REQUEST` cannot bound this — it is spent by the phone validator alone,
and `iban_case_gate` is `free`. The guarantee `ARCHITECTURE.md` derives from the budget does not
cover this term at all.

**Why no guard saw it — M4's lesson 6 on the DoS guards, again.** `tests/complexity.rs` varies field
size (DOS-01…03), entity count (DOS-04), alphabet (DOS-05), periodicity (DOS-06), field count
(DOS-07) and fixpoint charging (DOS-08/09) — and **every one of them holds the alphabet at digits,
`sk-` runs, or `a@b.co`**. Not one produces a body of mixed alphanumeric groups, which is the only
shape that makes the IBAN pattern match at every position *and* reject at every position. DOS-05 is
explicitly *"the third axis: what the bytes are"*, and its bytes are digit groups. `within_budget`
allows ~30 s in the debug profile, so this shape would have to get several times worse again before
an existing guard noticed.

**The claim this falsifies**, `docs/ARCHITECTURE.md`, under the budget table: *"Two terms make up a
request's CPU: `units x ~3 µs`, which the allowance caps at ~1.5 s, **plus** regex scanning and the
mask rewrite, linear in body size and entity count … Across every shape measured, a request costs at
most about **3 s**."* There is a **third term** — unbudgeted `free()` validator work, which is per
*candidate* rather than per byte — and the M11-R13 fix made it the largest of the three for a legal
body. The sentence was true when it was written: the pre-M11 build answers this shape in ~0.6 s.

**Fix — the choice is the maintainer's, because every option is product-visible.** Stated with what
each costs:

1. **Charge `iban_case_gate` to the budget** (drop it out of `free`; spend one unit per `iban_mod97`
   call). The bound then exists and is the one the architecture already describes. Cost: a
   pathological IBAN-shaped body starts being **refused** rather than slow — a new refusal on
   legal-looking traffic, which is precisely what M10 chose `500 000` over `50 000` to avoid, so the
   rate has to be measured against an ordinary payload before the number is picked.
2. **Bound the shrink rather than the validator** — cap the retries at, say, two separators instead
   of seven. Cheap, and invisible to correctness *if* every real rendering needs at most two cuts
   (the reported case needs one). That is measurable and must be measured: a cap derived from what
   the validator accepts is sound, one derived from what someone expects is M10-R13 again.
3. **Make the shrink not pay for what it already knows.** `iban_case_gate` returns `true` without
   arithmetic when the span carries no lowercase byte; the expensive path is only the lowercase one.
   Checking the ISO 13616 length before computing mod-97 is derived from the **validator** rather
   than from metadata, so it does not repeat M10-R13. Lowest product risk, smallest win.
4. **Accept it and republish the ceiling.** Legitimate — nothing here is unsafe and the shape is
   adversarial — but then the two-term model and the ~3 s figure must be rewritten in
   `ARCHITECTURE.md`, because as published they are now false.

I would take **3, then 1**: 3 carries no product risk and may close most of the gap, and 1 is the
only option that makes the architecture's own bound true. 4 alone leaves a privacy tool's
availability guarantee resting on a number that does not hold.

**Test that would have caught it.** `tests/complexity.rs` has no case whose alphabet is
**alphanumeric groups**, and that is the whole gap. A `DOS-10` built like DOS-06 — distinct,
non-repeating four-character `[a-z]{2}[0-9]{2}` groups, so the memo is inert — asserts that
`try_detect` on that shape is linear *and affordable*, and it fails on the commit that introduced
the fix. The stronger form asserts the **ratio** against an uppercase body of identical size, so it
measures the case-fold path rather than the machine — the same construction `PERF-M7` already uses
for its calibration leg.

<a id="m11-r19"></a>
### M11-R19 — `iban_case_gate`'s residue is published as **0** in five places; measured it is **1 of 936**, and the survivor is a real over-mask — *precision / docs, low*

**The claim.** `iban_case_gate` exists because folding IBAN's case sweeps in hex digests and base64
blobs, and the gate's justification everywhere is that it lets **none** of them through:

- `docs/ARCHITECTURE.md` — *"Residue: **0 of the 931**."*
- `docs/TESTING.md`, the CASE-02 note — *"Measured residue: **0 of the 931**."*
- `docs/TESTING.md`, the CASE-02 catalogue entry — *"**Measured residue: 0 of the 149 added.**"*
- `src/pii/recognizers.rs`, `iban_case_gate`'s doc — *"Measured residue of that gate on the same
  corpus: **0 of the 149**."*
- `src/pii/recognizers.rs`, CASE-02's doc — *"Measured residue: **0 of the 149 added**."*
- and the operator-facing form in `CHANGELOG.md` — *"a lowercase IBAN-shaped string that verifies as
  nothing is not [masked]"*.

Round 4 re-measured independently on a larger corpus and published **0 of 1 050**.

**Measured on 304.9 MB / 13 998 `.rs` files of uncurated third-party source
(`~/.cargo/registry/src`), through the shipped recognizer rather than a re-implementation of it:**

| build | IBAN spans | lowercase-bearing |
|---|---|---|
| `iban_case_gate`'s verification arm forced `true` (mutation C — the denominator) | 938 | **936** |
| **HEAD** | 3 | **1** |

So the residue is **1 of 936**, not 0. The survivor:

```text
ab22 ab23 ab44 ab45 ab66 ab67
    in  matrixmultiply-0.3.10/src/sgemm_kernel.rs
```

Six SIMD accumulator register names, masked as `[IBAN_1]`. It walks through the hole the source
comment beside the claim **already names**: `iban_length_ok` returns `true` for a country code it
does not know, so for a two-letter prefix like `ab` the gate is **mod-97 alone**, which one
arbitrary span in 97 passes. The comment concludes *"the zero survives that weaker reading, which is
the one the code actually implements"*. It does not.

**Why this is worth a row rather than a shrug.** It is the exact functional harm the gate was
introduced to prevent — *masking a hex digest inside a `tool_use.input`* — and the instance is a
matrix kernel's register list inside a source file, which is ordinary agent traffic. The rate is low
(≈1 per 300 MB) and the direction is safe (over-mask, restored byte-identically), so the finding is
not the behaviour. **It is that a number used to justify a design decision in five places does not
reproduce, and that the one place which reasoned about how it could fail concluded that it could
not.**

**Fix.** Two parts, and the second is the one that lasts.

1. Re-measure and republish it as a **rate with its corpus** rather than as a zero — *"1 of 936
   added matches over 304.9 MB"*, with the survivor quoted — in all five places, plus the CHANGELOG
   sentence, which currently promises an operator strictly more than the code delivers.
2. **State the mechanism as a bound rather than as an observation.** A span whose country code is
   not in `iban_country_length` is gated by mod-97 alone, so the *expected* residue is
   `added_matches / 97` — 936/97 ≈ 9.6, of which 1 was observed. **A measurement whose expected
   value is ~10 should never have been published as 0 without asking why**, and computing that
   expectation is what turns the figure from a corpus artefact into a property of the gate.

**Test that would have caught it.** `CASE-02` asserts the gate on hand-written strings, so it can
only ever confirm the cases somebody thought of. The invariant is a property test over generated
`[a-z]{2}[0-9]{2}(?: [a-z0-9]{4}){2,7}` spans: *a span the gate accepts whose country code is
unknown must pass mod-97*. The residue **rate** then belongs to the same corpus harness that already
produces the +931 figure — run in both directions, rather than only in the one that produced the
pleasing number.

<a id="m11-r20"></a>
### M11-R20 — the residue escalated to the maintainer is scoped to *lowercase*; measured, a canonical **uppercase** IBAN glued to a lowercase token has the identical fate — *docs, low (an open decision)*

**The statement**, in `docs/TESTING.md` -> `IBAN-05`, in this file's [M11-R13](#m11-r13) entry, and
in `5844a09`'s commit message, all in the same words:

> A **lowercase** IBAN glued to 1-4 alphanumerics (`es9121000418450200051332abcd`) still yields no
> candidate … That is **not a regression**: verified against a build of the exact pre-M11-R10
> recognizer, which produced no candidate for it either.

The *not a regression* half is correct, and I reproduced it: pre-M11-R10 leaks **3 840** of the same
5 280-case matrix against HEAD's **1 600**. **The scope is not.** The same fate befalls a
**canonical all-uppercase** IBAN glued to a lowercase 1-4-character token — a rendering M11-R10 did
not introduce and nobody has to contrive:

```text
in    : Please wire to ES6518529630741852963074for now.
masked: Please wire to ES6518529630741852963074for now.      (nothing masked at all)
```

At HEAD **1 600 of 5 280** matrix cases leak, and **every one is a glued trailing token**: broken
down, each of the four glued trailings contributes exactly 400, spread evenly across all three
letter cases — uppercase included. The mechanism differs by one step and the outcome is identical:
pre-M11 the pattern could not match `…3074for` at all; at HEAD it matches, and `iban_case_gate`
deletes it for the lowercase byte the glued word contributed.

**Why it matters, given that nothing changed.** This residue is the one item M11 deliberately **did
not decide** and handed to the maintainer as product-visible coverage. The framing offered to them —
*"an evasion-shaped input rather than a natural one"* — rests on the value being written in
lowercase, which nobody does by accident. *"An ordinary uppercase IBAN followed immediately by a
word"* is a different question, and it is the one actually on the table.

**Fix.** Restate the limit in `docs/TESTING.md` -> `IBAN-05` and in [M11-R13](#m11-r13)'s closure
note as: **any** IBAN — canonical uppercase included — **glued** to a 1-4-character token containing
a lowercase letter yields no candidate, because the continuous arm has no separator for the shrink
to cut at. Keep the *not a regression* conclusion, which is measured and correct, and give it the
number it now has: 3 840 -> 1 600 of 5 280.

**Test that would have caught it.** `IBAN-05`'s `TRAILING` list is `["", " for", " EUR", " x",
" abcd", " alone"]` — **every entry begins with a space**. Adding the glued forms turns it red, which
is why they are not there. The honest shape is a second assertion that pins the residue *as* the
residue — *a glued trailing token yields no candidate, in every letter case* — so that the day it
stops being true the guard says so, instead of staying quietly green. A limit nobody asserts is
indistinguishable from a limit nobody noticed.

**NOT closed — escalated to the maintainer 2026-09-04, which is what `CLAUDE.md` requires of it.**
All four options are product-visible: a new refusal on legal traffic (1), a retry cap that changes
what is detected (2), or republishing an availability ceiling (4). Those are not the builder's.

**What was done meanwhile, because it depends on no answer.** `iban_mod97` and `iban_length_ok` are
now **allocation-free** — the first used to build a compacted `String` and then a `format!`ed
rearrangement, two allocations per call, a fair price while the validator ran once per match and not
after `shrink_on_reject` made it run up to eight times. The arithmetic and every verdict are
unchanged.

Measured on this round's own shape — 4 MiB of distinct lowercase `[a-z]{2}[0-9]{2}` groups, **median
of 9**, with the uppercase control that proves the difference is the case-fold path and not the
machine:

| build | lowercase median | min | UPPERCASE control (median) | spans |
|---|---|---|---|---|
| HEAD, allocating | 2 573 ms | 2 012 | 694 ms | 56 729 |
| allocation-free | **2 108 ms** | **1 624** | 671 ms | 56 729 |

**~18% off, and the span counts are byte-identical** (56 729 and 1), which is the differential proof
that no verdict moved — the rule M10-R13 left behind about optimisations in front of validators.
**It does not close this finding**: the lowercase path is still ~3x its own uppercase control, and
term 3 is still unbudgeted. Option 3 as the round framed it — checking the length before mod-97 —
was measured and **rejected**: `iban_length_ok` answers `true` for a country code it does not know,
so on exactly the adversarial shape (random two-letter prefixes, ~95% unknown) it rejects nothing
earlier and buys nothing.

**One number this round did not have, measured while attributing the cost.** The shrink's price is
not only time. On the same 4 MiB body it takes the masked-span count from **7 943 to 56 729** —
**7.1x more over-masking** on an adversarial shape. Every one is an over-mask, restored
byte-identically, so the direction is safe; it is stated because option 2 (capping the retries)
would buy that back as well as the time, which changes the balance between the options.

**`ARCHITECTURE.md` has been corrected regardless of the decision**, because the sentence it
published was false: the CPU model now names **three** terms, states the measured 8–10 s and the
2.1 s/671 ms library pair, says plainly that "at most about 3 s" no longer holds, and points here
for the open decision. Leaving a knowingly false availability guarantee standing is M11-R14's defect,
and correcting a number is not choosing an option.

**Closed 2026-09-04 — republished as a rate with its corpus, and as a *bound* rather than an
observation.** All five places plus the CHANGELOG sentence now read **1 of 936 added matches over
304.9 MB**, with the survivor named (`ab22 ab23 ab44 ab45 ab66 ab67`, a matrix kernel's SIMD
register list). More important than the number: each one now states **why zero was never the right
answer** — `iban_length_ok` answers `true` for a country code the table does not know, so such a
span is gated by mod-97 alone and one in 97 passes, making the expected residue `added / 97` ≈ 9.6.
The bound is that rate.

The CHANGELOG sentence promised an operator strictly more than the code delivers (*"a lowercase
IBAN-shaped string that verifies as nothing is not [masked]"*); it now says *almost never*, gives
the measured rate, and says the value is masked rather than leaked and restored byte-identically.
`iban_case_gate`'s own doc — the one place that reasoned about this hole and concluded the zero
survived it — now says the opposite in the same sentence, so the reasoning and the number cannot
drift apart again. The neighbouring claim *"the rule is split by rendering, and it costs nothing"*
was corrected too: it costs very little, not nothing.

`docs/DEVLOG.md`'s 2026-09-03 entry still carries the 0. That is a running log of what was believed
on the day and is not rewritten; the correction is in this round's entry, which is how a log carries
one.

**Closed 2026-09-04.** The limit is restated in `docs/TESTING.md` -> `IBAN-05` without the
lowercase scoping: an IBAN **glued** to 1-4 alphanumerics yields no candidate whether the IBAN is
`es9121000418450200051332abcd` or a canonical uppercase `ES9121000418450200051332abcd` — one
lowercase byte anywhere in the glued token is enough to make the gate demand verification of the
over-long span, whatever case the IBAN itself is written in. The *not a regression* half is
unchanged and still verified against the pre-M11-R10 build, which matched neither string.

What goes to the maintainer alongside [M11-R18](#m11-r18) is therefore the wider statement, and the
same entry now carries the number that was missing from the trade: capping or removing the shrink
would buy back **7.1x** of over-masking on an adversarial body as well as the time.
