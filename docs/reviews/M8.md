## Round 1 (2026-07-19)

**What I verified independently.** Built and ran both suites via PowerShell (MSVC linker): **108
default** + **132 onnx** lib tests green, `clippy` clean on both feature sets, `cargo fmt --check`
clean. Ran all three gated GLiNER tests against the **real** int8 model
(`onnx-community/gliner_multi_pii-v1`, `model_quantized.onnx`, 349 MB) and **reproduced the DEVLOG
numbers to the digit**: Person 0.583 / 0.778, Organization 1.000 / 1.000, Location 0.909 / 1.000. The
`SMOKE-GLINER` decode is correct on the real export (Mario Rossi→Person, Google→Org, Milano→Location,
`020 7946 0958`→Phone, Anna Bianchi→Person, Acme Corporation→Org), so the `markerV0` tensor contract —
`words_mask`, `span_idx`, the word-major logits layout — is sound end-to-end. The inertness canary
reproduced: GLiNER *does* tag `[PERSON_1]`/`[ORG_1]`/`[PHONE_1]` (all as Person) yet `mask_all`
converges with the text unchanged.

**The safety questions the handoff raised, and what I found by trying to break them:**
- **Fixpoint convergence with a placeholder-tagging model — airtight.** I traced it and it does *not*
  rest on `keep_maskable` dropping *exact* placeholders. It rests on **S4**: GLiNER's `redetect → empty`,
  so GLiNER runs on **pass 0 only** and can contribute at most one masking pass. A multi-word GLiNER span
  that *crosses* a placeholder (I saw the real model emit exactly this shape — `"Scrivi a Tizio e a
  Caia"`, `"Bel Jan Jansen"`) is not an exact `[KIND_N]` token, so `keep_maskable` keeps it — but the
  worst that does is a bounded **over-mask on pass 0** (it swallows an echoed placeholder into a new one),
  never a stall and never a leak; pass 1 runs structured-only and converges. `keep_maskable`'s exact-drop
  only spares a *cleanly*-echoed placeholder the over-mask — it is not load-bearing for convergence.
- **A GLiNER-emitted `Phone` is `is_structured()` → sound, but the docs mis-describe the path (→ [M8-R3]).**
- **No leak / fail-open surface found.** Structured recognizers always run first in the composite; GLiNER
  is purely additive. Under `NER_REQUIRED` an unwrapped GLiNER error propagates → 400 (fail-closed); under
  fail-open it is `FailOpen`-wrapped → structured-only. `build_detector(true)` with no ML still aborts at
  startup (`required_ner_is_fatal_when_absent`, green).

**Net: M8 is clean on the axes that matter here — no leak, no fail-open regression, the fixpoint is
provably safe with GLiNER in the composite, and "addition, not successor" is honestly recorded.** The
five findings below are hardening / test-coverage / docs. None is a leak.

<a id="m8-r1"></a>
### M8-R1 — GLiNER chunking has no choke-point ceiling guard; the re-tokenized sequence is never checked against `max_len` (hardening)

**The scope item that was checked off but only half-delivered.** ROADMAP S3
([#m8](../ROADMAP.md#m8), line ~1062) required: *"Port M5's chunking discipline (the compile-time
headroom invariant [M5-R2]/[M5-R10], **enforcement at the single choke point**) … **Guard: every
re-tokenized window + its prefix stays under GLiNER's max.**"* Neither the enforcement nor the guard
was implemented.

**Mechanism.** `GLiNerDetector::infer` (`src/pii/gliner.rs:173-209`) plans windows from
`word_token_lens` — each word encoded **alone** (`encode(w, false)`, `:213-227`) — and subtracts a
`text_budget = max_len − prompt − specials` (`:181-196`). But `infer_window`
(`src/pii/gliner.rs:231-359`) then re-tokenizes the window **jointly** with the prompt
(`encode(pieces, true)`, `:244-250`), builds tensors of whatever length `seq` comes out, and calls
`session.run` — **with no check that `seq ≤ params.max_len`.** This is precisely the M5-R2/M5-R7
shape: *a window is planned in one tokenization's coordinates but re-tokenized from its own text*, and
"a bound you do not check is not a bound." The twin XLM-R path has exactly this guard —
`onnx::run_and_decode` is the *single* path into the session and it **rejects** an over-long sequence
with an `Err` (M5-R7), letting the posture owner (`FailOpen`/`try_detect`) decide. GLiNER has no
equivalent.

**Failure scenario.** If the per-word-**alone** token counts ever undershoot the joint,
`is_split_into_words` re-tokenization (a drift the mDeBERTa SentencePiece metaspace can introduce at
window edges), a window's real `seq` exceeds `max_len=384` and reaches the model unchecked. Outcome is
bounded to **fail-closed 400** (under `NER_REQUIRED`, if the ONNX graph errors on the over-long
sequence — the M5 `Expand`-overflow class) or **silent recall loss** (if the export has dynamic axes
and silently degrades). **Never a leak** — structured PII is detected unchunked over the whole field —
but availability is a privacy property here, and this is the exact axis M5 spent three rounds on.

**Honesty about likelihood.** I could **not** demonstrate it firing: for SentencePiece the per-word
drift is ≈0, and the budget already subtracts `prompt + specials`, so `seq ≈ max_len` by construction
with essentially no slack consumed. So this is **PLAUSIBLE, not observed** — but it is unobserved partly
*because* the multi-window path has never run against the real model at all (see [M8-R2]).

**Fix.** Add the M5-R7 choke-point check in `infer_window` right before `session.run`: if `seq >
self.params.max_len`, return `Err(anyhow!("GLiNER sequence {seq} exceeds max_len {max_len}"))` (value-
free), which already flows through `try_detect → DetectError` to the posture owner. Optionally add the
compile-time/`from_config`-time headroom assertion the scope named.

**Test that would have caught it.** The S3 "Guard" itself: a gated test that runs a field large enough
to force ≥2 windows and asserts every re-tokenized window's `seq ≤ max_len` (the GLiNER analogue of
`onnx.rs::chunk_tests` + the 481–483 drift assertion). See [M8-R2].

<a id="m8-r2"></a>
### M8-R2 — GLiNER's multi-window chunking path has never run against the real model (test-coverage)

**Mechanism / evidence.** Every gated input in `tests/gliner_eval.rs` is a single short sentence
(smoke: ~50 chars; canary: 53 chars; the eval corpus's **longest** input is 60 chars — measured), and
the text budget is ~360+ tokens, so **all of them fit one window**. `plan_word_windows` is unit-tested
(`gliner.rs:447-484`) purely as a function over integer token counts, and the cross-window merge/dedup
(`infer`, `:196-208`), the joint re-tokenization length, and `words_mask` construction on a chunked
field are **never exercised end-to-end**. The chunking code shipped `[x]`-checked (S3) on the strength
of a pure-function unit test alone — the same shape as PERF-01 measuring a repeated sentence and calling
it done.

**Failure scenario.** A systematic per-word-vs-joint token drift (→ [M8-R1]) or a cross-window
merge/coordinate bug would surface only in production, on the first field big enough to chunk — under
`NER_REQUIRED`, as a 400.

**Fix / test.** Add a gated large-field test (the GLiNER twin of
`ner_perf.rs::onnx_ner_latency_and_recall_across_field_sizes`): run GLiNER on a field that forces
several windows, assert (a) it returns without error, (b) a known entity near a window seam is still
detected (recall preserved by the one-word overlap), and (c) the [M8-R1] guard — each window's
re-tokenized `seq ≤ max_len`.

<a id="m8-r3"></a>
### M8-R3 — ARCHITECTURE says a GLiNER guess "loses in overlap"; false for its `Phone`, which is `is_structured()` and is *union-merged* (docs)

**Mechanism.** `ARCHITECTURE.md:573-575` states: *"a GLiNER guess overlapping a checksum-backed match
loses in `overlap`."* That holds for GLiNER's **NER** kinds (`Person`/`Organization`/`Location`, incl.
`address → Location`), which land in the NER partition of `resolve_overlaps` and take the whole-span
drop. It is **wrong for `phone number → Phone`**: `PiiKind::Phone.is_structured() == true`
(`pii/mod.rs:109-114`), so a GLiNER `Phone` goes into the **structured** partition and is **union-
merged** — never dropped, and if it is the highest-priority raw candidate it *names the union*
(`overlap::name_of`). So a GLiNER-guessed phone overlapping a deterministic match doesn't "lose"; it
extends/merges into a masked union.

**Why it still isn't a leak (verified).** The union-merge invariant — *no structured span's bytes are
ever abandoned* — holds regardless of who produced the span, so a GLiNER `Phone` false positive is a
bounded **over-mask** (it may mislabel a union `[PHONE_n]` or widen it), exactly the standing tradeoff.
The behaviour is sound; only the doc is misleading, and on a subtle, load-bearing point (the handoff
asked specifically whether the resolver handles a GLiNER structured kind soundly — it does, but not the
way the sentence describes).

**Fix (promote the rule).** In the GLiNER ARCHITECTURE paragraph (and next to the overlap invariant),
record the split: a GLiNER **NER** kind takes the greedy whole-span drop; a GLiNER **structured** kind
(`Phone`) is union-merged like any structured span and may name the union — both directions over-mask,
neither abandons bytes. This is the invariant a future builder needs before adding a GLiNER→structured
label mapping.

<a id="m8-r5"></a>
### M8-R5 — `load_gliner` silently disables GLiNER on partial config / a bad threshold (hardening, low)

**Mechanism.** `server.rs::load_gliner`:
- If `GLINER_MODEL_PATH` is set but `GLINER_TOKENIZER_PATH` **or** `GLINER_CONFIG_PATH` is missing (a
  typo'd var name), it returns `Ok(None)` — GLiNER **silently off** — with no log line. Under
  `NER_REQUIRED` with XLM-R also loaded (`ml_loaded > 0`), the proxy starts clean and the operator who
  meant to enable GLiNER never learns it didn't. For an **opt-in security feature**, a silent disable is
  a footgun: you believe GLiNER is protecting the un-anchored phone/address surface, and it isn't.
- `GLINER_THRESHOLD` is parsed with `.parse::<f32>().ok().unwrap_or(DEFAULT_THRESHOLD)`, so a typo
  (`0,15`, `hgh`) silently uses 0.15, and an out-of-range value (`2.0`) silently makes GLiNER a **no-op**
  (sigmoid ≤ 1 < 2) while it appears loaded — a silent total recall loss for the GLiNER layer.

**Not a leak / not a fail-closed violation** (structured always runs; XLM-R covers names in the
recommended config), so this is low. But it violates the spirit of the "loud about model
loading/config" posture (`NER_MODEL_REPO` fetch is logged; `id2label` parse fails closed).

**Fix.** `warn!` when `GLINER_MODEL_PATH` is set but a companion var is absent ("GLiNER disabled"),
and reject/`warn!` a `GLINER_THRESHOLD` outside `[0.0, 1.0]` or unparseable rather than silently
substituting the default.

---

_No finding is a leak or a fail-closed regression. R1/R2 are the pair worth acting on (the S3 discipline
M5 taught, not yet ported, and the missing test that would exercise it); R3 promotes the one non-obvious
invariant this milestone added; R4/R5 are housekeeping._

### Closure — builder (2026-07-19)

All five closed. **R1/R2 turned out to be more than hardening: acting on them exposed a real recall bug
the pure-function unit test had hidden** — exactly the risk R2 named.

- **M8-R1 — closed.** Added the M5-R7 choke-point guard in `infer_window` (`gliner.rs`): before
  `session.run`, `seq > params.max_len` → `Err` (value-free), flowing to the caller's posture. **But the
  guard alone was not the fix** — see R2.
- **M8-R2 — closed, and it earned its keep.** Added `gliner_chunks_a_large_field_and_keeps_recall`
  (gated). Writing it revealed that a window filled to the `max_len` budget makes the model return
  **all-low logits at `seq ≈ 384`** (measured — a 313-word window scored *zero* on a clear name), and
  that GLiNER int8's confidence **dilutes with context** well before that (a name at a window's start
  scores ≳0.2 while the window stays ≲100 text tokens, ~0.15 by ~130). **Fix:** the window is now capped
  at `MAX_WINDOW_TEXT_TOKENS = 100` (far below the `max_len` budget), which bounds the total context
  every span is scored against — the dilution is a function of window *size*, not the entity's position
  (M8-R7), so a small window scores an entity at any offset; `WINDOW_OVERLAP_WORDS = 8` separately keeps
  a boundary-crossing entity whole. This is the S3 "smaller windows" discipline, but for a *recall*
  reason unique to GLiNER, not the M5 length reason. Long-field recall stays weaker than short-field — a documented model property (the default
  XLM-R covers long system prompts); the test asserts the multi-window path runs without error and keeps
  a well-positioned entity. The eval numbers are unchanged (corpus sentences are single-window).
- **M8-R3 — closed.** `ARCHITECTURE.md` (and the `gliner_decode.rs` module doc, the same imprecision in
  source) now state the split by kind: a GLiNER **NER** kind takes the whole-span drop; a GLiNER
  **`Phone`** is `is_structured()` → union-merged and may name the union — both over-mask, neither
  abandons bytes.
- **M8-R4 — closed.** Added a 12th `gliner_decode` test (`decode_is_deterministic_on_tied_scores` — pins
  that placeholder-minting order is span-, not input-, ordered), so the count now genuinely is 12.
- **M8-R5 — closed.** `load_gliner` now returns **`Err`** (not `Ok(None)`) when `GLINER_MODEL_PATH` is
  set but a companion var is missing, and **rejects** a `GLINER_THRESHOLD` that is unparseable or outside
  `[0.0, 1.0]` — no more silent disable of an opt-in security feature.

Verified after the fixes: 109 default / 133 onnx lib green, `clippy`/`fmt` clean both feature sets, all
four gated GLiNER tests pass against the real int8 model (eval numbers reproduced to the digit).

### M8-R6 — `required_ner_is_fatal_when_absent` is non-hermetic; the M8 gated-test env breaks the lib suite (test-quality, low)

**Repro (reproduced, exit 101).** With the three `GLINER_*` vars set — i.e. **exactly the environment the
M8 gated-test workflow tells you to create** (`tests/gliner_eval.rs` header; the DEVLOG; the round-1/round-2
handoff instructions) — `cargo test --features onnx --lib` **fails**:
```
thread 'server::tests::required_ner_is_fatal_when_absent' panicked at src\server.rs:813:9:
assertion failed: build_detector(true, &[]).await.is_err()
test result: FAILED. 132 passed; 1 failed
```
In a clean shell the same command is 133/0.

**Mechanism.** `build_detector` calls `load_gliner`, which reads `GLINER_MODEL_PATH` straight from
`std::env` (`server.rs`). The test asserts that `NER_REQUIRED` with *no* ML configured is fatal — but an
ambient `GLINER_MODEL_PATH` makes GLiNER actually load, so `ml_loaded > 0`, the
`ensure!(!ner_required || ml_loaded > 0)` passes, and `build_detector` returns `Ok`. The test comment even
concedes the dependency ("*no model configured in the test env*").

**Scope, stated honestly.** The non-hermeticity is **pre-existing** — the same test already reads
`NER_MODEL_PATH` / `NER_MODEL_REPO`, so a developer set up to run `ner_eval` could always trip it. M8 (a)
**widened** the env surface it reads (`GLINER_MODEL_PATH`) and (b) shipped a **documented workflow** that
reliably creates the failing env. So the builder's "133 onnx lib green" is true only in a clean shell — a
caveat worth pinning, because the natural M8 dev loop (set `GLINER_*`, run everything) is the one that
breaks. Not a leak; CI (which sets none of these) is unaffected.

**Fix.** Make the `build_detector` tests hermetic. The clean version is dependency injection —
`load_gliner`/`load_onnx_ner` take their paths as parameters rather than reading `std::env` inside
`build_detector` — so the test controls the config. (Mutating/clearing env in the test is racy: cargo runs
tests multi-threaded and `std::env::remove_var` is process-global.) Minimally, document that the onnx lib
suite must run with the model env vars unset. **Test:** the same assertion, but driven through injected
"no ML configured" rather than ambient env.

<a id="m8-r7"></a>
### M8-R7 — the window-cap recall rationale mis-explains *why* it works (docs, low)

**Mechanism.** The `MAX_WINDOW_TEXT_TOKENS` doc (`gliner.rs`) and the builder's closure note both say the
small window *"keeps every entity near **some** window's start (via `WINDOW_OVERLAP_WORDS`) where it still
scores."* Measured, that causal story is wrong. The window stride is ≈ (window − overlap) ≈ 70–90 words
while the overlap is only 8 words, so a mid-field entity is at an arbitrary offset (up to ~70) in its best
window — **not** near any start. Yet my probe shows it is detected anyway, at *every* offset (pre = 0…70)
and mid-multi-window (word 120/200/300), all at 0.15. So recall is preserved not because entities sit near
a start, but because **capping total window context keeps every span's score above threshold regardless of
position** — the dilution the DEVLOG measured is a function of *total window length*, not of an entity's
position within it.

**Why it matters (promote the rule).** The two knobs have **different jobs**, and the doc conflates them:
`MAX_WINDOW_TEXT_TOKENS` bounds total context → protects *scores* (shrink it if int8 scores dilute);
`WINDOW_OVERLAP_WORDS` only keeps a **boundary-spanning entity whole** → must exceed the longest expected
entity, and has nothing to do with scoring. A future builder tuning either (e.g. for fp32, or adding a
longer entity kind) needs the right model: the overlap is not a recall-vs-position lever. Not a bug — the
shipped values are fine and I verified recall — but the rationale next to the constants is misleading on
exactly the point someone would change.

**Fix.** Correct the `MAX_WINDOW_TEXT_TOKENS` / `WINDOW_OVERLAP_WORDS` docs (and the ARCHITECTURE GLiNER
paragraph if it repeats it): recall is preserved by the bounded total context (position-independent,
measured); the overlap's role is whole-entity-at-boundary, sized to the longest expected entity.

## Round 4 (2026-07-19) — M8.1: opt-in GB/DE national phone recognizer

### M8-R8 — the swallow guard has a blind spot: a longer *invalid* arm-1 match shadows the first of two adjacent numbers; only the **fixpoint** (not the bounded regex) prevents the miss (hardening — **not a leak**)

**This is not a runtime leak** — I verified the fixpoint recovers it. It is recorded because the *reason*
it is safe is not the reason the code and tests claim, and that misattribution is a latent leak the M4
retrospective's own lessons predict (a guard tests the case the author thought of, not the sibling; safety
is credited to the wrong mechanism).

**Mechanism.** The national-phone regex (`recognizers.rs:337`) is a 3-arm alternation of **different
lengths**. Arm 1, the 3-group form `0\d{1,4}[ -]\d{3,4}[ -]\d{3,4}`, can consume the *trunk + first group*
of a 2-group number and then the *trunk* of the **next** number as its own second group — an over-long span
that crosses the boundary between two adjacent numbers. For `0800 1111 0800 1111`:

```text
at=0  arm-1 match [0..14]  "0800 1111 0800"   is_valid=false  → NOT recorded
      Scan::Overlapping resumes at next_char_boundary(start)=1
at=1  find_at(input,1) → [10..19] "0800 1111" (the SECOND number)  is_valid=true → run
      (the first number's valid 2-group form is at [0..9], which find_at(…,1) can never return)
RESULT: single-pass detect() yields ONE span — the second number. The first is absent.
```

Verified with the real recognizer:
`StructuredRecognizers::with_locales(&["gb"]).detect("0800 1111 0800 1111")` → a single `Phone` span
`"0800 1111"` at bytes `10..19`; the first `0800 1111` (bytes `0..9`) is **not** a candidate on pass 0. Same
for two *different* adjacent numbers where the first is a 2-group form (`0800 1111 0207 946 0958` → only
`0207 946 0958` on pass 0).

**Why it is nonetheless safe (verified, and this is the crux).** The request path masks with
`Vault::mask_all`, whose **fixpoint** re-detects. Pass 0 masks the second number → `0800 1111 [PHONE_1]`;
the first number is no longer shadowed (arm 1 cannot extend across `[PHONE_1]`), so pass 1 detects it via
arm 2 and masks it. Real `mask_all` output (path-dependency probe against the crate):

```text
"0800 1111 0800 1111"        → "[PHONE_1] [PHONE_1]"      round-trip exact
"0800 1111 0207 946 0958"    → "[PHONE_2] [PHONE_1]"      round-trip exact
"call 0800 1111 0800 1111 now" → "call [PHONE_1] [PHONE_1] now"
```

Both numbers are masked. And if the fixpoint ever failed to converge, `mask_all` fails **closed** (M4-R20),
never forwards. So: no fail-open leak today.

**Why it matters (the misattribution + the latent risk).**
1. **PHONE-NAT-04** (`national_phone_does_not_swallow_an_adjacent_number`, `recognizers.rs:1451`) asserts
   "the bounded-group regex must yield two spans, never one over-long span that `is_valid` would then reject
   (a leak)" — but its only input is `020 7946 0958 0161 496 0000`, where the greedy match at position 0 is
   *already* the valid full number (nothing longer forms), so the shadowing never triggers. The test
   confirms the case the builder pictured, not the sibling (2-group / freephone first number) where a longer
   **invalid** arm-1 match *does* form. It also tests only single-pass `detect()` — but for the pictured
   input single-pass already yields both, so it never depends on the fixpoint and never reveals that the
   sibling shape does.
2. **The safety is credited to the bounded regex, which does not deliver it here.** The
   `national_phone_recognizer` doc (`recognizers.rs:326-329`) states bounded groups mean "a match can never
   run across two adjacent numbers and swallow one" — but arm 1 **does** match across the boundary
   (`0800 1111 0800`); it is `is_valid`-rejected, and the shadowed first number is recovered **by the
   fixpoint**, exactly the backstop the *Sequential* (`Email`/`Secret`) recognizers document relying on and
   this *Overlapping* one's doc denies. Bounded groups bound the arm's *length* (keeping `Scan::Overlapping`
   linear, and stopping an *open* `(?:[ -]?\d)+` from eating an unbounded run) — they do not stop a
   cross-boundary match from shadowing a shorter valid form.
3. **Latent leak if the fixpoint reliance is ever weakened.** If a future builder makes the national phone
   override `redetect` to skip later fixpoint passes — a plausible latency move, by direct analogy with S4's
   "NER on pass 0 only" — the first-number miss becomes a **real fail-open leak**, and *no test would catch
   it*: PHONE-NAT-04 exercises a shape that doesn't shadow, and there is no `mask_all`-level test for the
   national phone at all.

**Fix (builder, source).**
- Add a **`mask_all`-level** guard (the shape PHONE-NAT-04 should have covered): two adjacent 2-group /
  freephone numbers (`0800 1111 0800 1111`, and a mixed `0800 1111 0207 946 0958`) must mask **both** — no
  raw digit group left in the masked body — asserted on the fixpoint output, plus exact round-trip. Keep the
  existing single-pass `detect()` assertion for the non-shadowing shape as-is.
- Correct the `national_phone_recognizer` doc: arm 1 *can* match across two adjacent numbers; the
  cross-boundary span is `is_valid`-rejected and the shadowed shorter form is recovered by **`mask_all`'s
  confirmed fixpoint**, the same backstop the `Scan::Sequential` recognizers name — bounded groups bound the
  *length* (linearity + no open-run swallow), not the cross-boundary match itself.

**Test that would have caught it.** The `mask_all`-level two-freephone case above; on the current code it
passes (the fixpoint works), but it makes the fixpoint reliance *load-bearing and visible*, so a future
`redetect` shortcut that reintroduces the miss fails it.

**Promote on close (proposed, ARCHITECTURE next to `Scan`/fixpoint).** *A multi-arm **bounded** recognizer
whose longest arm can span into an adjacent value inherits the Sequential recognizers' fixpoint reliance:
single-pass `detect()` can miss a shorter valid form shadowed by a longer **invalid** greedy match at the
same start (the overlapping rescan resumes forward of it and cannot return it). `mask_all`'s confirmed
fixpoint is the backstop — so such a recognizer must never override `redetect` to skip later passes, and its
swallow guard must assert at the `mask_all` level, not on single-pass `detect()`.*
