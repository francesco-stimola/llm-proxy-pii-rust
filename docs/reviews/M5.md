## Review 1 — M5 integration & performance (2026-07-14)

Reviewed `cd0395c` (integration tests) · `df62387` (perf harness) · `12c9ea8` (NER chunking) ·
`442144c` (README, CI/release, manual runbook).

### What I verified independently

**Build & suite.** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and
`cargo clippy --all-targets --features onnx -- -D warnings` all clean; `cargo test` **132 passed**
(+1 `#[ignore]`d), `cargo test --features onnx` **144 passed** (+4 `#[ignore]`d). Zero warnings on
both feature sets. The ROADMAP's counts are accurate.

**The chunking bug is real — reproduced from the pre-fix commit.** I built a detached worktree at
`df62387` (the commit *before* the fix), dropped in the new `tests/ner_perf.rs`, and ran it against
the real XLM-R int8 model. It fails exactly as claimed, and abruptly:

```text
reps=   16 (944 chars): 94.1821ms, 48/48 entities found
thread 'onnx_ner_latency_and_recall_across_field_sizes' panicked at tests\ner_perf.rs:94:35:
reps=64: NER call failed: onnx-ner detector failed: ONNX run: Non-zero status code returned
while running Expand node. Name:'/roberta/Expand' Status Message: invalid expand shape
```

So the failure mode really is an **outright error at ~3.8 KB of prose**, not a slowdown — and under
`NER_REQUIRED` that is a hard 400 on every such request. The diagnosis in ARCHITECTURE / DEVLOG /
ROADMAP is correct, including the correction of the *suspected* cause (quadratic self-attention) to
the actual one (position-embedding overflow). This is the right kind of finding: the measurement
was allowed to contradict the hypothesis.

**The fix works, and I re-measured it.** On `HEAD` the same test passes with linear scaling —
**460 ms / 1.96 s / 7.77 s** at 64×/256×/1024× (the builder recorded 448 ms / 2.07 s / 7.53 s;
same machine class, debug profile). Entity counts `192/192`, `771/768`, `3084/3072` — reproducing
the *over*-count the docs honestly flag.

**Drove the real binary end-to-end** (`--features onnx`, `NER_REQUIRED=1`, `RUST_LOG=…=trace`,
mock upstream, a **3852-char** field — well past the pre-fix cliff):

| | result |
|---|---|
| upstream saw `bob@test.com` / `4111111111111111` / `Mario Rossi` / `Giulia Bianchi` | **no** (all four) |
| upstream saw `[EMAIL_1]` `[CARD_1]` `[PERSON_1]` `[ORG_1]` `[LOCATION_1]` + the augmentation message | **yes** (all) |
| client got all four raw values restored; any `[KIND_N]` left unresolved | **yes** / **none** |
| raw PII anywhere in the `trace` logs | **none** (placeholders only) |

`[PERSON_1]`/`[ORG_1]`/`[LOCATION_1]` reaching the upstream on a 3852-char field *is* the proof that
chunking works in production, not just in a test: pre-fix, NER on that field returned nothing at all
(or 400 under `NER_REQUIRED`).

**What I tried to break and couldn't.**

- *Can the chunk slice panic on a multi-byte char?* I copied `chunk_char_ranges` verbatim into an
  off-repo probe and ran it with the **real** XLM-R tokenizer over 13 adversarial inputs — Chinese,
  Japanese, Cyrillic, emoji + flag sequences, combining marks, zalgo, mixed-script glue, a
  20 000-char single token, base64 runs, whitespace floods. **Every** window boundary landed on a
  `char` boundary; `&input[char_start..char_end]` never became unsliceable. (The *shape* of the risk
  is still real — see [M5-R3](#m5-r3) — but I could not produce it.)
- *Can chunking drop or duplicate an entity at a window boundary?* No, and for a reason worth
  writing down (I have — see the promotion note below). Windows are 480 tokens with a 448-token
  stride, so any entity ≤ 32 tokens is whole in at least one window. A *truncated* fragment from a
  neighbouring window (`Mil` vs `Milan`) survives `infer_chunked`'s `dedup()` (it only removes
  **exact** duplicates), but `overlap::resolve_overlaps` then cleans it up: all three NER kinds share
  `priority() == 0`, so its NER phase tiebreaks on **span length, descending** — the whole entity is
  taken first and the fragment is dropped as overlapping. The `>100%` entity counts in `ner_perf`
  are bare-detector output; production never sees them.
- *Does the mask→re-detect **fixpoint** still converge now that large fields actually reach the
  NER?* This is the one that worried me: ARCHITECTURE argues convergence from "a placeholder is
  **inert**", but that argument is about **recognizers** (regex), and an ML model is under no such
  constraint. I ran the real detector over 2 520 bytes of placeholder-only text
  (`Contact [PERSON_1] at [ORG_1] in [LOCATION_1] about [EMAIL_1]. ` ×40, large enough to be
  chunked): **0 entities tagged**. Full-hybrid `mask_all` converges on 412 B / 6.6 KB / 26 KB fields
  with no raw PII in the masked text. It holds — **empirically**, which is not the same as by
  construction. See [M5-R4](#m5-r4).
- *Are the release binaries self-contained?* Yes — `ort`'s `download-binaries` links ONNX Runtime
  **statically**: there is no `onnxruntime.dll` anywhere under `target/`, and the built `.exe` ran
  standalone. `release.yml` shipping a bare binary per target is therefore correct.

**No leak, no fail-open, no over-mask regression found.** Chunking is confined to the NER
(`OnnxNerDetector::infer`); structured PII is still detected over the whole field, unchunked, by the
fail-closed layer. The M5 findings below are one stale doc, three hardening/invariant items, and two
accuracy nits — nothing that forwards PII.

### M5-R1 — TESTING.md still says the NER is unchunked and quadratic — the exact claim M5 disproved *and* fixed

**Severity: docs (medium — it is in the file that governs the guards).**

`docs/TESTING.md:294-297`, closing the *Algorithmic complexity* section:

> **What is NOT covered here (stated so nobody reads more into it).** These guards bound the
> **structured** (default-build) path. The optional `onnx` NER feeds the whole field as **one
> sequence** with no chunking, so its self-attention is quadratic in field size — a separate,
> opt-in cost, to be **measured** by M5's perf harness (PERF-01) before NER is recommended for
> large bodies.

Every clause of this is now false:

1. the NER **does** chunk (`src/pii/onnx.rs::infer_chunked`, `12c9ea8`);
2. "its self-attention is quadratic in field size" is the hypothesis M5 **measured and refuted** —
   the real behavior was an *outright `Expand`-op error* past the position-embedding limit, which is
   the whole point of the finding;
3. "to be measured by M5's perf harness" is a **stale open point** — PERF-01 ran, and this is its
   result.

The equivalent block in `ARCHITECTURE.md:109-112` *was* updated (it now says "chunked and measured
linear (M5, PERF-01)"). TESTING.md's was not. A reader of TESTING.md — the file a builder opens
before touching a guard — is told the opposite of what shipped, and is told the disproved cause as
fact. This is precisely the "no stale open points" bar.

**Fix.** Replace the block with what M5 actually established: the guards bound the **structured**
path; the `onnx` NER is chunked (`MAX_SEQUENCE_TOKENS` / `CHUNK_OVERLAP_TOKENS`) and measured linear
in field size (PERF-01: 460 ms / 1.96 s / 7.77 s at 64×/256×/1024×), and it is a **recall**
mechanism only — never leak-relevant, because structured PII is detected over the whole field,
unchunked. Point at `ARCHITECTURE.md` → *NER chunking (M5, PERF-01)* rather than restating it.

**Test.** None possible — this is prose. The guard is the review itself; the reason it slipped is
that the same claim lived in two files and only one was updated. Keeping the *statement* in
ARCHITECTURE and a **pointer** in TESTING removes the duplicate that made the drift possible.

> **Closed 2026-07-14.** `TESTING.md`'s *What is NOT covered here* box now states what M5 actually
> established (the NER is **chunked**, measured linear, and a **recall** mechanism only, never
> leak-relevant) and **points at** `ARCHITECTURE.md` → *NER chunking (M5, PERF-01)* instead of
> restating the mechanism. The duplicate that allowed the drift is gone, and the box says so
> explicitly: **one home for a fact** is the project's rule for review findings, and it applies to
> design claims identically.

### M5-R2 — `MAX_SEQUENCE_TOKENS` does not bound what actually reaches the model

**Severity: hardening / availability (low-medium).**

`src/pii/onnx.rs:43-47`:

```rust
/// Upper bound on tokens (special tokens included) fed to the model in one call.
const MAX_SEQUENCE_TOKENS: usize = 480;
```

It isn't. `chunk_char_ranges` picks the window in the coordinates of the **whole field's**
tokenization, but `infer_chunked` then **re-tokenizes each window from its own text**
(`onnx.rs:161-164`) — correctly, because a middle window needs its own `<s>…</s>` framing. The
re-tokenized chunk is a *different* tokenization: it adds 2 special tokens and drifts at the two cut
edges. Nothing re-checks the result before `run_and_decode` hands it to the session.

Measured with the real XLM-R tokenizer (off-repo probe, verbatim copy of `chunk_char_ranges`, 13
inputs incl. CJK / combining marks / no-space runs): **every** chunk re-tokenizes to **481–483
tokens** — i.e. *always* over the 480 the constant claims to enforce.

That is fine today, but the margin is thinner than it looks. XLM-R's `config.json` declares
`max_position_embeddings: 514`, and RoBERTa-family position ids start at `pad_token_id + 1 = 2`, so
the **usable** sequence length is **512**, not 514. The real headroom is therefore `512 − 483 = 29`
tokens, held by nothing but the measured drift being small. If a future model has a tighter budget,
or a tokenizer drifts harder at a cut edge, the chunk silently overflows and **the PERF-01 failure
comes straight back** — an `Expand` error, i.e. a silent NER downgrade by default and a **hard 400
on every large request** under `NER_REQUIRED`. The one thing chunking exists to prevent.

**Fix.** Make the bound a bound. After re-tokenizing a chunk in `infer_chunked`, check its actual
token count against the model's usable limit and act on it rather than hoping: either re-split that
chunk with a smaller window, or (simplest) treat the overflow as the error it is and let the
existing fail-closed channel handle it — but *knowingly*, with a message that names the cause,
instead of surfacing a raw ONNX `Expand` error. Either way, correct the doc comment: 480 bounds the
**window**, not the **sequence**; the sequence is `window + specials + edge drift`.

**Test.** A pure unit test alongside `chunk_tests` cannot see this (it has no tokenizer). It wants a
`--features onnx`, `#[ignore]`d case in `tests/ner_perf.rs`: tokenize an adversarial multi-script
field, run `chunk_char_ranges`, re-tokenize every window, and assert each is within the model's
usable limit — the assertion that would have made the 481–483 drift visible instead of incidental.

> **Closed 2026-07-14 — the bound is now *checked*, at the one place every path goes through.**
>
> **The constants say what they mean.** `MAX_SEQUENCE_TOKENS` (a name that claimed to bound the
> *sequence* while only bounding the *window*) is split in two: **`MAX_WINDOW_TOKENS` = 480** (the
> planning window) and **`MODEL_MAX_TOKENS` = 512** (the model's usable length — XLM-R's 514
> `max_position_embeddings` minus RoBERTa's position-id offset of 2). The sequence is
> `window + specials + edge drift`, and only the second constant bounds *that*.
>
> **The ceiling is enforced, not hoped for.** `run_and_decode` — the **single choke point** the direct
> call *and* every re-tokenized chunk pass through — now clamps any sequence over `MODEL_MAX_TOKENS`
> and emits a kind-free `warn!` (a count, never the text). This is a safety valve, and it degrades the
> failure from *"the ONNX graph errors, so the whole field gets no NER (or 400s under `NER_REQUIRED`)"*
> to *"the tail of one window isn't scanned"* — which the next window's 32-token overlap re-covers
> anyway. Structured PII is unaffected either way.
>
> **The relationships between the constants are compile-time invariants.** `const _: () = assert!(…)`
> pins `MAX_WINDOW_TOKENS < MODEL_MAX_TOKENS` (drift needs headroom) and
> `CHUNK_OVERLAP_TOKENS < MAX_WINDOW_TOKENS` (a window must advance, or chunking wouldn't terminate).
> Get either wrong and the crate **does not build** — strictly better than a runtime test, and it was
> `clippy::assertions_on_constants` that pointed it out.
>
> **The drift is now asserted, not incidental** —
> `tests/ner_perf.rs::m5_r2_every_retokenized_window_stays_within_the_models_usable_length`
> (`--features onnx`, `#[ignore]`d) drives the **real** `chunk_char_ranges` (made `pub` for exactly
> this: a copy of the logic in the test would drift from the code it guards) with the **real**
> tokenizer over six adversarial fields — Chinese, Japanese, Cyrillic, combining-mark/zalgo,
> mixed-script, and a 4 000-char run of `あ` with no spaces at all. It **independently reproduces the
> reviewer's measurement** — worst re-tokenized window **481–483** tokens in every case, against the
> 512 ceiling — and asserts each window both chunks (non-vacuity) and stays under the limit. The
> clamp is a valve that must never fire; this is what makes sure it doesn't.

### M5-R3 — the chunk slice hard-indexes tokenizer offsets — the one place on the masking path that can panic on attacker input

**Severity: hardening (low — fails closed; not reproduced).**

`src/pii/onnx.rs:160`:

```rust
let chunk = &input[char_start..char_end];
```

`char_start` / `char_end` come from `Encoding::get_offsets()` — tokenizer-derived **byte** offsets
(the doc comment calls them "char offsets", which is a second, smaller inaccuracy: they are byte
offsets that *happen* to land on char boundaries). Indexing a `&str` with a byte range that is not
on a `char` boundary **panics**.

This module already does not trust that. `ner_decode::decode_entities` (`ner_decode.rs:72,92-98`)
guards the *identical* class of offset with `text.get(start..end)` and a `warn!` — added by
**M2-R6**, whose whole subject was tokenizer offsets landing off a boundary. `Vault::mask`
(`anonymizer.rs:156-168`) does the same with an explicit `is_char_boundary` check, and
`overlap::materialize` (`overlap.rs:150-156`) spells the rule out:

> Never a panic: this is a proxy, and the input is attacker-influenced.

The new chunk slice is the only spot on that path that breaks the rule. Consequence if it ever
fires: the stage panics inside `spawn_blocking`, and per ARCHITECTURE the request is **blocked**
(400) — so it **fails closed, and is not a leak**. It is an availability hole on an unauthenticated
path, of the M4-R19 family.

**I could not reproduce it.** 13 adversarial inputs through the real tokenizer (Chinese, Japanese,
Cyrillic, emoji/flags, combining marks, zalgo, mixed-script glue, 20 000-char single token, base64
runs) produced **zero** off-boundary window edges. So this is a latent trap, not a live bug — but it
is a trap the codebase has already been bitten by once (M2-R6) and has *already decided* how to
handle everywhere else.

**Fix.** Use the same guard the rest of the module uses — `input.get(char_start..char_end)`, and on
`None` either widen to `char` boundaries (`overlap::widen_to_char_boundaries` is right there) or skip
the window with a kind-free `warn!`. Skipping costs recall on one window; panicking costs the
request.

**Test.** `chunk_tests` can pin it without a model: feed `chunk_char_ranges` an offsets table whose
window edge falls **inside** a multi-byte char (the `fake_offsets` helper builds tables directly), and
assert `infer_chunked`'s slicing step does not panic — the same shape as
`a_union_ending_inside_a_multibyte_char_still_covers_every_constituent` (`overlap.rs`), which exists
for exactly this reason on the resolver side.

> **Closed 2026-07-14 — and closed with the guard the codebase already had, rather than a second one.**
>
> `chunk_char_ranges` now takes `input: &str` and widens every window it emits through
> **`overlap::widen_to_char_boundaries`** — the *same* function the resolver uses, for the *same*
> reason, promoted from private to `pub(crate)` with a note saying so. Widening only ever *adds* bytes,
> so it cannot shrink a window's coverage, and it makes every returned range **sliceable by
> construction**. That was the right shape for the fix: the reviewer's point was not "add a check here"
> but "this module already decided how to handle tokenizer offsets everywhere else (M2-R6, M4-R14) and
> this one spot breaks the rule" — so the fix is to *apply the existing rule*, not invent a parallel one.
>
> `infer_chunked` still refuses to index: it uses `input.get(start..end)` with a `debug_assert!` plus a
> kind-free `warn!` + skip in release — the same drop-never-leak-never-panic shape as `Vault::mask`'s
> malformed-span guard. Belt and braces, deliberately: the range is now correct by construction, but
> this is a proxy on attacker-influenced input and a panic costs the request.
>
> **Test:** `chunk_tests::every_window_is_sliceable_even_when_an_offset_lands_inside_a_multibyte_char`
> feeds an offsets table that deliberately cuts a 3-byte `€` and a 4-byte `𝄞` in half, and asserts every
> returned range is `input.get(..)`-able. **It carries its own non-vacuity assertion** — it first checks
> the offsets table *really does* land off a `char` boundary, because a guard that silently stopped
> exercising its hazard is precisely how M4-R13 and M4-R24 stayed invisible. Ask what the corpus holds
> constant.

### M5-R4 — the fixpoint's convergence proof covers the recognizers, not the NER — and chunking newly routes large fields through it

**Severity: invariant / docs (low-medium — fails closed; the *next* planned model is the one likely to break it).**

`ARCHITECTURE.md:125-128` (and the same argument in `anonymizer.rs:68-72`):

> `Vault::mask_all` therefore re-detects until the text yields nothing. It converges because a
> placeholder is **inert** (no recognizer can match `[KIND_N]` or span across it), so each pass
> strictly shrinks the un-masked text.

The parenthesis is the proof, and it is a proof about **regex recognizers** — `[KIND_N]` has no `@`,
no `sk-`, not enough digits, and `[`/`]` are outside every character class. Sound, by construction.

But `mask_all` is called with the **`CompositeDetector`**, and the NER inside it is an ML model
under no such constraint. Nothing prevents XLM-R from tagging `[PERSON_1]` (or a dense run of
placeholders) as a `Person`/`Organization`. If it did, a pass would mask a placeholder, the text
would not strictly shrink, `MAX_MASK_PASSES` would be exhausted, and the request would **400** —
fail-closed (M4-R20 saw to that), so **not a leak**, but a hard availability failure on ordinary
input.

This is not new to M5 — but M5 is what makes it *reachable at scale*: before `12c9ea8`, a field over
~500 tokens didn't run the NER at all (it errored). Chunking now routes exactly the large,
placeholder-dense fields through it that would exercise this path.

**I checked, and it holds — for this model.** The real XLM-R int8 detector over 2 520 bytes of
placeholder-only text (large enough to be chunked) tags **0 entities**; full-hybrid `mask_all`
converges on 412 B / 6.6 KB / 26 KB fields. So the system is correct today. What is missing is the
*statement* that this is an **empirical property of the chosen model**, not a construction proof —
and therefore a **model-swap checkpoint**.

That matters more than it sounds, because the Backlog's designated successor is **GLiNER**, a
*zero-shot, open-label, context-driven* span extractor. A model whose whole design is "match by
context against labels you pass at inference" is *unusually* likely to look at
`Contact [PERSON_1] at [ORG_1]` and tag both. Whoever evaluates GLiNER must re-run this check, and
right now nothing tells them to.

**Fix.** Write it down next to the invariant it qualifies (`ARCHITECTURE.md`, *Masking must run to a
fixpoint*): placeholder inertness is proved by construction for the **structured recognizers** and
verified **empirically** for the current NER (XLM-R int8: 0 entities on placeholder-only text); a
**new NER model must re-verify it**, and if it fails, the failure is a 400 (fail-closed), not a leak.
Mirror the one-liner in `anonymizer.rs::mask_all`'s doc comment, whose convergence argument has the
same gap.

**Test.** A `--features onnx`, `#[ignore]`d case (`tests/ner_perf.rs` or `ner_eval.rs`):
`detector.detect("Contact [PERSON_1] at [ORG_1] in [LOCATION_1] about [EMAIL_1]. ".repeat(40))` must
return **no** entities — i.e. the model treats placeholders as inert. It is one assertion, it runs
only when a model is configured, and it is exactly the check a model swap must not skip.

> **Closed 2026-07-14.** The qualification is now written down **next to the invariant it qualifies**,
> in all three places the invariant is stated: `ARCHITECTURE.md` → *Masking must run to a fixpoint*
> (the full argument, plus why GLiNER makes it urgent), and `Vault::mask_all`'s doc comment
> (`anonymizer.rs`), whose convergence argument had the identical gap. The claim is now precise:
> placeholder inertness is proved **by construction** for the deterministic recognizers and holds
> **empirically** for the current NER — making it a **model-swap checkpoint**, not a theorem.
>
> **Test:** `tests/ner_perf.rs::m5_r4_the_ner_treats_placeholders_as_inert` (`--features onnx`,
> `#[ignore]`d) asserts XLM-R tags **zero** entities across a 3 040-byte placeholder-only field (large
> enough to exercise the *chunked* path — the one M5 newly opened), and that the **full hybrid**
> `mask_all` reaches its fixpoint on it rather than exhausting `MAX_MASK_PASSES` into a 400. It passes.
>
> The failure mode it guards is worth restating, because it is the *opposite* of the usual one here:
> if a future model tags placeholders, nothing leaks — masking is **fail-closed**, so the request 400s
> (M4-R20). The cost is **availability**, on ordinary input. That is why this is a checkpoint and not a
> footnote: **GLiNER**, the Backlog's designated successor, is a *zero-shot, open-label,
> **context**-driven* extractor — a model whose entire design is "match by context against labels you
> pass at inference", i.e. exactly the kind that could read `Contact [PERSON_1] at [ORG_1]` and tag
> both. Whoever evaluates it now has a one-line test telling them so.

### M5-R5 — CI never exercises the declared MSRV

**Severity: low.**

`Cargo.toml:5-7` declares `rust-version = "1.82"` — the M4-R22 fix, whose stated purpose is "keeps
CI from picking an older toolchain that cannot compile the crate". But both CI jobs pin
`dtolnay/rust-toolchain@stable` (`.github/workflows/ci.yml:17,40`), so **nothing ever builds the
crate on 1.82**. `rust-version` only makes `cargo` refuse a *too-old* toolchain; it cannot detect
that the code has drifted *past* the declared floor. The day someone uses a 1.85 API, CI stays green
and the MSRV claim becomes fiction — which is the same failure the field was added to prevent.

ROADMAP's M5 section states "CI has its MSRV ([M4-R22](reviews/M4.md#m4-r22))" — true of the
manifest, not of CI.

**Fix.** Either add a third matrix leg pinned to the MSRV (`dtolnay/rust-toolchain@1.82`, `cargo
check` is enough — it need not run the suite), or drop the ROADMAP claim to what is true: the MSRV is
*declared*, not *verified*. Declaring-without-verifying is a defensible tradeoff for a solo project;
saying CI enforces it is not.

**Test.** The CI job *is* the test.

> **Closed 2026-07-14 — and it was not the small one. The declared MSRV was fiction.**
>
> The finding said `rust-version` "cannot detect that the code has drifted *past* the declared floor".
> It had. Rather than pick between the two offered fixes, I **measured** — and `1.82` cannot so much as
> *parse* the dependency tree:
>
> ```text
> $ cargo +1.82 check --all-targets
> error: failed to parse manifest at `…/idna_adapter-1.2.2/Cargo.toml`
> Caused by:
>   feature `edition2024` is required
> ```
>
> The **real** floors, measured per feature set (`cargo +<ver> check --all-targets [--features onnx]`):
>
> | build | declared | 1.85 | 1.86 | 1.89 | **true floor** |
> |---|---|---|---|---|---|
> | default | 1.82 | ✗ `icu_*` / `idna_adapter` need 1.86 | ✓ | ✓ | **1.86** |
> | `--features onnx` | 1.82 | ✗ | ✗ `redb` ← `hf-xet` needs 1.89 | ✓ | **1.89** |
>
> **The MSRV differs per feature set — which a single `rust-version` cannot express.** `Cargo.toml` now
> declares **1.86**, the floor of the *default* (shipped, native-dep-free) build, and documents that
> `--features onnx` needs **1.89**; building onnx on 1.86–1.88 fails with cargo's own explicit
> `redb@3.1.3 requires rustc 1.89`, which is self-explanatory. Declaring 1.89 instead would have lied in
> the other direction — refusing a perfectly good default build on 1.86.
>
> **Fix:** a new `msrv` matrix job in `.github/workflows/ci.yml` **builds** both floors
> (`dtolnay/rust-toolchain@master` pinned to `1.86` / `1.89`, `cargo check --all-targets`). `check` is
> enough — `test` runs on stable in the job above; this one answers only *"does it still compile on the
> oldest toolchain we promise?"*.
>
> **The lesson, and it is the M4-R22 lesson finally landing.** M4-R22 added `rust-version` *to prevent
> this exact failure*, and it structurally could not: the field makes cargo refuse a too-**old**
> toolchain, but nothing makes the *crate* stay compatible with it. A declared MSRV with no job building
> on it is not a floor — it is a comment that looks like a guarantee. **Only a job that builds on the
> MSRV can hold the MSRV.** The finding was filed `low`; it was really the round's most load-bearing

### Promoted to the design docs this round

One rule that is **already correct** in the code but was written down nowhere, and which the next
person to touch either chunking or `PiiKind::priority` needs:

> **Chunking's boundary fragments are cleaned up by the resolver, not by the `dedup()`.**
> `infer_chunked`'s `dedup()` removes only **exact** duplicates. A window that cuts an entity in
> half emits a *truncated* fragment (`Mil` where the neighbouring window sees `Milan`), which is a
> different span and survives it. What removes it is `overlap::resolve_overlaps`' NER phase: all
> three NER kinds share `priority() == 0`, so it tiebreaks on **span length, descending**, takes the
> whole entity first, and drops the fragment as overlapping. **This is load-bearing:** give
> `Person` a higher priority than `Location` and a truncated boundary fragment could outrank the
> whole entity it was cut from.

Added to `ARCHITECTURE.md` → *NER chunking (M5, PERF-01)*. The rest of this round's lessons are the
**fixes** for the findings above, and belong in ARCHITECTURE / TESTING when those findings close —
not here.
