the **record**: the full finding, the fix, the tests, and what it taught us.

> **Read the design docs first, not this archive.** Every conclusion here that still governs the code was
> promoted to [`../ARCHITECTURE.md`](../ARCHITECTURE.md) (the no-abandoned-bytes invariant, the

## Review 1 — first landing (2026-07-12) — sound, no blockers

Verified independently: **83 tests green (default) / 91 + 1 `#[ignore]`d (`--features onnx`), no
warnings**; `cargo build --features onnx` links `ort` clean.

The three-tier refactor holds — the universal recognizers (email / secret / card / IBAN / phone) are
byte-identical to the pre-M4 set and US SSN stays active by default, so **no M1/M1.5 regression**: the
IBAN-no-trailing-word, phone-no-over-match, Luhn and mod-97 guards all still pass. The new national-ID
regexes are word-boundary anchored on both ends, so a CF/NINO can't fire inside a longer alphanumeric
token (API key / hash / UUID / base64). No raw PII in logs; fail-closed posture unchanged.

**M3-R2 confirmed sound:** `demask_json_string` JSON-escapes the substituted value and is wired **only**
to the `arguments` fields (buffered `demask_response` + streaming `ToolArg`); `content` keeps the plain
`demask`; the round-trip is exact and `demask_json_string_keeps_inner_json_valid` is **non-vacuous** (it
asserts the plain path *would* produce invalid JSON).

<a id="m4-r1"></a>
### M4-R1 — `PII_LOCALES` gated the national IDs · design · **closed 2026-07-13**

**Finding.** National-ID recognizers were selected by `PII_LOCALES`, so a national ID that reached the
proxy from an unconfigured country was forwarded **in clear**. For a privacy tool recall beats precision —
*a miss is a leak*.

**Fix (Option A — always-on, privacy-first).** National-ID recognizers run **regardless of
`PII_LOCALES`** (`national_id_recognizers()`). `PII_LOCALES` is narrowed to gate only genuinely
**FP-prone** recognizers (e.g. national *phone* formats), via the `fp_prone_recognizers(code)` seam —
which is wired end-to-end but empty today, so `PII_LOCALES` is a documented no-op.

**Prerequisite: [M4-R2](#m4-r2).** An always-on *loose* recognizer over-masks globally, so the NINO had
to be tightened before this could land.

**Tests.** `national_ids_are_always_on` (LOC-01), `locale_selection_is_scoped`. Docs: SETUP §6,
ARCHITECTURE.

<a id="m4-r2"></a>
### M4-R2 — GB NINO over-match · precision · **closed 2026-07-13**

**Finding.** `\b[A-Za-z]{2}\d{6}[A-Da-d]\b` masks *any* 2-letter + 6-digit + A–D token — an order or
reference code like `PO123456A` becomes `[NATID_1]`. An over-mask on legitimate text, not a leak — but
under [M4-R1](#m4-r1)'s always-on policy it fires **globally**, so it had to be tightened first.

**Fix.** `nino_prefix_valid` implements the real HMRC prefix rules: 1st letter ∉ D/F/I/Q/U/V, 2nd ∉
D/F/I/O/Q/U/V, disallowed pairs BG/GB/KN/NK/NT/TN/ZZ, suffix A–D.

**Tests.** `uk_nino_prefix_rules_reject_lookalikes` (LOC-03) — `PO123456A`, `GB…`, `DA…` rejected; a
valid NINO still masks.

<a id="m4-r3"></a>
### M4-R3 — IT Codice Fiscale had no check character · precision · **closed 2026-07-13**

**Finding.** The CF regex accepted lowercase and skipped the **check character** (the final letter is a
checksum), so a wrong-checksum or lowercase look-alike was masked as `Verified`. FP risk was low
(anchored + a highly specific letter/digit interleave), but it was inconsistent with the other national
IDs, which are all checksum-gated.

**Fix.** `cf_check_valid` — the odd/even conversion table + mod-26 check character.

**Tests.** `italian_codice_fiscale_checksum_rejects_broken` (LOC-07).

<a id="m4-r4"></a>
### M4-R4 — ARCHITECTURE mis-grouped US SSN under `NationalId` · docs · **closed 2026-07-12**

**Finding.** `ARCHITECTURE.md` listed US SSN under `PiiKind::NationalId` / `[NATID_N]`. It isn't: US SSN
keeps its own `PiiKind::Ssn` / `[SSN_N]`. (`mod.rs` and `TESTING.md` were already correct.)

**Fix.** Corrected by the reviewer in that round's doc commit.

<a id="m4-r5"></a>
### M4-R5 — FR NIR missed the INSEE special months · recall (leak) · **closed 2026-07-13**

**Finding.** The NIR regex fixed the month field to `01–12` (`(?:0[1-9]|1[0-2])`), so a real NIR carrying
an INSEE **special month code** — `20` (birth month unknown / born abroad) or the provisional `30–42` /
`50–99` (SANDIA) ranges — never matched. On the always-on tier that is a **miss, i.e. a leak**.

**Fix.** The month alternation admits the special codes; the mod-97 key still gates precision (~1/97).

**Known limitation (documented, not fixed).** Corsica's `2A` / `2B` department puts **letters** in the
NIR body — the same class of gap. Noted in a code comment and here.

**Tests.** `french_nir_special_month_is_not_missed` (LOC-08).

## Review 3 — close-out (2026-07-13) — M4 genuinely complete, no blockers

Reviewed `a474da8` (recognizers + priority reorder + e2e) + `2da01c0` (docs) + `91e67af` (proptest seed).
Verified independently: **96 tests green (default), 0 failed, no warnings**; `cargo build --features onnx`
compiles **and** links `ort` clean.

**All checksum validators audited against the official algorithms — correct.** Hand-verified with an
official test number each: **DE Steuer-ID** ISO 7064 Mod 11,10 (`86095742719` → check 9 ✓); **NL BSN**
11-proef (`111222333` → weighted sum 66 ✓; `sum != 0` excludes all-zeros); **PT NIF** mod-11
(`123456789` → control 9 ✓); **zh Resident ID** ISO 7064 MOD 11-2 (`11010519491231002X` → 'X' ✓);
**IT CF** odd/even + mod-26 (`RSSMRA85T10A562S` → 'S' ✓, the full 26-entry ODD table matches); **ES
DNI/NIE** mod-23 and **FR NIR** mod-97 re-confirmed. The 9-digit recognizer masks only when BSN **or**
NIF accepts; the 11-digit only when DE **or** LV accepts.

**LV `32…` shape-only branch — a conscious, documented tradeoff.** It is the one always-on recognizer
with **no checksum** (any 11-digit starting `32` is accepted — the post-2017 randomized form has nothing
to verify). FP surface ≈ 1% of standalone 11-digit tokens, masked unconditionally. Acceptable under the
privacy-first rule.

**Priority reorder is safe** *(as assessed at the time — [M4-R9](#m4-r9) later proved this assessment
wrong; see [the retrospective](#retrospective))*. The only change is Email (2→3) crossing above
Ssn/NationalId (3→2). Email and Ssn/NationalId only overlap when the ID is a *substring of an email local
part*, where the email is the complete correct match.

**Priority fix found by proptest (during the builder's own close-out).** The numeric recognizers
(`\d{9}` / `\d{11}` / 18-digit) matched an email's numeric **local part**, and `NationalId` (then 3)
outranked `Email` (then 2) → the email was **fragmented**. Reordered to
`Secret6 > Iban5 > Card4 > Email3 > Ssn≈NationalId2 > Phone1`, with the guard
`numeric_email_local_part_is_not_hijacked_by_a_national_id` and a committed proptest seed
(`gj000000a@aa.aa`).

<a id="m4-r6"></a>
### M4-R6 — the pure-numeric national IDs over-mask ~18% of 9-digit tokens · accepted tradeoff · **closed 2026-07-13**

**Finding.** `\b\d{9}\b` (NL BSN ∪ PT NIF) accepts ≈ 2/11 ≈ **18%** of arbitrary 9-digit tokens on
checksum alone; `\b\d{11}\b` (DE ∪ LV, incl. the unconditional LV `32…` ≈ 1%) likewise. Always-on, so it
fires globally.

**Resolution — documented, deliberately NOT fixed.** The over-mask is **accepted**: it is fail-safe
(over-mask, never leak) and squarely inside the project's stated direction. Context-gating a national ID
on a nearby keyword would **reintroduce leaks** and directly contradict [M4-R1](#m4-r1) (*"a miss is a
leak"*). The clean precision path is the **contextual GLiNER detector (Backlog)**, not a regex keyword
gate. Recorded in code comments on both recognizers and in ARCHITECTURE.

**Tests.** `bare_numeric_national_ids_are_masked_by_design` (LOC-13) pins **both** halves: `524287244`
(an arbitrary PT-NIF-valid number) *is* masked by design, and `524287245` (fails both checksums) is left
in clear — so the checksum still filters the majority.

<a id="m4-r7"></a>
### M4-R7 — an email whose local part is a card/IBAN/secret gets fragmented · precision · **closed 2026-07-13, mechanism twice superseded**

**Finding.** `4111111111111111@x.com` masked as `[CARD_1]@x.com` — the `@domain` forwarded in clear.
Generalized from the numeric-ID case found by proptest in [review 3](#review-3): the same happens when an
email's local part is exactly a card, an IBAN, or a secret.

**Fix (original).** Make **`Email` the top structured priority**, on the premise that *"nothing else
structured carries `@`, so it can only overlap an email by **containment**."*

> ⚠️ **That premise was false, and the fix was a leak.** The email local-part class `[A-Za-z0-9._%+-]`
> **excludes the space**, so a *space-grouped* card or IBAN glued to a domain overlaps an email only
> **partially** — and a top-priority Email then discarded the whole card. See [M4-R9](#m4-r9). The
> mechanism was replaced twice (M4-R9's containment gate, then M4-R15's naming rule); the **asserted
> behaviour** below never changed and still holds.

**Tests.** `email_beats_a_card_iban_or_secret_local_part` (LOC-12) — `4111111111111111@x.com`,
`DE89370400440532013000@x.com`, `sk-abcdef123456@x.com` each mask as a single `Email`.

<a id="m4-r8"></a>
### M4-R8 — DE Steuer-ID missed the consecutive-triple rule · precision · **closed 2026-07-13**

**Finding.** `de_steuerid_valid` checked ISO 7064 Mod 11,10 and the "exactly one repeated digit in the
first 10" structural rule, but not the 2016+ refinement: a digit appearing three times must **not** sit in
three *consecutive* positions.

**Fix.** Enforce it. Pure precision gain, **zero recall cost** — a valid ID never has one.

**Tests.** `de_steuerid_rejects_a_consecutive_triple` (LOC-14) — self-verifying: the same digits with the
same valid Mod 11,10 check digit, differing only in placement; consecutive → rejected, non-consecutive →
accepted.

## Review 4 — the M4-R6/R7/R8 fixes (2026-07-13) — **one BLOCKER: the priority reorder leaks**

Reviewed `3845bfe` (fix) + `4de5d38` (docs). Verified independently: **99 tests green (default), 0

M4-R6 and M4-R8 are **sound**: `bare_numeric_national_ids_are_masked_by_design` genuinely asserts both

But M4-R7's Email-top reorder **introduces a real Card/IBAN leak**.

<a id="m4-r9"></a>
### M4-R9 — a space-grouped card/IBAN glued to a domain leaks · **BLOCKER — LEAK** · **closed 2026-07-13, mechanism later deleted**

**Finding.** [M4-R7](#m4-r7)'s premise — *"a card/IBAN/secret can only overlap an email by being a
substring of its local part"* — holds only for the **continuous** forms its test covered. The email
local-part class `[A-Za-z0-9._%+-]` (`recognizers.rs:104`) **excludes the space**. So when a
**space-grouped** card or IBAN is immediately followed by `@domain.tld`, the email match forms from **only
the last group** and *partially* overlaps the card — it does not contain it. `resolve_overlaps`
(`overlap.rs:25`) then settled the overlap by **dropping the whole lower-priority span**, and since
`Email` now outranked `Iban`/`CreditCard`, it **discarded the entire card**:

```text
card 4111 1111 1111 1111@example.com   →   card 4111 1111 1111 [EMAIL_1]
                                                  ^^^^^^^^^^^^^^ 12 Luhn-valid card digits, in clear
iban DE89 3704 0044 0532 0130 00@example.com → iban DE89 3704 0044 0532 0130 [EMAIL_1]
```

A **regression**: pre-M4-R7 the card won and masked whole (`[CARD_1]@example.com` — only the harmless
`@domain` in clear). Reproduced independently with a standalone copy of the regex + resolver. The
space-grouped **NINO** (`AB 12 34 56 C@x.com`) has the same shape and was a latent leak even *before*
M4-R7.

Continuous forms, dash-grouped cards (`-` is in the local-part class) and `sk-…` / `AKIA…` secrets (no
space) stay safe — the gap is exactly the space-grouped Card/IBAN/NINO.

**Fix (the recommended one, not the minimal revert).** Two complementary mechanisms:
1. an **Email containment gate** in `resolve_overlaps` (`drop_spans_contained_in_an_email`), run *before*
   the priority sort — a structured span lying **entirely inside** an Email span is a false decomposition
   of its local part and is dropped, so the email wins;
2. **`Email` moved to the lowest structured priority** (below `Phone`, above NER), so every *partial*
   overlap falls through to priority and the checksum-backed structured span wins.

Containment → Email wins; partial overlap → structured wins.

> ⚠️ **This fix was itself a leak, and the gate was later deleted.** It only chose *which side* of a
> partial overlap leaks — see [M4-R10](#m4-r10) / [M4-R11](#m4-r11), and
> [the retrospective](#retrospective). The gate is gone since [M4-R15](#m4-r15).

**Tests.** `grouped_forms_attached_to_a_domain_do_not_leak` (recognizers),
`grouped_pii_glued_to_a_domain_leaks_nothing` (`tests/adversarial.rs`, asserted on the **masked body**),
plus two resolver units. **Verified non-vacuous:** re-raising `Email` makes them fail.

## Review 5 — the M4-R9 fix (2026-07-13) — **two NEW BLOCKERS: the leak moved, it didn't go away**

Reviewed `5f31482` (fix) + `7d5668e` (docs). Verified independently: **103 tests green (default) / 111 +
1 `#[ignore]`d, no warnings** — both counts match the builder's claim exactly.

The **original M4-R9 leak is genuinely closed** — reproduced through `Vault::mask` (the bytes the upstream
actually receives): `card 4111 1111 1111 1111@example.com` → `card [CARD_1]@example.com`;
`iban DE89 …@example.com` → `iban [IBAN_1]@example.com`; `AB 12 34 56 C@x.com` → `[NATID_1]@x.com`. The
non-vacuity claim is true (verified in an isolated clone). Containment cases still hold.

**But the fix did not eliminate the leak class — it swapped which side of a partial overlap leaks.** The
root cause was untouched: `resolve_overlaps` settled every overlap by **dropping the whole loser span**,
so the loser's bytes were simply *abandoned in clear*. A flat `priority()` scalar can express *"one of
them wins"*; it **cannot** express *"**both** must be masked"*. M4-R7 made `Email` win and abandoned the
card; M4-R9 makes the structured span win and abandons the **email**.

<a id="m4-r10"></a>
### M4-R10 — the containment gate strands the span it deleted · **BLOCKER — LEAK** · **closed 2026-07-13**

**Finding.** `drop_spans_contained_in_an_email` (`overlap.rs:76`) drops a contained structured span
**unconditionally, before the priority sort** — but the containing `Email` is **not guaranteed to
survive** that sort. If a *third* span partially overlaps the email, the email loses on priority (it is
now the *lowest* structured tier) and is dropped too. The contained span, **already deleted by the gate**,
is then masked by **nothing at all**:

```text
555 867 5309.4111111111111111@x.com  →  [PHONE_1].4111111111111111@x.com   16 card digits in clear
555 867 5309.sk-abcdef123456@x.com   →  [PHONE_1].sk-abcdef123456@x.com    an API secret in clear (!)
555 867 5309.123456789@x.com         →  [PHONE_1].123456789@x.com          a NIF in clear
4111 1111 1111 1111.4111111111111111@example.com → [CARD_1].4111111111111111@example.com
```

Note the second one: `Secret` is the **highest**-priority kind, and the gate deleted it *before priority
was ever consulted*. The gate's own doc comment (`overlap.rs:74`) checked the **wrong direction** — it
reasoned that an email is never stranded, when the danger was a stranded **card**.

This directly violated the invariant that both `overlap.rs:41` (*"Structured PII is never lost either
way"*) and `ARCHITECTURE.md:74` (*"Fail-safe in both directions: PII is never left in clear"*) claimed
to hold.

**Fix.** See [the shared fix](#the-fix-union-merge) below.

<a id="m4-r11"></a>
### M4-R11 — a partial overlap abandons a real email's local part · **BLOCKER — LEAK** · **closed 2026-07-13**

**Finding.** The mirror image. Demoting `Email` to the lowest structured tier (`mod.rs:98`) means a
structured span that only **partially** overlaps a **real** email now wins and drops the *whole* email
span — leaving the part outside the structured span (its **local part**: a person's name or handle, plus
the domain) **in clear**. Reachable because the email local-part class includes `.` and `-`, which are
also phone separators:

```text
555 867 5309john.doe@example.com     →  [PHONE_1]john.doe@example.com     a complete, deliverable email
+39 333 1234567.mario.rossi@example.com → [PHONE_1].mario.rossi@example.com  name + domain in clear
AB 12 34 56 C.bob@x.com              →  [NATID_1].bob@x.com
```

Pre-M4-R7 `Email` outranked `Phone` and `Ssn`/`NationalId`, so the phone and NatID shapes are a
**regression**. And the NINO case is a pure **trade**, not a fix: it used to leak the NINO, it now leaks
the email.

*(A bare left-over `@domain.tld` is **not** PII and is accepted — `[PHONE_1]@x.com` is fine. A left-over
**local part** is not.)*

<a id="the-fix-union-merge"></a>
### The fix — replace the ranking with an invariant (`0ed0c7c`)

One change closes both. The resolver's governing rule became:

> **No structured span's bytes are ever abandoned.**

1. **Structured union-merge.** Overlapping structured spans collapse into their **union** (labelled by the
   highest-priority kind; ties → longest → incumbent). One sort-by-start sweep reaches the fixpoint — a
   merge can only extend the union rightwards, so it never creates an earlier overlap. It over-masks
   slightly (a bare `@domain` may land inside the placeholder) — **over-mask, never leak**.
2. **`resolve_overlaps` now takes the `input`**, because the union's `text` must be **re-sliced from the
   source**: `Vault` keys on `entity.text` and splices by `span`, so a merged union must mask and restore
   **verbatim**. A union wider than its winning candidate is honestly re-tagged `Confidence::Structural`.
3. **The containment gate stays and is now provably safe** — an email is never *dropped*, only absorbed
   into a union covering at least its own span. *(It was deleted outright a round later — see
   [M4-R15](#m4-r15) — once we noticed it never affected a **span**, only a **label**.)*
4. **NER keeps the whole-span drop** (M2-R7) — abandoning a `Person` remainder costs recall, never a leak.
5. **`PiiKind::priority` now ranks LABELS, not survivors.** A lower priority can no longer cost coverage.

**The test that encodes it — PROP-03** (`every_structured_candidate_byte_is_covered`): glue PII values,
including the grouped shapes, in arbitrary orders; assert **every raw structured candidate is fully
covered by some resolved span**, and that mask→demask is still exact.

**A per-byte invariant cannot be satisfied by picking a winner** — which is precisely why the two
priority-only fixes each passed their own hand-written case while leaking the other side. **Verified
non-vacuous:** with the union-extension disabled all 7 tests fail, and PROP-03 *independently
rediscovered* the M4-R11 leak, shrinking to `555 867 5309john.doe@example.com`. Its regression seed is
checked in (`proptest-regressions/pii/recognizers.txt`).

<a id="m4-r12"></a>

LOC-10 and the ROADMAP M5-Arabic note (*"`Email` outranks the numeric national IDs"* — it no longer does).
The asserted *behaviour* was unchanged in all three; only the stated **mechanism** was wrong.

**Fix.** Corrected by the reviewer in that round's doc commit.

## Review 6 — the union-merge (2026-07-13) — the overlap leak class is genuinely CLOSED; **one NEW BLOCKER elsewhere**

Reviewed `0ed0c7c` (fix) + `2985022` (docs). The **fourth** review of this overlap code. Verified
independently: **110 tests green (default) / 118 + 1 `#[ignore]`d, 0 failed**; a **from-scratch rebuild**
(`cargo clean -p` + `cargo check --all-targets`, both feature sets) emits **no warnings**.

**The invariant holds — I tried hard to break it and could not.**

- **All seven previously-leaking inputs are clean**, reproduced through `Vault::mask`. No card digit,
  IBAN group, NINO group, secret or email local part survives in clear, and every one round-trips exactly.
- **The fixpoint claim is correct.** `merge_structured` is textbook merge-intervals: sorted by start
  (ties → longest first), a candidate can only extend the running union rightwards, and a new group opens
  only when `candidate.start >= union.end` — so no later candidate can reach back into a closed group.
  Chains (A∩B, B∩C, A∩C = ∅) merge transitively; a fully-contained span is absorbed. One pass genuinely
  reaches the fixpoint.
- **No structured byte can be abandoned.** Enumerated **every** discard site: (1) the containment gate
  only drops a span contained in an `Email`, and an `Email` is *never* dropped; (2) the merge sweep drops
  nothing, it unions; (3) the NER drop only touches non-structured kinds — and `ner_decode::label_to_kind`
  can *only* return `Person`/`Organization`/`Location`, so no NER span can ever enter the structured
  partition; (4) no other dedup/filter exists.
- **Fuzzed the resolver itself**, not just the regexes: **500,000** randomized synthetic candidate sets
  (1–6 spans, arbitrary kinds incl. NER, arbitrary ranges, duplicates, containment, chains) straight into
  `resolve_overlaps` → **zero** violations of: output spans pairwise non-overlapping · every structured
  candidate fully covered by **one** output span · `entity.text == input[span]` · `demask(mask(x)) == x`.
- **Over-masking is provably bounded — no cap needed.** A union is the union of *candidate* intervals, so
  it can only ever cover bytes some recognizer already claimed as PII-shaped: it can **never** swallow
  ordinary prose (300k randomized trials with ordinary sentences interleaved: **0** non-candidate bytes
  absorbed). Widest union in 300k trials of glued real PII: **148 bytes / 8 candidates**, every byte of it
  PII-shaped.
- **PROP-03 is genuine and non-vacuous.** A reference implementation of the old drop-the-loser resolver
  leaves 3 uncovered candidates on the three canonical inputs, reproducing the historical outputs. The
  checked-in seed decodes to **exactly** the M4-R11 leak.

**But the review found a leak of a different class, outside the overlap code — pre-existing, not a
regression.**

<a id="m4-r13"></a>
### M4-R13 — the structured recognizers are **inert in CJK text** · **BLOCKER — LEAK** · **closed 2026-07-13**

**The worst leak in the project, and it was one character in every regex.**

**Finding.** Rust `regex`'s **`\b` is Unicode-aware**: a Han / Kana / Cyrillic / Greek / Arabic letter
**is** a word character. So there is **no word boundary between a CJK character and a digit** — and
Chinese and Japanese have **no inter-word spaces**, so the glued form is the *natural* way to write it,
not an evasion. Every `\b`-anchored recognizer (all 12 of them) was **completely inert** in CJK prose:

```text
我的信用卡号是4111111111111111   → matched NOTHING          16 Luhn-valid card digits, upstream in clear
密钥sk-abcdef123456              → matched NOTHING          an API secret in clear
我的身份证号是11010519491231002X → the zh Resident ID pack shipped in M4 NEVER FIRED in Chinese
账号DE89370400440532013000       → IBAN in clear
编号123-45-6789                  → SSN in clear
カード番号は4111111111111111です  → card in clear
Карта4111111111111111            → card in clear
```

The same values **are** masked the moment a space is inserted, which pins the cause precisely. This is
squarely inside the **declared M4 domain**: `zh` is one of the ten declared languages, ARCHITECTURE states
"structured PII is language-independent", and M4 shipped a zh Resident ID pack that never fires in
Chinese.

**Fix.** `(?-u:\b)` — an **ASCII** word boundary — on all 12 anchored recognizers. The anti-FP guarantee is
preserved **exactly**: an ID still cannot fire inside a longer *ASCII* token (`card4111111111111111`,
hashes, base64, UUIDs, `PO123456A`). Only a non-ASCII **letter** stops counting as part of a number.
`Email` and `Phone` needed no change (anchored by character classes, not `\b`).

**Why it survived four reviews — the real lesson.** `tests/corpus/pii_cases.json` contained **zero
non-ASCII characters**, and M4's "validate the declared domain" pass validated the **NER** on zh —
**never the structured recognizers**. The suite was ASCII-shaped, so an entire class of *total* failure
was invisible to it. Every review kept auditing the code we had tests for.

**Tests.** New corpus category `non_ascii_scripts` (CJK-01…05, JA-01, CYR-01 positives + 2 ASCII-token
negatives) + non-ASCII round-trips RT-05/RT-06, picked up automatically by the data-driven
`pii_corpus.rs`; `cjk_prose_does_not_hide_structured_pii` (unit);
`structured_pii_is_detected_in_cjk_and_cyrillic_prose` and
`ascii_token_anti_false_positive_guarantee_survives_the_ascii_boundary` (`tests/adversarial.rs`, on the
**masked body**). **Any new recognizer must now be exercised in a non-ASCII context.**

**Verified non-vacuous:** restoring `\b` makes the detector return `[]` on the Chinese card sentence, and
corpus CJK-01 + RT-05 fail with *"PII must be masked"* — the card really was going upstream in clear.

<a id="m4-r14"></a>
### M4-R14 — the merge's one fallback degrades *toward* the leak · hardening · **closed 2026-07-13**

**Finding.** `merge_structured`'s re-slice (`overlap.rs:141-155`) fell back to `None => winner` when
`input.get(union)` failed — i.e. it silently returned the **winning candidate's span alone, abandoning
every other constituent's bytes**. That is precisely the leak class the commit had just closed.

**Unreachable today** (all structured spans come from `regex` matches over the same `input`, hence always
on char boundaries), so **not a live leak** — but it is a booby trap in the exact code path the invariant
rests on, and the **Backlog GLiNER** detector would emit spans from a *model*, not a regex.

**Fix.** `materialize` first **widens the union out to the enclosing `char` boundaries** (clamped to the
input) — widening only *adds* bytes, so it can never abandon a constituent — which makes the re-slice
**total**. The remaining (now genuinely unreachable) `None` arm returns the **whole group unmerged**
rather than one span that drops constituents, guarded by a `debug_assert!` and a kind-only
`tracing::warn!`. **No panic** — this is a proxy and the input is attacker-influenced.

**Tests.** `a_union_ending_inside_a_multibyte_char_still_covers_every_constituent` — two overlapping
structured spans whose union endpoint falls *inside* a 3-byte `€`.

<a id="m4-r15"></a>
### M4-R15 — a `Secret` could be announced as `[PHONE_1]` · observability · **closed 2026-07-13 — and it deleted the containment gate**

**Finding.** In `555 867 5309.sk-abcdef123456@x.com` the containment gate deleted the `Secret` (it sits
inside the email's local part) *before* priority was consulted, so the union was labelled by the phone —
`[PHONE_1]`. **No leak** (the secret is masked), but the model is told `[PHONE_1]` stands for a phone when
it actually stands for a phone + secret + email blob, and the kind-only audit `debug!` **under-reports a
`Secret` as a `Phone`**.

**Fix — and a strict simplification.** Name the union by the highest-priority **raw** candidate it covers
(including ones the gate had dropped). Implementing that revealed **the gate was never needed**: an
enclosed span, if not deleted, simply **merges into** its enclosing email, giving the *identical* union.
The gate only ever affected the **label**.

So `drop_spans_contained_in_an_email` is **gone**, replaced by `name_of`: highest-priority raw candidate,
**except** when the union is *exactly* an `Email` span — a genuine email whose local part merely *looks*
like a card or ID (`4111111111111111@x.com`) keeps the `Email` label, preserving the
[M4-R7](#m4-r7)/[M4-R9](#m4-r9) behaviour every earlier review ratified.

**Deleting nothing also structurally removes the [M4-R10](#m4-r10) trap**: with no span deleted, no span
can be stranded.

**Tests.** `an_enclosed_secret_names_the_union_not_the_phone` and
`a_span_enclosed_by_an_email_is_still_covered_and_names_the_union` (resolver);
`a_span_enclosed_by_an_email_is_never_stranded` (recognizers) — `555 867 5309.sk-abcdef123456@x.com` now
resolves to a single span labelled **`Secret`**.

<a id="m4-r17"></a>
### M4-R17 — `find_iter` hides a real value from the candidate set · **LEAK** (pre-existing) · **closed 2026-07-13**

**The bug that hid *behind* the guard.**

**Finding.** `raw_candidates` drove each recognizer with `regex::find_iter`, which is **leftmost and
non-overlapping per recognizer**: after a hit it resumes at the match's **end**. A real PII value that
*starts inside* an earlier match of the **same** recognizer is therefore **never emitted as a candidate at
all** — and PROP-03's invariant (*"every raw candidate is covered"*) is then satisfied **vacuously** for
it. *The invariant is only ever as strong as the set it quantifies over.*

```text
4111 1111 1111 1111@123-45-6789-4111 1111 1111 1111
   →  [CARD_1]@[CARD_2] 1111
                       ^^^^^ the shifted window `6789-4111 1111 1111` happens to be Luhn-valid and
                             matches first, so the REAL trailing card is never a candidate
```

**Verified pre-existing:** reproduces byte-identically at `3e1aa07`, so it is not caused by the union-merge
commits — it is a limit of the **candidate-generation** layer, not of the resolver.

**Fix — and note the reviewer's own suggestion would not have worked.** The suggested *"re-scan the
uncovered gaps"* fix does **not** close its own repro: the gap is ` 1111`, and the hidden card *starts
inside the covered region*, so no amount of gap re-scanning surfaces it. Verified before implementing.
The leak is in candidate generation, so that is where it is fixed:

**`Recognizer::push_candidates` resumes one `char` past each match's *start*, not its end.** Overlapping
hits of one recognizer are **coalesced into maximal runs** as they are found, which bounds the candidate
set on pathological input (a long row of 4-digit groups matches at every boundary) at no cost to coverage —
the resolver would union those spans anyway. Each hit is still validated (Luhn / checksum) **before**
joining a run.

> ⚠️ This fix is what introduced the O(n²) DoS — see [M4-R19](#m4-r19).

**And PROP-04, added as asked, found a live leak on its first run.**

```text
4111111111111111555 867 5309   the card and phone form ONE 19-digit run, not Luhn-valid, so the card
                               is correctly NOT a candidate (an ID never fires inside a longer token)
4111111111111111[PHONE_1]      masking the phone SPLIT the run and EXPOSED a clean, Luhn-valid card
                               — upstream, in clear
```

**Masking rewrites the bytes around what it replaced, and a value is only recognizable in context.** So
**`Vault::mask_all` masks to a fixpoint** — re-detect until the text yields nothing, wired into
`PrivacyStage`. It converges because a placeholder is **inert** (no recognizer can match `[KIND_N]` or
span across it); `MAX_MASK_PASSES` is a safety bound; the round-trip stays exact.

**Tests.** `a_value_hidden_behind_an_earlier_match_is_still_a_candidate`,
`masking_a_phone_must_not_expose_a_card` (recognizers);
`a_value_hidden_behind_an_earlier_match_is_not_left_in_clear` (`tests/adversarial.rs`, on the masked
body); and **PROP-04 `masking_leaves_nothing_detectable`** — re-run the detector on the masked output, it
must find nothing. PROP-04 is the right companion to PROP-03: PROP-03 quantifies over the *candidate set*,
PROP-04 over the **output bytes**, which no candidate-generation gap can hide. Seed checked in.

**Verified non-vacuous:** restoring `find_iter` semantics drops the real trailing card from the candidate
set and the repro fails.

## Review 8 — the M4-R16/R17/R18 fixes (2026-07-13) — correctness sound, but a **DoS regression** + a latent fail-open

Reviewed `0c7193b` (fix) + `e3f6017` (docs) + `190d283` (seed). Verified independently: **127 passed / 1
ignored** under `--features onnx`, **zero warnings** on both feature sets.

The M4-R17 fix is real and **non-vacuous** (proven by source mutation): reverting `find_at` + `start()+1`
to `find_iter` semantics reproduces the exact `[CARD_1]@[CARD_2] 1111` leak, and the fixpoint alone does
**not** save it (the leftover ` 1111` is not independently detectable) — so **both** mechanisms are
load-bearing. Round-trips are exact; **NER does not corrupt them** (falsified the hypothesis that it
might: XLM-R int8, run live, never labels or spans a `[KIND_N]` placeholder, in bare form or in
IT/EN/FR/DE/ES/CJK prose → no nested placeholders). No FP regression; the `Confidence` downgrade on a
coalesced run is a non-issue (its only consumer is a kind-only `debug!`).

**But the new candidate scan is quadratic and runs inline on the request thread.** The findings below are
**the four open items of M4** — see the ledger in [`../ROADMAP.md`](../ROADMAP.md).

<a id="m4-r19"></a>
### M4-R19 — algorithmic-complexity DoS in the overlap rescan · **BLOCKER — OPEN**

**A regression introduced by `0c7193b` (the [M4-R17](#m4-r17) fix).**

**Finding.** `Recognizer::push_candidates` (`src/pii/recognizers.rs`) resumes `regex.find_at` at
`m.start()+1` after **every** hit. For the two **unbounded-length** recognizers — the Email local part
`[A-Za-z0-9._%+-]+@…` and Secret `sk-[A-Za-z0-9_-]{6,}` — that is **O(n) start positions × O(n) match
length = O(n²)**.

Measured (release build), input `"a"*N + "@b.co"`:

| N | HEAD | at `6c68150` (pre-fix) |
|---|---|---|
| 16k | 982 ms | ~2 ms |
| 50k | 9.5 s | — |
| 100k | 37 s | — |
| 200k | **151 s** | ~8 ms |

~18,000× at 200 KB, and doubling N quadruples the time — textbook O(n²). `"sk-"*100k` → **135 s** vs 18 ms
(~7,500×).

**Why it's exploitable.** The default body limit is **16 MiB with no per-field cap**
(`DEFAULT_MAX_BODY_BYTES`, `config.rs:50`), so a single ~1–2 MB `content` field — trivially under the
limit — pegs a core for **minutes**. Masking runs **synchronously inline** on the tokio worker
(`server.rs:251`, no `spawn_blocking`) and `mask_all` calls `detect()` ≥2×, so a handful of concurrent
such requests exhaust the executor and **the proxy stops serving**. This is **unauthenticated** — masking
precedes any upstream auth.

Bounded-length recognizers (card / phone / IDs) stay linear. The blowup is specific to the two unbounded
patterns — which is also why the overlap rescan buys them **no coverage**: a value hidden inside an
Email/Secret match merges into the same coalesced run regardless.

**Fix (suggested).** Bound the overlap rescan — either resume at `run.end` for unbounded recognizers and
do the `start()+1` rescan only within a window of the recognizer's max plausible match length (card ≈ 19,
ID ≈ 18 chars), or tag recognizers `overlap_scan: bool` and leave Email/Secret on plain `find_iter`.
Independently: move masking to `spawn_blocking` and/or add a **per-field size cap**.

**Test.** `detect()` and `mask_all` on `"a"*1_000_000 + "@b.co"` and `"sk-"*350_000` must complete in well
under a few hundred ms — a guard that fails on O(n²).

<a id="m4-r20"></a>
### M4-R20 — `mask_all` fails **open** on pass exhaustion · low-medium — **OPEN**

**Finding.** After `MAX_MASK_PASSES` the loop returns `current` **with no final re-detect**
(`src/pii/anonymizer.rs:83-95`), so any PII still present is **forwarded in clear** — which contradicts
the project's fail-closed bar.

The claim in `ARCHITECTURE.md` and the code comment — *"hitting it can only mean over-masking … not a
leak"* — is **unproven**: *"each pass strictly shrinks the un-masked text"* guarantees **eventual**
convergence, not convergence **within 4 passes**.

**Not shown reachable.** An exhaustive search over 314,432 glued inputs (plus handcrafted 5-value chains)
never exceeded **2** passes, because masking *fragments* a digit run rather than peeling it, keeping
exposure depth tiny. So this is a **latent** fail-open, not a demonstrated leak.

**Fix.** After the loop, one final `try_detect(&current)`; if it returns anything, return
`Err(DetectError)` so `PrivacyStage` **blocks** (fail closed). Keep the `warn!`. **Correct the
ARCHITECTURE sentence** (still uncorrected — deliberately, so the doc matches the code until this lands).

**Test.** A synthetic detector whose masking always re-exposes one entity → `mask_all` must return `Err`,
not forward.

<a id="m4-r21"></a>
### M4-R21 — `mask_all` runs the detector ≥2× · perf note — **OPEN**

**Finding.** `mask_all` runs the detector **≥2×** on every PII-bearing request (one to mask, one to
confirm the fixpoint). Under NER this roughly **doubles inference**: a single `detect()` is **64 ms** vs a
full `mask_all` at **127 ms** (1.99×, 20 iterations, XLM-R int8).

Inherent to the fixpoint design and **acceptable for correctness**. Not a bug. Fold into M5's perf
harness. Possible later optimization: skip the confirmation pass when the last `mask` changed no bytes
adjacent to un-masked digits.

<a id="retrospective"></a>
## Retrospective — one bug, five rediscoveries

M4-R7 → M4-R9 → M4-R10/R11 → M4-R13 → M4-R17 are not five bugs. They are **one bug seen from five angles**,
and each "fix" that only re-ranked the priorities **relocated the leak instead of closing it**:

| Round | "Fix" | What actually happened |
|---|---|---|
| M4-R7 | `Email` becomes top priority | the **card** now leaks on a partial overlap |
| M4-R9 | `Email` becomes lowest + a containment gate | the **email** now leaks on a partial overlap; the gate can strand what it deleted |
| M4-R10/R11 | **invariant, not ranking** — union-merge | ✅ the class is closed |
| M4-R13 | — | the same regexes were **inert in CJK** all along; the corpus couldn't see it |
| M4-R17 | — | the *candidate generator* hid values, so the invariant passed **vacuously** |

Four lessons, all hard-won, all now recorded in
[`../ARCHITECTURE.md`](../ARCHITECTURE.md) and [`../TESTING.md`](../TESTING.md) next to the code they
govern — this archive is not their home:

1. **When a bug is "who wins an overlap", check whether the loser's data is silently discarded.** If a fix
   only re-ranks, it **relocates** the leak. Encode the safety property as a **per-item / per-byte
   invariant test**, not a hand-written example — examples confirm the case you thought of; invariants
   catch the one you didn't.
2. **A test corpus has a shape, and that shape is a blind spot.** Ours was 100% ASCII, so a *total*
   detection failure in CJK was invisible for four reviews. Ask what the corpus **cannot express**
   (script, encoding, length, locale), not just what it covers.
3. **An invariant is only as strong as the set it quantifies over.** PROP-03 quantified over the
   *candidate set*, so a value the recognizers never emitted satisfied it **vacuously** — the bug hid
   *behind* the guard. Always add a companion property that quantifies over something the bug cannot hide
   behind: here, the **output bytes** (PROP-04). It found a live leak on its first run.
4. **A transform can create the very thing it removes.** Masking rewrites surrounding bytes, and a value
   is only recognizable *in context* — so masking can **expose** PII that was undetectable before. Any
   context-sensitive scrubber must run to a **fixpoint**, not a single pass.
