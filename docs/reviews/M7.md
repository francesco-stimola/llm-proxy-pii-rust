### M7-R1 — the headline "2.17 s" and the executable bar measure `NER_POOL_SIZE=1`, which the server does not default to · measurement · **open**

**Finding.** M7's deliverable is a number, and the number the milestone reports is not the number the
product ships with.

`tests/m7_latency.rs:436` defaults the pool to **1**:

```rust
let pool = std::env::var("NER_POOL_SIZE").ok().and_then(|s| s.parse().ok()).unwrap_or(1);
```

`src/server.rs:163` defaults it to **2**:

```rust
let pool_size = std::env::var("NER_POOL_SIZE").ok().and_then(|s| s.parse().ok()).unwrap_or(2);
```

So `build_hybrid()` → `pool=1` → `default_intra_threads(1)` = **12**, while the shipped server →
`pool=2` → `default_intra_threads(2)` = **6**. **PERF-M7-01 — the test that makes M7's bar
executable — never runs the configuration `server.rs` produces.**

The divergence is deliberate and documented in the harness (*"the shape M7 measures against: the
personal proxy… one session, the whole box"*), and as a *choice of what to optimize* it is defensible —
M7 exists for the concurrency ≈ 1 case. The defect is that the resulting number is then reported as the
**default's**:

- `ROADMAP.md:553` — *"**Met: 2.17 s** with the derived thread default"* …
- `ROADMAP.md:561` — *"latency 4.58 s → **2.85 s** (1.61×)"*, describing **the same default**.

Both sentences are in the same milestone section and cannot both be true. `2.17` is `pool=1, intra=12`;
`2.85` is `pool=2, intra=6`, which is what an operator who sets nothing actually gets. The status row
(`ROADMAP.md:38`) then carries `2.17 s` unqualified as the product figure, and `TESTING.md:512` records
PERF-M7-01 as *"masked … as production does … Measured **2.17 s**"* — true of the *walk*, false of the
*config*. **`README.md:163-167` / `README.it.md:164-168` get this exactly right** (both rows, both
labelled), so the ledger currently contradicts the README.

**Three consequences, in increasing order of how much they matter.**

1. **The guard guards the wrong thing.** `assert!(turn.as_secs_f64() < 3.0)` has ~28% headroom against
   2.17 s. The shipped default sits at 2.85 s — **5% headroom** — and *nothing asserts it*. A future
   change that costs the default 10% ships green.
2. **The 20–40 KB caveat is extrapolated from the un-shipped shape.** DEVLOG:204-205 says the top of the
   range gives *"~3.7 s (personal shape)"* — and labels it, honestly. But 2.85 s × (40/22.3) ≈ **5.1 s**
   is the sentence for the shipped default, and it appears nowhere. "Over the bar by 23%" and "over the
   bar by 70%" are different messages.
3. **The CC battery will run at the default.** `MANUAL_VERIFICATION.md` never mentions `NER_POOL_SIZE`,
   so the human closing M7's last box gets 2.85 s/turn, not the *"~2.2 s"* TESTING.md:674 promises them.
   (Harmless for the battery's runtime; it is the same conflation.)

**Repro.** Three runs of `m7_s1_how_much_of_the_box_can_one_request_use` on this box, `2×6` (the shipped
default) vs `1×12` (the measured shape): `2203/2194`, `2342/2519`, `2338/2379` ms — **a tie**. So on my
box the gap the docs report (2847 vs 2092, 36%) does not reproduce at all; the two shapes perform the
same. That does not weaken this finding, it re-points it: *which* number is right is box-specific, but
*which configuration the guard measures* is not.

**Fix.** Make the harness mirror the server, and let the sweep carry the personal shape:
- `build_hybrid()` → `.unwrap_or(2)`, matching `server.rs:163`, so the bar assert guards the **shipped**
  config. The `pool=1` rows already exist in PERF-M7-03's sweep, which is where that shape belongs.
- Wherever a turn latency is quoted, name its shape. `ROADMAP.md:38` and `:553` should carry the
  **default's** number (2.85 s on the reference box) — the README's two-row table is the model.
- Re-derive the 40 KB extrapolation from the default, or state both.

**Test.** PERF-M7-01's `build_hybrid()` must not be able to drift from `server.rs`'s default again. The
cheap version is the `.unwrap_or(2)` above plus a comment tying it to `server.rs`; the version that
cannot drift is to assert the bar for **both** shapes (parametrize the existing test over
`[(2, derived), (1, derived)]` and assert `< 3 s` on each), which also documents the trade in the one
place that fails when it stops being true.

### M7-R2 — the sweep draws settled conclusions from n=1 measurements, and the SMT conclusion does not replicate · measurement · **open**

**Finding.** `m7_s1_how_much_of_the_box_can_one_request_use` runs **one warm-up turn and one measured
turn per configuration** (`tests/m7_latency.rs:638-639`). Three of its rows became stated conclusions in
DEVLOG:184-189 and were escalated in ROADMAP:576-580 — including this one:

> **"SMT may hurt; 6 may beat 12." It does not** — 12 logical threads beat 6 (2.09 s vs 2.46 s).
> Hyperthreading helps this int8 model. ***Both* of the "measure, don't reason" items resolved against
> the intuition that was written down.**

**It does not replicate.** Three independent re-runs, `1×6` vs `1×12`:

| run | `1×6` | `1×12` | winner |
|---|---|---|---|
| builder's, on record | 2,462 | 2,092 | 12, by 18% |
| mine #1 | **1,946** | 2,194 | **6, by 11%** |
| mine #2 | 2,717 | **2,519** | 12, by 8% |
| mine #3 | **2,311** | 2,379 | **6, by 3%** |

The sign flips run to run. And the **same configuration** (`1×6`) spans 1,946–2,717 ms across my three
runs — a **39% spread**, more than double the 18% effect the conclusion is read off. The measurement
design cannot distinguish the claim from noise, so the honest status of the SMT question is
**unresolved**, not *resolved against the intuition*. The write-up's rhetorical high point — *both*
"measure, don't reason" items resolved against intuition — rests on the one row that doesn't hold.

This is load-bearing, not trivia: `default_intra_threads` divides `available_parallelism()`, i.e. the
**logical** count. That divisor is the right choice *if* SMT helps. If SMT is neutral here — which is
what four runs actually show — then the base of the derivation is an open question the milestone
believes it closed.

**What does replicate, and should be kept exactly as written** — I checked each:
- **The pool is inert at concurrency 1.** `2×1` ≈ `1×1` in all three runs (4205/4214, 5595/5312,
  5248/5280). The S1a correction is solid.
- **Scaling is sublinear.** 12 threads bought 1.92× / 2.22× / 2.21× (claimed: 2.19×). Solid.
- **`pool=1` costs throughput.** I measured 0.504 vs 0.642 turns/s = **−21%** (claimed −23%). Solid —
  and this is the one that refuted the builder's own prior "it is not a trade at all", so it earns its
  place in the write-up.

**Also does not replicate:** the `2×6` vs `1×12` latency gap (docs: 2,847 vs 2,092, 36%; mine: a tie in
all three runs — see [M7-R1](#m7-r1)). Which means `README.md:170-172`'s *"set `NER_POOL_SIZE=1`: it is
the lowest-latency **and** lowest-RAM shape"* rests, on the latency half, on a gap I cannot reproduce.
**The RAM half is sound and independent** (each session holds its own copy of the weights — that is
arithmetic, not a benchmark), so the recommendation survives; its stated *reason* should lead with RAM.

**Fix.**
- Demote the SMT row to **unresolved / box-specific** in DEVLOG:188 and ROADMAP:578, and drop the
  "*both* items resolved against intuition" framing — one did (`pool=1` is not free), one didn't.
- Keep the three claims that replicate; they are the sweep's real output.
- Add the reference box's run-to-run spread next to the tables, so a future reader knows an 18% delta on
  this harness is inside the noise.
- `README.md:170-172`: lead the `NER_POOL_SIZE=1` recommendation with RAM; qualify the latency half.

**Test.** PERF-M7-03 should repeat each configuration **≥3×** and print **min and median**, not a single
sample. Minimum is the more meaningful statistic for a latency benchmark on a noisy box (it is the
closest to the interference-free cost), and printing the spread is what makes the "is this real?"
question answerable from the harness's own output instead of from a second reviewer's re-runs. That is
the guard that would have caught this: with three reps, the SMT row would have printed as a tie and
never become a conclusion.

### M7-R3 — nothing pins `intra_threads`' inertness w.r.t. detection, and every recall guard pins `intra=1` · invariant · **open**

**Finding.** M7's whole safety argument is *"`intra_threads` is purely a performance knob"*. That claim
is **true** — I verified it (below) — and it is **asserted by no test**, because the two harnesses that
could notice deliberately hold the knob at its pre-M7 value:

```rust
// tests/ner_eval.rs:131-133
// pool=1, intra=1: this harness scores *recall*, not latency — pinning both knobs keeps a
// score reproducible across boxes with different core counts.
let ner = OnnxNerDetector::load(&model, &tokenizer, id2label, 1, 1, needs_tt)

// tests/ner_perf.rs:40-43
// pool=1, intra=1: these guards measure *recall* and *pass counts*, not wall clock, so they
// pin the historical single-threaded shape rather than inheriting M7's derived default …
OnnxNerDetector::load(&model, &tokenizer, id2label, 1, 1, false)
```

The reasoning is **good** — a recall score that moves with the runner's core count is worthless — and
the consequence is that **the knob production just changed is the one every recall guard holds at its old
value**. The M5-R4 placeholder-inertness guard and the chunking guards all pass, and would pass
identically if `intra > 1` mangled every span, because they never run with `intra > 1`.

**Why this is not paranoia.** ONNX Runtime's intra-op parallelism repartitions GEMM and reduction work
across threads; floating-point addition is not associative, so a different partition can change a logit
in its last bits. The BIO decode is a **per-token `argmax`** (`ner_decode`), so a near-tie between two
labels can flip on nothing but thread count — and a flipped `B-PER` is lost recall, which in this repo
is the thing a miss makes into a leak. This is precisely [M5-R4](M5.md#m5-r4)'s shape: *the convergence
proof covers the recognizers, not the NER; inertness is **empirical** for the model, and a model swap must
re-check it.*

**Verified (reviewer's throwaway probe, outside the repo — a path-dep binary on the lib with `--features
onnx`).** 21 inputs lifted from `tests/corpus/ner_cases.json`, plus a >512-token input (to exercise the
chunked path, where a window-boundary decision is most likely to differ), plus the M7 system-prompt
paragraph that produces the `("An", Organization)` hit. Fingerprinted every detection as
`(kind, span.start, span.end)` at `pool=1`, `intra ∈ {1,2,3,4,6,8,12}`:

```text
intra= 1 (the shape every recall guard pins): 171 entities
intra= 2: 171 entities, 0 inputs differ from the intra=1 baseline  [IDENTICAL]
intra= 3: 171 entities, 0 inputs differ from the intra=1 baseline  [IDENTICAL]
intra= 4: 171 entities, 0 inputs differ from the intra=1 baseline  [IDENTICAL]
intra= 6: 171 entities, 0 inputs differ from the intra=1 baseline  [IDENTICAL]
intra= 8: 171 entities, 0 inputs differ from the intra=1 baseline  [IDENTICAL]
intra=12: 171 entities, 0 inputs differ from the intra=1 baseline  [IDENTICAL]
```

**Byte-identical, spans included, at every thread count.** So: **no regression, and the milestone's claim
stands.** This finding is about the *guard*, not the code.

**Why it still matters.** The property is empirical, not structural, and two scheduled Backlog items would
invalidate it silently:
- **A different execution provider** (*GPU optimization → DirectML/CUDA* — the natural next step on this
  box) is where cross-thread-count non-determinism is genuinely *likely*, not merely possible.
- **A model swap** (*Evaluate GLiNER*) re-opens it, exactly as M5-R4 says.

Today the only thing standing between either of those and a silent recall change is a reviewer happening
to run this probe again.

**Fix.** Promote the rule to where it governs, per CLAUDE.md's *promote what outlives the review*:
- **`ARCHITECTURE.md`**, in the new *NER threading* section: **`NER_INTRA_THREADS` changes performance
  only. That it does not change *detection* is empirical — verified on XLM-R int8 + the CPU EP, identical
  spans at intra 1…12 — not guaranteed by the runtime. A model change or an execution-provider change must
  re-verify it.** Put it next to M5-R4's neighbouring rule; they are the same lesson about the same layer.
- **`TESTING.md`**, next to THREAD-01: say plainly that the recall guards pin `intra=1` *on purpose*, and
  that the inertness of `intra > 1` is therefore covered by the guard below and nothing else.

**Test.** An `#[ignore]`d live guard in `ner_perf.rs` — the file that already owns the live-NER guards:
detect the `ner_cases.json` inputs (plus one chunked input) at `intra=1` and at
`intra=available_parallelism()`, assert the `(kind, start, end)` sets are **identical**. ~15 lines, needs
no new fixture, and it is the test that turns "a reviewer checked once in July 2026" into something a
DirectML EP swap trips over.

### M7-R4 — THREAD-01's oversubscription assert exempts the one regime where the product *does* exceed the box · test-quality · **open**

**Finding.** `src/pii/onnx.rs:487-497`:

```rust
fn the_two_knobs_multiply_to_at_most_the_box() {
    // Anything that lets the product exceed the core count is the oversubscription this
    // derivation exists to prevent (12 cores, intra=12, pool=2 → 24 threads …).
    for cores in [1usize, 2, 4, 6, 8, 12, 16, 64] {
        for pool in [1usize, 2, 3, 4, 8] {
            let intra = derive_intra_threads(pool, cores);
            assert!(intra >= 1, …);
            assert!(pool * intra <= cores.max(pool), …);   // ← the escape hatch
```

Work the two regimes:
- **`pool ≤ cores`**: `intra = floor(cores/pool)`, so `pool * intra ≤ cores`, and `cores.max(pool)` **is**
  `cores`. The assert says what its name says, and holds. ✔
- **`pool > cores`**: `intra` clamps to 1, product = `pool`, and `cores.max(pool)` widens to **`pool`** —
  so the assert reads `pool <= pool` and passes **while `pool` threads run on `cores` cores**. `pool=8,
  cores=2` → 8 threads on a 2-core box: real oversubscription, asserted green, by a test named
  `the_two_knobs_multiply_to_at_most_the_box` and commented *"anything that lets the product exceed the
  core count is the oversubscription this derivation exists to prevent"*.

**The assert is not vacuous** — I checked this specifically, since it is the obvious suspicion. In the
`pool > cores` regime it still pins `intra == 1` (any `intra ≥ 2` would make `pool*intra > pool` and
fail), so the test does have teeth in all 40 pairs. The problem is narrower and more interesting: the
`.max(pool)` term encodes a **real and unavoidable exception** — the derivation *cannot* fix `pool >
cores`, because `intra` floors at 1 and nothing clamps `NER_POOL_SIZE` — and it encodes it **silently**,
in a way that contradicts the comment three lines above it and the name three lines above that.

This propagates: `ARCHITECTURE.md:509-511` states the invariant **unconditionally** — *"the invariant is
that the product fits the box"* — which is false for `NER_POOL_SIZE > cores`, an env var an operator can
set to anything. (Not a new risk: `NER_POOL_SIZE` has been unclamped since M2, and a silly pool hits the
~400 MB-per-session RAM wall long before the thread wall. But M7 is the milestone that *declares* this
invariant, so M7 owns stating its domain.)

**Fix.**
- `ARCHITECTURE.md`: state the bound and its domain — *the derivation bounds `pool × intra` by the core
  count **while `pool ≤ cores`**; beyond that `pool` alone oversubscribes and nothing clamps it, because
  `intra` cannot go below 1. `NER_POOL_SIZE > cores` is an operator error the proxy does not defend
  against.*
- The test: either rename it to what it proves (`derived_intra_never_oversubscribes_beyond_the_pool_itself`)
  or — better — split the regimes and make the exception explicit: assert `pool * intra <= cores` for
  `pool <= cores`, and assert `intra == 1` for `pool > cores`, with the comment saying why that is the
  best available. Same coverage; the test then *documents* the limit instead of hiding it inside a `max`.

**Test.** This *is* the test. The change above is the fix.

### M7-R5 — `NER_POOL_SIZE=0` isn't filtered like `NER_INTRA_THREADS=0`, and the startup log then names a pool the process doesn't have · observability · **open**

**Finding.** M7 added the new knob with a careful `0`-guard and a comment explaining exactly why
(`src/server.rs:167-172`):

```rust
let intra_threads = std::env::var("NER_INTRA_THREADS")
    .ok().and_then(|s| s.parse::<usize>().ok())
    .filter(|n| *n > 0)                              // 0 = unset, never ORT's "pick for me"
    .unwrap_or_else(|| crate::pii::onnx::default_intra_threads(pool_size));
```

…and left the adjacent, older knob asymmetric (`src/server.rs:160-163`):

```rust
let pool_size = std::env::var("NER_POOL_SIZE")
    .ok().and_then(|s| s.parse().ok())
    .unwrap_or(2);                                   // ← no `.filter(|n| *n > 0)`
```

**The behaviour is safe** — I traced it, and it is safe *by two independent accidents*, which is worth
saying out loud. `NER_POOL_SIZE=0` → `pool_size = 0` → `default_intra_threads(0)` survives only because
`derive_intra_threads` does `pool_size.max(1)` (`onnx.rs:139`) → `12`; and `load` clamps the pool
`0 → 1` (`onnx.rs:180`) in a **shadowed local**. Effective shape: `1 × 12`. Correct.

**The log is not.** `server.rs:220`:

```rust
tracing::info!(model, pool_size, intra_threads, "ONNX NER detector loaded");
```

`pool_size` here is the **unclamped** outer binding — `load`'s clamp is a shadow inside `load`. So
`NER_POOL_SIZE=0` prints `pool_size=0, intra_threads=12` while the process runs one session with twelve
threads. That line exists *because* M7 made `intra_threads` derived — its own comment says *"an operator
debugging latency must be able to see what was picked without reproducing the arithmetic"* — and in this
case the operator reads a pool of `0`, an intra of `12`, and cannot reconcile them with
`intra = cores/pool` by any arithmetic at all.

**Fix.** `.filter(|n| *n > 0)` on the pool read too, so both knobs treat `0` as unset, `load`'s clamp
becomes unreachable-by-construction from the server, and the logged value is the effective one. One line,
and it makes the two adjacent env reads say the same thing about the same edge case.

**Test.** `server::tests` already owns this surface (`required_ner_is_fatal_when_absent`). The honest
version needs the env read lifted out of `load_onnx_ner` into a small pure helper (e.g.
`resolve_pool_and_intra(pool_var, intra_var, cores) -> (usize, usize)`) — which is worth it anyway, since
that helper is the thing THREAD-01 would then be able to test end-to-end rather than only its arithmetic
core: assert `("0", unset)` and `(unset, "0")` both resolve to the same `(pool, intra)` as their
unset/clamped equivalents. If that refactor isn't wanted, clamp at the read site so the logged value is at
least true.

### M7-R6 — the fixture is 22.3 KiB; every doc says 22.8 KB, and the per-KB columns use the other unit · docs · **open**

**Finding.** The harness prints its own size:

```text
=== fixture: 112 fields, 22823 bytes (22.3 KB) ===
```

22,823 B ÷ 1024 = **22.3 KiB**. Every doc says **22.8 KB** — 22,823 ÷ 1000, i.e. decimal kB:
`ROADMAP.md:550`, `DEVLOG.md:113`, `:158`, `:204`, `TESTING.md:509`, `README.md:160`, `README.it.md:161`.

The docs are **internally** inconsistent, not merely unconventional: the `ms/KB` columns are computed by
the harness as `ms / (bytes/1024.0)` (`m7_latency.rs:545-549`, `:645`), so they are per-**KiB**. The
README therefore prints "22.8 KB" and "~128 ms/KB" in the same table, and 2.85 s ÷ 22.8 = 125, not 128.
One of the two numbers is in the wrong unit and they can't both be right.

Nothing downstream changes — no conclusion turns on 2%. It is on the record because this milestone's own
standard is that a number is verified against what the test prints, and this one wasn't.

**Fix.** Say **22.3 KiB** (or just `22,823 B`, which needs no unit argument) in all seven places, matching
the harness's own output. If decimal kB is preferred for the README's general audience, then the `ms/KB`
columns must be recomputed to match — but the cheaper fix is to quote the harness.

**Test.** N/A (docs). The fixture's size guard (`(20_000..50_000).contains(&total)`) is in bytes and is
correct; only the prose derived from it slipped.

### M7-R7 — the `(Organization, "An")` over-mask: deferring is right, but its only durable home is the archive · tradeoff · **open**

**Finding.** The builder asked whether deferring this was right. **It was, and I'd have made the same
call** — for the reasons given (it fails *toward* masking, so it is not a leak; it is
[M4-R6](M4.md#m4-r6)'s accepted precision class; precision work needs its own recall argument; M7's scope
is latency). Nothing below disputes the deferral. This is about where it is written down.

Today the over-mask lives in **DEVLOG 2026-07-16** (history — correct, and inert) and in the **ROADMAP
M7 S0 box** (a milestone section that closes and stops being read). `PERF-M7-02` reports it at runtime,
which is right but only tells you if you run it. Per CLAUDE.md — *"if a finding taught the codebase a
**rule** — a tradeoff we now accept on purpose — write it into `ARCHITECTURE.md`, next to the thing it
governs. A lesson left only in the archive is one the next builder re-learns the hard way"* — this
belongs in ARCHITECTURE, and it isn't there.

**Why it is not just another M4-R6 instance** (which is the argument for filing it under M4-R6 and moving
on):
- **Different mechanism.** M4-R6 is a *deterministic recognizer* over-matching pure-numeric IDs (~18% of
  9-digit tokens). This is the **NER** emitting a 2-character fragment of a word it half-recognized. The
  fix paths are unrelated: M4-R6's is context (GLiNER); this one's is a span-quality floor or a
  subword-boundary rule.
- **Different blast radius, and it is large.** M4-R6 mangles a number in user data. This mangles
  **`"Anthropic's"` → `"[ORG_1]thropic's"` in the system prompt**, on **every Claude Code turn** — the
  instruction text the model must read correctly to behave. It corrupts *boilerplate*, not payload, and
  the proxy's own augmentation prompt then tells the model `[ORG_1]` is a real value to use verbatim.
  Nobody had seen it because nobody had run the NER over a real system prompt (which is the S0 lesson
  itself, one level down).
- **It has a latency consequence M7 already priced.** It is *why* the biggest field in the turn pays two
  passes (~940 ms of the original 4.24 s). So it is the concrete link between the precision backlog and
  the S4 fixpoint lead — the ROADMAP says S4 is "more relevant than the plan concluded" *because of this
  bug*, and that connection dies with the milestone section.

**Fix.** Two short additions, no code:
- **`ARCHITECTURE.md`**, next to the NER/over-mask discussion: record the accepted tradeoff — *the NER may
  emit sub-word fragments of organization names (measured: `"An"` from `"Anthropic's"`), which over-mask
  boilerplate in system prompts. Accepted, same class as M4-R6: it fails toward masking. It costs the
  field a second fixpoint pass, which is a latency cost, not a correctness one.*
- **`ROADMAP.md` → Backlog → *Evaluate GLiNER***, which already names itself *"the clean **precision** path
  for M4-R6's accepted over-mask"*: add this as its second exhibit, with the note that it is an
  NER-span-quality problem and so is the one of the two that a **model** change could actually fix.

**Test.** None needed — `PERF-M7-02` already reports it, at the right level (reports, does not assert;
the right number is a precision question). Its catalog entry in `TESTING.md:517-522` is accurate.
